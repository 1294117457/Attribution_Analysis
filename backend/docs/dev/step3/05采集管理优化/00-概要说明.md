# 05 采集管理优化 · 概要

> 范围：把采集管理从「**一个接口 = 一条 cron 方案**」重构为
> 「**元数据表 + 方案表 + 方案项关联表**」三表结构，
> 并把触发方式从「只有 cron」扩展为「每日定时 + 固定频率」。
> **状态：方案阶段，未改任何代码。**

---

## 0. 需求原文（两轮）

### 第一轮：触发方式

> 当前实现有「定时执行」switch + cron 下拉框，我不太理解。
> 我原本的设想是可以给某些接口设计每天定时的采集方案，或者固定频率的采集方案，
> 然后后续自动触发。就是先选择定时还是定频，然后选择固定时间或者频率，
> 就一个时间选择器选择 24 小时中的某些时间，或者频率就是可以选择多少小时、分钟、秒采集一次。
> 然后「仅交易日」和「参数配置」功能暂时不要吧，我想先保证任务触发的时间、频率功能。

### 第二轮：数据模型

> 实际就是说设计一个 collectplan，内部核心字段的采集方案的的类型、时间，
> 然后一个再一个 plan 和具体 api 关联的表，表明这个方案适用哪些接口。
> 然后给当前的 fetcher 也建表，collect_plan 也一个表，
> 然后用一个表关联 plan 和 fetcher，其中后续还可以基于关联表来记录
> plan 中对应 fetcher 需要携带什么参数。

**第二轮的结论**（详见 `06-fetcher配置化可行性分析.md`）：

| 提案部分 | 判定 |
|---------|------|
| plan 表存触发配置 | ✅ 采纳 |
| plan ↔ fetcher 关联表（带 params） | ✅ 采纳（`collect_plan_items`） |
| fetcher 建表存**元数据** | ✅ 采纳（`collect_fetchers`） |
| fetcher 逻辑配置化 | ❌ 不采纳（80% 是业务逻辑，性能收益为 0） |

## 1. 已确认的决策

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 表结构 | **三表**：`collect_fetchers` / `collect_plans` / `collect_plan_items` |
| 2 | `collect_groups` | **彻底删除**（实查 0 条数据，无沉没成本） |
| 3 | fetcher 逻辑 | **保持硬编码**，只把元数据落库 |
| 4 | 原 cron 下拉框 | **彻底删除**（UI / ORM / DB 列全部删） |
| 5 | 定频支持单位 | 秒 / 分钟 / 小时，统一存秒 |
| 6 | 「仅交易日」 | **字段删除**（查实是死字段，代码从未读取） |
| 7 | 一个接口能否多方案 | ✅ 可以（`collect_plan_items` 解除 `task_type` unique 限制） |
| 8 | **旧数据处理** | **`collect_plans` 23 行全部 DELETE，不备份**（唯一 1 条 `enabled=false` 从未生效） |
| 9 | **旧方案迁移** | **不迁移**（改造后方案列表为空，用户按需创建） |
| 10 | **向后兼容** | **一律不做**。表结构、字段名、API 全部按新模型干净重建，不留孤儿列、不留过渡代码 |
| 11 | `group_run_id` | **改名 `plan_run_id`**（含 DB 列名 + 索引名 + API 参数 + 前端字段） |

### ⚠️ 「不留兼容包袱」的具体含义

这是本次重构的**基调决策**，影响每一个设计选择：

| 不做 | 说明 |
|------|------|
| 不保留 `cron` / `params` / `trading_day_only` / `task_type` 孤儿列 | 直接 `DROP COLUMN` |
| 不做「ORM 读新列、兼容旧列」的双写 | 直接重建表结构 |
| 不做「旧 API 路径继续可用」的转发层 | `/collect/groups/*` 直接 404 |
| 不保留 `patch_plan` 兼容旧调用方 | 直接删 |
| 不做 `CronTrigger` fallback 路径 | `validate_cron` 整个删掉 |
| 不保留 `group_*` 命名的任何痕迹 | 连 DB 索引名一起改 |

**理由**：这些表目前**零有效数据**（23 行 plans 中 `enabled=true` 的有 0 条，groups 有 0 条）。
留着兼容层等于给不存在的问题写适配代码，且会长期挂在代码里增加维护成本。

## 3. 一句话结论

**代码不动，配置进 DB。**

- **代码层**：23 个 `BaseCollectTask` 子类 + 18 个 fetcher Protocol 实现 —— **一行不改**
- **数据层**：`collect_fetchers`（接口元数据镜像）+ `collect_plans`（触发配置）+ `collect_plan_items`（方案包含哪些接口 + 各带什么参数）
- **执行层**：`plan` 触发 → 按 `sort_order` 顺序跑 items → 复用现有 `submit()` / `execute_task()` 流水线

## 4. 改动规模概览

| 类别 | 文件数 | 预估 |
|------|-------|------|
| 后端 ORM / 迁移 | 3 | 40 行 |
| 后端 Service / Repo / Port | 4 | 350 行 |
| 后端 Scheduler | 1 | 120 行 |
| 后端 DTO / Router | 2 | 150 行 |
| 前端 | 4（含 1 个新组件） | 400 行 |
| 测试 | 2 | 250 行 |
| **合计** | **16** | **约 1300 行** |

**比原方案（只改触发字段，约 600 行）大 1 倍多**，主要增量在：
- `collect_plans` 主键语义从 `task_type` 改成 `id`（牵动 repo / service / API 路径）
- 前端从「单接口单卡片」改成「方案列表 + 多接口编排」（结构性变化）

⚠️ 本次会**真删数据**：
- `collect_plans` 表 **DROP TABLE**（23 行，含 1 条 `enabled=false` 的无效配置）
- `collect_groups` 表 **DROP TABLE**
- `sys_collect_tasks.group_run_id` 列 **RENAME 为 `plan_run_id`**（数据保留）
