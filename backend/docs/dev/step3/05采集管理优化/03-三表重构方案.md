## 1. 三张表的职责边界

| 表 | 性质 | 写权限 | 内容 |
|----|------|-------|------|
| `collect_fetchers` | **代码镜像**（只读） | 仅启动期自动补录 | 接口元数据：叫什么、打哪个数据源、接受什么参数、写哪张表 |
| `collect_plans` | **配置** | 用户 | 方案：叫什么、什么时候触发、失败了要不要继续 |
| `collect_plan_items` | **配置** | 用户 | 方案包含哪些接口、各带什么参数、什么顺序 |

**一句话**：`collect_fetchers` 回答"**系统有哪些接口**"，
`collect_plans` + `collect_plan_items` 回答"**什么时候跑哪些接口**"。

```
                    ┌─────────────────────────┐
                    │  collect_fetchers       │  ← 代码镜像
                    │  task_type (PK)         │
                    │  label / facet / ...    │
                    └───────────┬─────────────┘
                                │ FK (task_type)
                    ┌───────────▼─────────────┐
                    │  collect_plan_items     │
                    │  plan_id (FK)           │
                    │  task_type (FK)         │
                    │  params / sort_order    │
                    └───────────┬─────────────┘
                                │ FK (id)
                    ┌───────────▼─────────────┐
                    │  collect_plans          │  ← 用户配置
                    │  id (PK)                │
                    │  schedule_type / times  │
                    └─────────────────────────┘
```

## 2. 表结构定义

### 2.1 `collect_fetchers`（新建）

```python
class CollectFetcherDB(Base, TimestampMixin):
    """采集接口元数据（代码的 DB 镜像，启动期自动对账补录）

    ⚠️ 这张表**不是配置源**，代码里的 CollectTaskRegistry 才是唯一事实来源。
       它的价值是：UI 可展示 / 可做表单驱动的参数 schema / 启动期能发现漂移。
    """
    __tablename__ = "collect_fetchers"

    task_type: Mapped[str] = mapped_column(String(64), primary_key=True)
    label: Mapped[str] = mapped_column(String(64), nullable=False, default="")
    facet: Mapped[str] = mapped_column(String(32), nullable=False, default="")
    sub_facet: Mapped[str] = mapped_column(String(32), nullable=False, default="")
    description: Mapped[str] = mapped_column(String(255), nullable=False, default="")

    # 'batch'（采集任务，可入方案） / 'realtime'（实时接口，不可入方案）
    kind: Mapped[str] = mapped_column(String(16), nullable=False, default="batch")
    # 数据源：Tushare / Pytdx / Adata-THS
    source: Mapped[Optional[str]] = mapped_column(String(32), nullable=True)
    # 'ready'（可执行） / 'planned'（占位未实现） / 'orphan'（DB 有但代码已删）
    status: Mapped[str] = mapped_column(String(16), nullable=False, default="ready")

    default_params: Mapped[dict] = mapped_column(JSON, nullable=False, default=dict)
    # 参数字典：{"days": {"type": "int", "label": "天数", "min": 1}}
    # 供前端渲染表单；非强约束，解析失败不阻塞
    params_schema: Mapped[dict] = mapped_column(JSON, nullable=False, default=dict)
    supports_run_one: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    sort_order: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
```

| 字段 | 来源（代码） | 说明 |
|------|------------|------|
| `task_type` | `handler.name` | 主键，与 `task_registry` 的 key 一致 |
| `label` | `handler.label or handler.name` | UI 显示名 |
| `facet` / `sub_facet` | `handler.facet` / `handler.sub_facet` | 四面分类 |
| `description` | `handler.description` | 副标题 / tooltip |
| `kind` | realtime 查询 / 否则 batch | 决定能否入方案 |
| `status` | `handler.status` | ready / planned |
| `default_params` | `handler.default_params` | 参数默认值 |
| `supports_run_one` | `handler.supports_collect_one` | 是否支持按单元调用 |
| `sort_order` | `handler.sort_order` | catalog 排序 |
| `source` | 新增（见下） | **代码里目前没有**，需要给 handler 加类变量 |
| `params_schema` | 新增（见下） | **代码里目前没有**，可先留空 |
| `target_table` | 新增（见下） | ⚠️ **建议本轮不加**，见 §2.2 |

### 2.2 ⚠️ 关于 `source` / `params_schema` / `target_table`

你最初的设计里有这三列，但代码侧目前**没有对应来源**：

| 字段 | 问题 | 建议 |
|------|------|------|
| `source` | `BaseCollectTask` 没有 `source` 类变量。要加就得改 23 个文件（或在 `di.py` 维护映射表） | **本轮加类变量 + 批量赋值**，或**先留空** |
| `params_schema` | 各接口参数差异极大（`days` / `years` / `only_missing` / `limit` / `list_status`），没有统一 schema | **本轮留空**，`default_params` 已经够画表单初值 |
| `target_table` | 落库表名散落在各任务的 `RepoImpl` 调用里，没有声明式来源 | **本轮不加**（要用得先重构 23 个任务） |

**理由**：这三列都不是本次重构的必要条件。
`source` 的真实价值是"UI 显示这个接口的数据源"——但 `description` 里已经写了
（`"上榜汇总 + 净买卖额（tushare top_list）"`），收益有限。

**如果 `source` 你确实想要**，最省事的做法是在 `BaseCollectTask` 加一个类变量
并从 `di.py` 的注册映射里推导，而不是逐个改文件。见 `05-待确认问题.md` Q5。

### 2.3 `collect_plans`（改造：主键语义变更）

```python
class CollectPlanDB(Base, TimestampMixin):
    """采集方案：触发配置 + 编排策略

    ⚠️ 主键语义变更：旧版 task_type 是 unique 主关联键，
       改后 id 是主键，task_type 移到 collect_plan_items。
    """
    __tablename__ = "collect_plans"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    name: Mapped[str] = mapped_column(String(64), nullable=False)

    enabled: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)

    # None = 尚未选择触发方式（仅手动）
    # 'time'     = 每日定时（按 times 里的时间点）
    # 'interval' = 固定频率（按 interval_seconds）
    schedule_type: Mapped[Optional[str]] = mapped_column(String(16), nullable=True)

    # schedule_type='time' 时生效，形如 ["09:30", "15:00"]，24 小时制、分钟精度
    times: Mapped[list] = mapped_column(JSON, nullable=False, default=list)

    # schedule_type='interval' 时生效；单位统一存"秒"，秒/分/时只是 UI 换算
    interval_seconds: Mapped[Optional[int]] = mapped_column(Integer, nullable=True)

    # 某项失败 / 取消后是否中断后续项（吸收自 collect_groups）
    stop_on_fail: Mapped[bool] = mapped_column(Boolean, nullable=False, default=True)

    # 上次执行记录；last_task_id = 该次执行第一项的 task_id
    last_run_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=False), nullable=True)
    last_task_id: Mapped[Optional[int]] = mapped_column(Integer, nullable=True)
```

**字段变更清单**：

| 字段 | 动作 | 说明 |
|------|------|------|
| `id` | **语义变更** | 从"自增主键"变成"业务主键"（job id / API 路径都用它） |
| `name` | **新增** | 方案名，如"盘前同步"（旧版没有，因为一个接口一个方案不需要名字） |
| `enabled` | 留 | 总开关 |
| `schedule_type` | **新增** | `NULL` / `time` / `interval` |
| `times` | **新增** | `JSON` list，24 小时制时间点 |
| `interval_seconds` | **新增** | 间隔秒数 |
| `stop_on_fail` | **新增** | 吸收自 `collect_groups.stop_on_fail` |
| `last_task_id` | 留 | 上次执行的第一项 task_id |
| `task_type` | **删除映射** | 移到 `collect_plan_items` |
| `cron` | **删除映射** | 被 `times` + `schedule_type` 取代 |
| `params` | **删除映射** | 移到 `collect_plan_items.params` |
| `trading_day_only` | **删除映射** | 死字段（`02` §2.3） |
| `last_group_run_id` | 不加 | 直接复用 `last_task_id`（语义相同，都是"该次执行第一项的 task_id"） |
| `created_at` / `updated_at` | 留 | `TimestampMixin` |

### 2.4 `collect_plan_items`（新建）

```python
class CollectPlanItemDB(Base, TimestampMixin):
    """采集方案项：方案包含哪些接口 + 各带什么参数 + 执行顺序"""
    __tablename__ = "collect_plan_items"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    plan_id: Mapped[int] = mapped_column(
        Integer, ForeignKey("collect_plans.id", ondelete="CASCADE"), nullable=False, index=True,
    )
    task_type: Mapped[str] = mapped_column(
        String(64), ForeignKey("collect_fetchers.task_type"), nullable=False,
    )
    params: Mapped[dict] = mapped_column(JSON, nullable=False, default=dict)
    # 单项临时停用（不动整个方案就能跳过某一项）
    enabled: Mapped[bool] = mapped_column(Boolean, nullable=False, default=True)
    sort_order: Mapped[int] = mapped_column(Integer, nullable=False, default=0)

    __table_args__ = (
        UniqueConstraint("plan_id", "task_type", name="uq_plan_task_type"),
    )
```

**`UniqueConstraint(plan_id, task_type)` 的取舍**：

| 选项 | 优点 | 缺点 |
|------|------|------|
| **有唯一约束**（推荐） | 同一方案内不会重复跑同一接口 | 想"同一接口跑两次不同参数"就不行 |
| 无约束 | 灵活 | 可能配出重复项，用户容易踩坑 |

**我的建议**：加约束。真要跑两次不同参数，可以拆成两个方案。
如果你的场景确实需要，放开即可（`05-待确认问题.md` Q3）。

### 2.5 为什么 `interval_seconds` 存秒而不是"数值 + 单位"

存两个字段（`interval_value` + `interval_unit`）看着直观，但：
- 后端要处理单位换算，判重、比较都要先归一化
- `IntervalTrigger` 直接吃秒数，中间多一层无意义的转换

**统一存秒**：`3600` 就是 1 小时。UI 层做换算，用户选"1 小时"存 `3600`，
选"30 秒"存 `30`。后端零换算逻辑，也避免了"存了 60 秒还是 1 分钟"这类歧义。

### 2.6 交互约束

| 规则 | 值 | 理由 |
|------|-----|------|
| 定时模式时间点数量 | 1 ~ 24 个 | 24 小时最多 24 个整点，再多无意义 |
| 时间点精度 | 分钟 | 秒级定时用定频模式表达 |
| 重复时间点 | 自动去重 | `["09:30","09:30"]` 存成 `["09:30"]` |
| 时间点存储顺序 | 按 `HH:MM` 升序 | 便于 UI 回显和 diff |
| 定频下限 | **30 秒** | 见 §6.3 |
| 启用但未选方式 | 报错 | 避免"开关打开但什么都不跑"的困惑 |
| 方案至少 1 个启用项 | 报错 | 否则启用了也什么都不跑 |
| 方案名长度 | ≤ 64 | 与 `String(64)` 对齐 |

## 3. `collect_fetchers` 的维护机制

### 3.1 启动期对账

```python
async def sync_fetcher_catalog(conn) -> dict[str, int]:
    """启动时用代码注册表对账 collect_fetchers 表

    Returns: {"inserted": n, "updated": n, "orphaned": n}
    """
    from infrastructure.adapter.scheduler.collect import get_collect_task_registry
    from infrastructure.adapter.realtime import get_realtime_registry

    registry = get_collect_task_registry()
    code_side: dict[str, dict] = {}

    for t in registry.supported_types():
        h = registry.get(t)
        code_side[t] = {
            "label": h.label or h.name,
            "facet": h.facet or "",
            "sub_facet": h.sub_facet or "",
            "description": h.description or "",
            "kind": "batch",
            "status": h.status or "ready",
            "default_params": dict(h.default_params),
            "supports_run_one": h.supports_collect_one,
            "sort_order": h.sort_order,
        }

    rt = get_realtime_registry()
    for q in rt.all():
        code_side[q.name] = {
            "label": q.label or q.name, "facet": q.facet or "",
            "sub_facet": q.sub_facet or "", "description": q.description or "",
            "kind": "realtime", "status": "ready",
            "default_params": dict(q.sample_params),
            "supports_run_one": False, "sort_order": q.sort_order,
        }

    # ... upsert / orphan 标记见 §3.2
```

### 3.2 三种漂移的处理

| 情况 | 处理 | 日志 |
|------|------|------|
| 代码有、DB 无 | **自动 INSERT**（补录） | `info` |
| DB 有、代码无 | 标 `status='orphan'`，**不删** | `warning`（带 task_type 列表） |
| 两边有但元数据变了 | UPDATE + 记 warning | `warning`（列出变化字段） |

**为什么 orphan 不自动删**：删了会连带 `DELETE` 掉 `collect_plan_items`（外键 CASCADE），
用户在不知情的情况下丢掉方案配置。**保留 + 标记 + UI 禁用**更安全。

### 3.3 调用时机

```python
# main.py lifespan —— 必须在 setup_collect_task_registry 之后
setup_collect_task_registry([...])          # 先注册代码侧
setup_realtime_registry([...])
await _sync_fetcher_catalog()               # 再对账 DB
if settings.COLLECT_SCHEDULER_ENABLED:
    await start_collect_scheduler(...)
```

⚠️ **顺序很重要**：`_sync_fetcher_catalog` 依赖 `get_collect_task_registry()`，
必须放在 `setup_collect_task_registry(...)` 之后。

### 3.4 顺带解决一个隐患

`collect_plan_items.task_type` 有 FK 指向 `collect_fetchers.task_type`。
如果 `collect_fetchers` 的行被人工删了，FK 会阻止（默认 RESTRICT）。
**这是好事**——比"方案项指向不存在的接口"要好。

但要注意：PostgreSQL 的 FK 要求目标列有 unique/primary 约束。
`collect_fetchers.task_type` 是 primary key，满足条件。✅

## 4. 调度逻辑

### 4.1 job id 约定

```
定时模式： plan:{plan_id}@{HH:MM}     每个时间点一个独立 job
定频模式： plan:{plan_id}             单 job
```

从 `plan:{task_type}` 改成 `plan:{plan_id}`——因为一个接口现在可以出现在多个方案里，
job id 必须能区分方案。

### 4.2 ⚠️ 核心：定时模式必须一个时间点一个 job

**不能把多个时间点合并成一个 cron 表达式**，理由见 `02-现状盘点与问题诊断.md` §2.5（笛卡尔积问题）。

```python
def sync_plan(
    self,
    plan_id: int,
    enabled: bool,
    schedule_type: Optional[str],
    times: Optional[list[str]] = None,
    interval_seconds: Optional[int] = None,
) -> None:
    """按方案配置同步 APScheduler job"""
    prefix = f"plan:{plan_id}"
    self._remove_prefix(prefix)          # ← 必须先清掉该方案的所有旧 job

    if not (enabled and schedule_type):
        return

    if schedule_type == "time":
        for hhmm in times or []:
            hour, minute = (int(x) for x in hhmm.split(":"))
            self._scheduler.add_job(
                self._fire_plan,
                CronTrigger(hour=hour, minute=minute, timezone=self._tz),
                args=[plan_id],
                id=f"{prefix}@{hhmm}",
                replace_existing=True,
                max_instances=1,
                coalesce=True,
                misfire_grace_time=300,
            )
        logger.info("注册采集 job: plan=%d  定时 %s", plan_id, times)
        return

    if schedule_type == "interval":
        self._scheduler.add_job(
            self._fire_plan,
            IntervalTrigger(seconds=interval_seconds),
            args=[plan_id],
            id=prefix,
            replace_existing=True,
            max_instances=1,
            coalesce=True,
            misfire_grace_time=60,      # 定频容错窗口调小，避免积压补跑
        )
        logger.info("注册采集 job: plan=%d  每 %ds", plan_id, interval_seconds)
```

**`max_instances=1` 现在有了新含义**：以前是"一个接口一个 job"，
现在是"一个方案一个 job 槽位"。方案内 3 个接口串行执行，
第 2 次触发时第 1 次还没跑完 → 跳过。**这正是想要的防重叠语义。**

### 4.3 前缀清理 + 取最早触发时间

APScheduler 没有"按前缀删除"的 API，要自己写：

```python
def _remove_prefix(self, prefix: str) -> None:
    """删除该前缀下的所有 job（含 @HH:MM 后缀的多个子 job）"""
    for job in self._scheduler.get_jobs():
        if job.id == prefix or job.id.startswith(prefix + "@"):
            self._scheduler.remove_job(job.id)
```

`next_run` 改成取**前缀下所有 job 的最小值**：

```python
def next_run(self, prefix: str) -> Optional[datetime]:
    """该方案的下次触发时间 = 多个 job 中最早的那个"""
    runs = [
        job.next_run_time
        for job in self._scheduler.get_jobs()
        if job.id == prefix or job.id.startswith(prefix + "@")
    ]
    runs = [r for r in runs if r is not None]
    return min(runs) if runs else None
```

⚠️ **job id 的前缀冲突**：`plan:1` 是 `plan:1@09:30` 的前缀，
但 `plan:11` 也是 `plan:1` 的前缀……**等等，`plan:1` 不等于 `plan:1@`**，
所以 `startswith("plan:1@")` 不会命中 `plan:11@09:30`。安全。

但要**写测试验证这一点**（`04` §2 测试⑥）。

### 4.4 校验函数替换 `validate_cron`

```python
MIN_INTERVAL_SECONDS = 30
_TIME_RE = re.compile(r"^(?:[01]\d|2[0-3]):[0-5]\d$")

def validate_schedule(
    schedule_type: Optional[str],
    times: Optional[list[str]],
    interval_seconds: Optional[int],
) -> None:
    """校验触发配置；非法时抛 ValueError

    - schedule_type 必须是 None / 'time' / 'interval'
    - 'time'：times 至少 1 个、最多 24 个，格式严格 HH:MM
    - 'interval'：interval_seconds 必须 ≥ MIN_INTERVAL_SECONDS
    """
    if schedule_type not in (None, "time", "interval"):
        raise ValueError(f"触发方式无效: {schedule_type}")
    if schedule_type == "time":
        tl = times or []
        if not tl:
            raise ValueError("启用每日定时需要至少一个触发时间")
        if len(tl) > 24:
            raise ValueError(f"触发时间最多 24 个，当前 {len(tl)} 个")
        for t in tl:
            if not _TIME_RE.match(str(t)):
                raise ValueError(f"时间格式无效: {t!r}（应为 HH:MM，如 09:30）")
    if schedule_type == "interval":
        if interval_seconds is None:
            raise ValueError("启用固定频率需要设置间隔")
        if interval_seconds < MIN_INTERVAL_SECONDS:
            raise ValueError(f"采集间隔不能小于 {MIN_INTERVAL_SECONDS} 秒")
```

**要点**：
- `HH:MM` 用正则严格校验，**不要只 `split(":")` 然后 `try/except int`**，
  否则 `"9:5"` 会被当成 9 点 5 分
- `MIN_INTERVAL_SECONDS = 30` 定义成模块级常量，方便测试和后续调整

### 4.5 启动期重建

```python
for p in plans:
```

### 4.6 `_fire_plan` 改成按 plan_id

```python
async def _fire_plan(self, plan_id: int) -> None:
    """定时触发：执行整个方案（按 sort_order 顺序跑各方案项）"""
    from application.service import CollectManageService
    from infrastructure.config.di import get_collect_manage_service

    svc = get_collect_manage_service()
    try:
        # 放进托管集合，关闭时由 cancel_background 统一取消
        from application.service import spawn
        run_id = await svc.run_plan(plan_id, trigger="schedule")
        logger.info("采集方案 %d 定时触发完成: plan_run_id=%s", plan_id, run_id)
    except Exception:
        logger.exception("采集方案 %d 定时触发失败", plan_id)
```

**与现在的差异**：现在是 `await svc.submit(task_type, None, trigger="schedule")`（非阻塞，立即返回）。
改成 `run_plan` 后会**阻塞到整个方案执行完**。

⚠️ **这是有意的**：因为 `max_instances=1` 保证同一方案不会重叠，
阻塞等待不会导致 job 堆积。而 `spawn()` 保证进程关闭时能被统一取消。

### 5.2 实现（基于现有 `run_group` 改造）

```python
async def run_plan(self, plan_id: int, trigger: str = "manual") -> Optional[int]:
    async with self._session_factory() as session:
        plan = await self._config_repo.get_plan(plan_id, session)
        if plan is None:
            logger.warning("采集方案 %d 不存在，跳过执行", plan_id)
            return None
        name = plan.name
        stop_on_fail = plan.stop_on_fail
        items = await self._config_repo.list_plan_items(session, plan_id)   # 已按 sort_order 排序

    plan_run_id: Optional[int] = None
    logger.info("采集方案 [%s] 开始: %d 项, trigger=%s", name, len(items), trigger)

    for idx, item in enumerate(items, 1):
        task_type = item.task_type
        try:
            sub = await self.prepare(
                task_type, item.params, trigger,
                plan_item_params=item.params,     # ← 参数来源改为方案项
                plan_run_id=plan_run_id,
                plan_first=plan_run_id is None,
            )
        except TaskConflict as e:
            logger.info("采集方案 [%s] 第 %d 项跳过: %s", name, idx, e)
            continue
        except Exception as e:
            logger.error("采集方案 [%s] 第 %d 项 %s 创建失败: %s", name, idx, task_type, e)
            if stop_on_fail:
                break
            continue
        # ... 同 run_group 的后续逻辑（execute_task + 中断判断 + _touch_plan）
```

### 5.3 `sys_collect_tasks.group_run_id` → `plan_run_id`（改名，不复用）

**决策 #11：改名，不保留旧名。**

`sys_collect_tasks` 这一列的语义从"任务组执行 ID"变成"方案执行 ID"。
既然定了「不留兼容包袱」，就**连列名和索引名一起改干净**：

| 位置 | 旧 | 新 |
|------|-----|-----|
| DB 列 | `group_run_id` | `plan_run_id` |
| DB 索引 | `ix_sys_collect_tasks_group_run_id` | `ix_sys_collect_tasks_plan_run_id` |
| ORM 字段 | `SysCollectTaskDB.group_run_id` | `SysCollectTaskDB.plan_run_id` |
| `task_to_dict` 输出 key | `"group_run_id"` | `"plan_run_id"` |
| 列表查询参数 | `?group_run_id=xxx` | `?plan_run_id=xxx` |
| 前端 `CollectTask` 字段 | `group_run_id: number \| null` | `plan_run_id: number \| null` |
| `prepare()` 参数 | `group_run_id=` / `group_first=` | `plan_run_id=` / `plan_first=` |
| `CollectPlanDB` 字段 | `last_group_run_id` | `last_task_id`（沿用，不新增列） |

**列内数据保留** —— `RENAME COLUMN` 不动数据，历史任务的关联关系不丢（见 §7.6）。

**`prepare()` 的两个参数一并改名**：


### 5.4 ⚠️ 顺手修 `stop_on_fail` 的判断条件

现在只看 `status`，而 `_decide_status` 里"部分失败也算 success"，
导致 `stop_on_fail` 基本不生效（`02` §2.4）。

```python
# ❌ 旧：只看 status
if stop_on_fail and status in ("failed", "cancelled"):
    break

# ✅ 新：status 终态失败，或失败率超过阈值
failed_hard = status in ("failed", "cancelled")
failed_mostly = (
    row.success_count == 0
    and row.fail_count > 0
)
if stop_on_fail and (failed_hard or failed_mostly):
    logger.warning(
        "采集方案 [%s] 第 %d 项 %s 中断（成功%d 失败%d），停止后续 %d 项",
        name, idx, status, row.success_count, row.fail_count, len(items) - idx,
    )
    break
```

⚠️ **注意**：我没有改成"失败率 > X%"，因为阈值需要你定（`05` Q4）。
上面这版只拦"完全失败"和"零成功"，比原来的"永远不触发"好，
但对"4900 失败 / 100 成功"这种极端情况仍不会中断。

**如果你要真正的失败率阈值**，需要在 `collect_plans` 加一个字段
`fail_rate_threshold: float`（默认 1.0 = 只要有一个成功就继续）。
见 `05-待确认问题.md` Q4。

```python
async def replace_plan_items(self, session, plan_id: int, items: list[dict]) -> None:
    """全量替换方案项（PUT 语义）

    ⚠️ 不能简单 DELETE 全部再 INSERT —— 那样 sort_order 变了会导致
       方案项 id 全部变化。这里用差量更新：保留 id 不变的，只删新增/删除的。
    """
    existing = {i.task_type: i for i in await self.list_plan_items(session, plan_id)}
    wanted = {it["task_type"] for it in items}

    # 删除不再存在的
    for tt, row in existing.items():
        if tt not in wanted:
            await session.delete(row)

    # 新增 / 更新
    for idx, it in enumerate(items):
        tt = it["task_type"]
        if tt in existing:
            row = existing[tt]
            row.params = dict(it.get("params") or {})
            row.enabled = bool(it.get("enabled", True))
            row.sort_order = idx * 10          # 10 的倍数便于中间插入
        else:
            session.add(CollectPlanItemDB(
                plan_id=plan_id, task_type=tt,
                params=dict(it.get("params") or {}),
                enabled=bool(it.get("enabled", True)),
                sort_order=idx * 10,
            ))
    await session.flush()
```

```python
def _check_plan(self, fields: dict) -> dict:
    name = (fields.get("name") or "").strip()
    if not name:
        raise ValueError("方案名称不能为空")
    if len(name) > 64:
        raise ValueError("方案名称不能超过 64 个字符")

    schedule_type = fields.get("schedule_type")
    times = _normalize_times(fields.get("times"))
    interval_seconds = fields.get("interval_seconds")
    validate_schedule(schedule_type, times, interval_seconds)

    enabled = bool(fields.get("enabled"))
    if enabled and not schedule_type:
        raise ValueError("启用方案需要选择触发方式")

    items = self._validate_items(fields.get("items") or [])
    if enabled and not items:
        raise ValueError("启用方案需要至少一个启用的采集接口")
    if not items:
        raise ValueError("方案至少需要包含一个采集接口")

    return {
        "name": name, "enabled": enabled,
        "schedule_type": schedule_type, "times": times,
        "interval_seconds": interval_seconds,
        "stop_on_fail": bool(fields.get("stop_on_fail", True)),
        "items": items,
    }


def _validate_items(self, items: list[dict]) -> list[dict]:
    """校验方案项：已注册 / status=ready / 非实时接口 / 不重复"""
    seen: set[str] = set()
    out: list[dict] = []
    for it in items:
        task_type = (it.get("task_type") or "").strip()
        if not task_type:
            continue
        if task_type in seen:
            raise ValueError(f"方案内重复的采集接口: {task_type}")
        seen.add(task_type)

        if self._realtime_registry.get(task_type) is not None:
            raise ValueError(f"{task_type} 是实时接口，不能加入方案")
        handler = self.handler(task_type)           # 未注册 → UnknownTaskType
        if handler.status != "ready":
            raise ValueError(f"{task_type} 尚未实现，不能加入方案")

        out.append({
            "task_type": task_type,
            "params": dict(it.get("params") or {}),
            "enabled": bool(it.get("enabled", True)),
        })
    return out
```

### 7.5 重建方式：`DROP TABLE` + `create_all`

```python
async def _rebuild_collect_config_tables(conn) -> None:
    """重建采集配置三表（破坏性 · 一次性）

    ⚠️ 会真删数据。执行前提（已确认）：
      - collect_plans 23 行，其中 enabled=true 的 0 行，无任何有效配置
      - collect_groups  0 行
      - 用户已确认不需要备份

    幂等策略：用 information_schema 判断新结构是否已就位，已就位则直接返回。
    这样第二次启动不会把用户新建的方案再删一遍。
    """
    from sqlalchemy import text

    # ① 检测是否已是新结构（新结构有 name / schedule_type，且无 task_type 列）
    probe = await conn.execute(text("""
        SELECT column_name FROM information_schema.columns
        WHERE table_name = 'collect_plans'
    """))
    cols = {r[0] for r in probe.fetchall()}
    if {"name", "schedule_type"} <= cols and "task_type" not in cols:
        logger.info("collect_plans 已是新结构，跳过重建")
        return
    if not cols:
        # 表不存在（首次部署）→ 无需重建，交给 create_all
        return

    # ② 删除旧表（collect_plan_items 若存在也要先删，它有 FK 指向 collect_plans）
    for stmt in [
        "DROP TABLE IF EXISTS collect_plan_items",
        "DROP TABLE IF EXISTS collect_plans",
        "DROP TABLE IF EXISTS collect_groups",
    ]:
        await conn.execute(text(stmt))
    logger.warning("已删除旧 collect_plans / collect_groups 表，将按新结构重建")
```

⚠️ **删表顺序很重要**：`collect_plan_items` 有 FK 指向 `collect_plans`，
必须先删子表（虽然 `DROP TABLE` 会自动处理依赖，但显式写更清晰）。

### 7.6 `sys_collect_tasks` 列改名：`group_run_id` → `plan_run_id`

这是**唯一需要在保留数据的表上做破坏性操作**的地方（`sys_collect_tasks` 有真实任务历史）。

```python
async def _rename_group_run_id_to_plan_run_id(conn) -> None:
    """sys_collect_tasks.group_run_id → plan_run_id（列名 + 索引名）

    ⚠️ 改索引名是因为 ORM 的 index=True 会按新列名生成 ix_sys_collect_tasks_plan_run_id，
       旧索引名残留会造成索引重复。

    列内数据保留（历史任务的 group_run_id 值直接沿用，语义一致）。
    """
    from sqlalchemy import text
    probe = await conn.execute(text("""
        SELECT column_name FROM information_schema.columns
        WHERE table_name = 'sys_collect_tasks'
    """))
    cols = {r[0] for r in probe.fetchall()}

    if "plan_run_id" in cols:          # 已改名，幂等返回
        return
    if "group_run_id" not in cols:     # 从未有过该列（全新库）
        return

    for stmt in [
        "DROP INDEX IF EXISTS ix_sys_collect_tasks_group_run_id",
        "ALTER TABLE sys_collect_tasks RENAME COLUMN group_run_id TO plan_run_id",
        "CREATE INDEX IF NOT EXISTS ix_sys_collect_tasks_plan_run_id ON sys_collect_tasks (plan_run_id)",
    ]:
        try:
            await conn.execute(text(stmt))
        except Exception as e:
            logging.warning("plan_run_id 改名跳过: %s | %s", stmt, e)
```

⚠️ **`RENAME COLUMN` 保留列内数据**，所以历史任务的关联关系不丢。
这与 `collect_plans` 的「删表重建」不同——那张表没数据，这张表有真实历史。

**为什么必须改索引名**：
```191:192:D:\codes\Attribution_Analysis\backend\src\main.py
        "ALTER TABLE sys_collect_tasks ADD COLUMN IF NOT EXISTS group_run_id INTEGER",
        "CREATE INDEX IF NOT EXISTS ix_sys_collect_tasks_group_run_id ON sys_collect_tasks (group_run_id)",
```
ORM 里 `plan_run_id: Mapped[Optional[int]] = mapped_column(Integer, nullable=True, index=True)`
会生成 `ix_sys_collect_tasks_plan_run_id`。如果旧索引还在，同一列会有两个索引。

### 7.7 新表的创建时机

**两张新表不需要迁移函数** —— `Base.metadata.create_all` 自动建：

```python
# main.py lifespan
async with async_engine.begin() as conn:
    await _migrate_rename_kline_table(conn)
    await _migrate_concepts_adata_rebuild(conn)
    await conn.run_sync(Base.metadata.create_all)     # ← 重建后立刻建出新结构
```

⚠️ **顺序至关重要**：`create_all` 在第一段事务，删表也必须在第一段事务**之前**完成，
否则 `create_all` 会先按新 ORM 建表（表已存在 → 跳过），然后删表把它删掉。

**正确顺序**：把删表也放到 `create_all` 之前。

```typescript
export function formatInterval(seconds: number | null | undefined): string {
  if (!seconds || seconds <= 0) return '-'
  if (seconds % 3600 === 0) return `${seconds / 3600} 小时`
  if (seconds % 60 === 0) return `${seconds / 60} 分钟`
  return `${seconds} 秒`
}

export function scheduleLabel(p: {
  enabled: boolean
  schedule_type: 'time' | 'interval' | null
  times: string[]
  interval_seconds: number | null
}): string {
  if (!p.schedule_type) return '仅手动'
  const body =
    p.schedule_type === 'time'
      ? `每日 ${(p.times ?? []).join('、')}`
      : `每 ${formatInterval(p.interval_seconds)}`
  return p.enabled ? body : `${body}（已停用）`
}
```

## 10. 风险与回滚

| 风险 | 等级 | 缓解 |
|------|------|------|
| 前端结构性重写引入 bug | 🟡 中 | 后端先行，前端最后做；`collect/catalog` 端点不动保证手动采集不受影响 |
| **删表顺序写错导致新表没建出来** | 🔴 高 | §7.8 明确：`_rebuild_collect_config_tables` 必须在 `create_all` **之前**；重建函数用 `information_schema` 探测保证幂等 |
| `collect_fetchers` 与代码漂移导致方案项失效 | 🟢 低 | 启动期对账 + orphan 标记 + UI 禁用 |
| 改后端文件杀掉在跑的采集 | 🟢 低 | 动工前确认无运行中任务 |
| 定时方案误配高频导致打爆数据源 | 🟡 中 | `MIN_INTERVAL_SECONDS=30` + `max_instances=1` + `TaskConflict` 三重保护 |
| 旧前端调已删的 `/collect/groups` | 🟢 低 | 后端先改、前端后改，中间窗口期该页面报错但不影响其他功能 |

### 回滚路径

**因为「不留兼容」是有意的破坏性改动，回滚只有一条路：git revert + 重建表。**

| 层 | 操作 |
|----|------|
| 代码 | `git revert` 全部改动（本次改动建议单独一个 commit） |
| DB · `collect_plans` / `collect_groups` | 已 DROP TABLE。回滚后 `create_all` 会按旧 ORM 自动重建空表，**数据不恢复**（本来就无有效数据） |
| DB · `collect_fetchers` / `collect_plan_items` | 留空表无害，回滚后 ORM 不映射 |
| DB · `sys_collect_tasks.plan_run_id` | `RENAME COLUMN` 可逆：`ALTER TABLE sys_collect_tasks RENAME COLUMN plan_run_id TO group_run_id`，**数据完整保留** |
| DB · 索引 | 同样可逆：`DROP INDEX ix_..._plan_run_id` + `CREATE INDEX ix_..._group_run_id` |

**唯一的真实数据损失**：`collect_plans` 那 23 行（其中 0 行有效配置）。这是有意的（决策 #8）。
