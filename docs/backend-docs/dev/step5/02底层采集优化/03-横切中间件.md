# 03 横切中间件：Metrics / Retry / Throttle

> 对应 README 流程 ⑥。阶段 P1 建好，P2 / P3 逐步删除旧的重复实现。

## 1. 现在重复在哪

| 位置 | 重复内容 |
| :-- | :-- |
| 13 个任务文件（`cap_*` ×6、`fin_top10_*` ×2、`base_*` ×4、`fin_report`） | `RATE_LIMIT_WAIT=60`、`RATE_LIMIT_RETRIES=3`、`_fetch_with_rate_limit`、`_sleep_cancellable`、`_check_cancel`、`asyncio.to_thread` |
| `daily_kline.py` | `_fetcher_pool`、`_api_interval`、限频退避 `1s → 60s` |

| `realtime/framework.py` | `SOURCE_CONCURRENCY={"ths":5,"tdx":1}` 同源并发 |

同一个 tushare token 的限频，现在由各任务各自感知、各自等待，彼此不知道对方在等。

## 2. 装配顺序

```python
def build_middleware(prov: Provider) -> Provider:
    return Metrics(Retry(Throttle(prov, group=prov.throttle_group)))
```

```
调用 → Metrics → Retry → Throttle → Provider.fetch → Client
```

- **Metrics 在最外层**：一次调用（含内部重试）只记一次，耗时包含等待时间，反映调用方真实感受。
- **Retry 在 Throttle 外面**：每次重试都重新排队拿令牌，重试不会绕过限流把配额打爆。
- 三个包装类都继承 `Provider`，对外接口完全不变，Gateway 感知不到。

实时查询的缓存不放在这条链里，留在 `RealtimeQueryFramework`（见 05）。缓存的 TTL 跟交易时段走、还要做单飞和过期降级，这些只对实时查询有意义。

## 3. Throttle（同源限流）

```python
THROTTLE_GROUPS = {
    "tushare":  ThrottleConfig(concurrency=settings.COLLECT_MAX_CONCURRENCY, min_interval=0.15),
    "adata:ths": ThrottleConfig(concurrency=5, min_interval=0.5),
    "tdx":      ThrottleConfig(concurrency=1, min_interval=0),
}
```

- 每个分组一个 `asyncio.Semaphore` + 最小调用间隔。**同组的所有 Provider 共享**：日 K、资金流向、估值共用 tushare 一个分组。
- 数值来源：`tdx=1` / `ths=5` 取自现在的 `SOURCE_CONCURRENCY`；`adata` 的 0.5s 取自 `REQUEST_DELAY`；tushare 的 0.15s 取自 `daily_kline` 的 `concurrency * 0.15`。上线后按实际限频情况调整。
- 配置放 `datasource/core/middleware.py` 的常量里，不新增 env；确实需要按环境调整时再加 settings 字段。
- 单进程假设，与现在一致。多副本部署时要改成 Redis 令牌桶，本次不做。

**风险**：采集任务和实时查询共用 `adata:ths` 分组。概念批量采集期间，页面上的概念分时查询需要排队。这是正确的（两者共用同花顺的 IP 配额），但如果体感变慢，后续可以给实时查询预留 1 个并发名额。

## 4. Retry（同源重试）

| 异常 | collect 策略（默认） | query 策略（实时） |
| :-- | :-- | :-- |
| `RateLimited(retry_after)` | 等 `retry_after`（tushare 60s），最多 3 次 | 不等，直接抛（交给 Gateway 换源或实时降级） |
| `SourceUnavailable` | 退避 1s、3s，最多 2 次 | 退避 0.5s，最多 1 次 |
| `InvalidParams` / `NotSupported` | 不重试 | 不重试 |

collect 策略的数值与现在一致：tushare 的 `RATE_LIMIT_WAIT=60` / `RATE_LIMIT_RETRIES=3`，adata 的 `RETRY_BACKOFF=(1,3)`。

### 4.1 策略怎么传进来

Provider 签名不变，用 `contextvars` 传调用上下文：

```python
# datasource/core/context.py
call_policy: ContextVar[CallPolicy] = ContextVar("call_policy", default=CallPolicy.COLLECT)
cancel_check: ContextVar[Callable[[], None] | None] = ContextVar("cancel_check", default=None)
```

- `DataGateway.fetch(..., policy=CallPolicy.QUERY)` 在调用前设置 `call_policy`；实时框架传 `QUERY`，其余默认 `COLLECT`。
- `execute_task` 开始时设置 `cancel_check = lambda: _raise_if_cancelled(task_id)`（抛的就是现在的 `Cancelled`）。
- datasource 层只调用这个函数，不 import 采集模块，依赖方向不反转。

### 4.2 可取消的等待

```python
async def _sleep(seconds: float) -> None:
    check = cancel_check.get()
    while seconds > 0:
        if check: check()                 # 已取消 → 抛 Cancelled，任务立即收尾
        step = min(1.0, seconds)
        await asyncio.sleep(step)
        seconds -= step
```

这就是现在每个任务里的 `_sleep_cancellable`，只写这一份。用户在页面上点取消，正在等 60s 限频的任务最多 1 秒内退出，行为与现在一致。

## 5. Metrics（调用统计）

- Redis：`ds:stats:{dataset}:{tool}:{yyyymmdd}`，HASH 字段 `calls / errors / rate_limited / latency_sum / last_error / last_error_at`，保留 7 天。格式与现有 `rt:stats:*` 一致。
- 日志：失败时打一行 `dataset / tool / 异常类型 / 耗时`，用 `%r` 输出异常（adata 有空 message 的异常，现在的 framework 已经踩过这个坑）。
- 写统计失败只打 debug，不影响调用。
- 采集管理页可在接口详情里展示每个数据源的成功率和最近错误（前端改动另议，本次只保证数据有）。

## 7. 验收

- 人为把 tushare 分组 `concurrency` 调成 1 跑 `cap_moneyflow`，确认串行；恢复后并发正常。
- 限频场景（连续采集触发 tushare 限频）下，日志显示等待 60s 后重试成功，进度不重复计数。
- 等待限频期间点取消，任务 1 秒内变为 `cancelled`。
