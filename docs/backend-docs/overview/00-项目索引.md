## 1. 项目概览

A 股个股归因分析系统：采集行情 / 估值 / 概念等多维数据入库，前端做股票面板、操作池、采集管理，并为后续 AI 归因提供统一数据入口（`GET /api/v1/stocks/{symbol}/analysis`）。

| 层 | 技术 |
|---|---|
| 后端 | Python 3.13 · FastAPI · SQLAlchemy 2（async + asyncpg）· pydantic-settings |
| 存储 | PostgreSQL（`stock_db`）· Redis（采集进度 `collect:progress:{task_id}`、实时接口缓存 `rt:{name}:{key}` / 统计 `rt:stats:*`） |
| 数据工具 | tushare 1.4.3 · adata 2.9.5 · tdxpy（pytdx 协议）· pandas |
| 前端 | Vue 3 · TypeScript · Vite · Element Plus · Pinia |

## 2. 运行方式

```powershell
# 后端（backend/ 目录，读取 backend/.env）
python .\src\main.py            # uvicorn :8000，WatchFiles 热重载；Swagger: /docs

# 命令行触发采集任务（依次执行并等待完成）
python .\scripts\trigger_collect.py concept concept_membership --limit 20

# 测试
pytest tests\infrastructure
```

关键配置（`src/infrastructure/config/settings.py`，`.env` 覆盖）：`DATABASE_URL`、`REDIS_URL`、`TUSHARE_TOKEN`、`COLLECT_CONCURRENCY`(3) / `COLLECT_MAX_CONCURRENCY`(8) / `COLLECT_CHUNK_SIZE`(30)。

注意：
- 启动时 `main.py` 的 `lifespan` 会先跑迁移函数（`_migrate_*`，重命名/重建旧表）再 `Base.metadata.create_all`，**没有 Alembic**，新表靠 ORM 自动建、改列需写迁移函数。
- WatchFiles 也监听 `scripts/`、`tests/`，改这些文件会触发重载；重载会等待正在跑的后台采集任务。
- `tests/test_e2e_api.py` 会删除开发库数据，勿在有真实数据的库上跑。

## 6. 采集框架

> 摘要：[`collectmanage摘要.md`](collectmanage摘要.md)（链路 / 任务表 / 业务侧采集入口 / 已知问题）

- **任务基类** `scheduler/collect/base.py` `BaseCollectTask`
  - 元数据 ClassVar：`name`（task_type）/ `facet` / `sub_facet` / `label` / `description` / `status`（`ready`|`planned`）/ `sort_order`（同子分类内排序）
  - 生命周期：`estimate_total(params)` → `run(params, on_unit_done)` → `TaskSummary`；取消通过 `is_cancelled` 协作式检查（抛 `Cancelled`）
  - 单元接口：`list_units(params)` + `collect_one(unit, params) -> UnitResult`；默认 `run()` 遍历单元（`concurrency` 分批、失败末尾重试一轮），`default_params` 为默认参数
  - 状态判定：仅 `success == 0 且 fail > 0` 时为 failed
- **统一入口** `application/service/collect_app_service.py` `CollectAppService`：`submit`（后台任务，防重 + 记录 + Redis）/ `run_one`（同步单元，业务路由用）/ 采集方案 CRUD（`collect_plans` + `collect_plan_items`）/ 方案执行（串行，`stop_on_fail`）
  > ⚠️ **任务组（`collect_groups` / `run_group`）已彻底移除**——原 S0–S4 方案里的「任务组」被「采集方案 + 方案项」两表取代，代码中仅 `main.py` 的 `_rebuild_collect_config_tables()` 保留 `DROP TABLE IF EXISTS collect_groups` 作历史清理。
- **调度器** `scheduler/collect_scheduler.py`：APScheduler（`Asia/Shanghai`），启动时加载启用的 `collect_plans`；`.env` `COLLECT_SCHEDULER_ENABLED=false` 可关闭
- **注册表** `scheduler/collect/registry.py`：`main.py` lifespan 注册所有任务；`catalog()` 输出 facet → sub_facet → tasks（按 `(sort_order, label)` 排序），空 facet 不输出。四个 facet：`tech` 技术面 / `capital` 资金面 / `fundamental` 基本面 / `news` 新闻面。
- **Fetcher 绑定** `infrastructure/config/di.py: setup_default_registry()`（在 lifespan 调用，按三组注册）：

- **⚠️ 绝不要在 `backend/` 任何位置写文件（临时脚本 / 日志 / 输出）**：`main.py` 用了 `reload=True` + watchlist，WatchFiles 监听整个 `backend/` 目录。**日志文件被持续写入 = 每次写入都触发热重载 = 后端反复重启 = 正在跑的采集任务被 `asyncio.CancelledError` 杀掉**（`execute_task` 会把它记成 `status=cancelled`，且后端日志里看不到任何采集记录，只有"被事件循环取消"）。2026-10-05 连续踩坑两次：先是在根目录建 `__tmp_verify.py`，后是用 `Tee-Object` 把采集日志写进 `backend/scripts/`——两次都导致 `fin_top10_floatholders` 任务在 0~33 秒内被取消。**正确做法**：临时脚本放 `backend/` 之外（如仓库根的 `scripts_tmp/`），日志只输出到终端或写进 `backend/` 外的路径；提交采集后不要在后端目录内产生任何文件变动。
