# 基础设施规范

> 适用范围：`backend-java` 全部 Maven 模块
> 核心原则：**所有跨进程、跨线程的资源，配置必须显式、生命周期必须交给 Spring、降级必须有兜底。**
> 配套文档：`../纵向分层规范/Service层规范.md`（谁该用这些资源）、`异常与响应规范.md`（失败怎么表达）

---

## 0. 一句话结论
> **连接池、线程池、Redis、HTTP 客户端——这四类资源都是「共享且昂贵」的。**
> 规则只有三条：**① 显式配置，不靠默认值 ② 生命周期交给 Spring ③ 降级路径必须写清楚。**

---

## 1. 职责速查

| 资源 | 谁创建 | 谁销毁 | 谁使用 |
|---|---|---|---|
| 数据库连接池 | Spring Boot（`DataSource`）| 容器关闭时 | Mapper（通过 MyBatis）|
| 业务线程池 | Spring（`@Bean`）| 容器关闭时 | Service（异步任务）|
| Redis 连接 | Spring Boot（Lettuce）| 容器关闭时 | Service（缓存 / 限流 / 验证码）|
| HTTP 客户端 | Spring Cloud OpenFeign | 容器关闭时 | Service（跨服务调用）|

> ⚠️ **共同点**：这四样**都不是**业务代码该 `new` 出来的。
> 业务代码只负责「用」，不负责「建」和「关」。

## 2. 数据库连接池

### 2.1 核心原则

| 原则 | 说明 |
|---|---|
| **必须显式配置，不靠默认值** | HikariCP 默认 `maximum-pool-size=10`，在有业务线程池的场景下往往不够 |
| **池大小 ≥ 可能同时占用连接的线程数** | 否则线程会阻塞在「等连接」上，表现为接口变慢而非报错 |
| **必须设 `connection-timeout`** | 池满时快速失败（暴露问题），好过无限等待（掩盖问题） |
| **`idle-timeout` < `max-lifetime`** | 否则空闲连接不会被回收，池会持续膨胀 |
| **`max-lifetime` < DB 侧连接回收时间** | 避免连接被 DB 单方面掐断 |
| **开启泄漏检测** | 忘记 `close()` 的连接能被自动发现 |

### 2.2 参数说明

| 参数 | 含义 | 设定依据 |
|---|---|---|
| `maximum-pool-size` | 池内最大连接数 | ≥ (Tomcat 请求线程数 + 业务线程池并发数) × 安全系数，**但不超 DB 的 `max_connections` 可承受份额** |
| `minimum-idle` | 最小空闲连接 | 略大于「日常并发」，避免冷启动首个请求等建连 |
| `connection-timeout` | 获取连接的最长等待（毫秒）| 远端 DB 取较短值。超时说明池已被打满，应尽快暴露 |
| `idle-timeout` | 空闲连接回收时间（毫秒）| **必须小于** `max-lifetime`，否则连接根本不会被回收 |
| `max-lifetime` | 连接最大存活时间（毫秒）| 应**大于** `idle-timeout`，且**小于** DB 侧的连接回收时间（如 `idle_in_transaction_session_timeout`），避免被 DB 单方面掐断 |
| `leak-detection-threshold` | 泄漏检测阈值（毫秒）| 明显大于单次查询耗时。**调成 0 会关闭该功能** |

> 📌 **关于探活**：PostgreSQL JDBC 驱动实现了 `Connection.isValid()`，
> HikariCP 默认走它，**不需要**额外配 `connection-test-query`（配了反而多一次往返）。
> 只有驱动不支持 `isValid()` 时才需要显式指定探活 SQL。

> 📌 **连接池大小的经验公式**：`连接数 ≈ CPU 核数 × 2 + 磁盘数`（针对 IO 密集型再加业务线程数）。
> 但**上限由 DB 决定**：多个应用实例共享一个 DB 时，
> `所有实例的池大小之和` 必须 `< DB 的 max_connections`。
> 这也是「为什么不能每个实例都开 50 个连接」的原因。

### 2.3 事务与连接的关系

**事务持有连接的时间 = 事务方法耗时**。因此：

| 规则 | 原因 |
|---|---|
| `@Transactional` 方法内**禁止**远程调用 | 远程耗时 3s → 连接被占 3s → 池被耗尽 |
| `@Transactional` 方法内**禁止**做 IO 密集操作（文件、大 JSON）| 同上 |
| 只读查询**不加** `@Transactional` | 加了徒增连接占用，无收益 |
| 事务方法要**短** | 越短，池的吞吐量越高 |

> 📌 典型反例：在一个 `@Transactional` 方法里循环调 100 次外部 API，
> 连接会被占住整个循环时长。正确做法是「事务内只做数据库写，远程调用放事务外」。

### 2.4 连接泄漏的排查

`leak-detection-threshold` 触发时，日志会打印持有连接的栈。常见原因：

| 症状 | 原因 |
|---|---|
| 栈里是 `Mapper` 方法 | 事务未提交 / 未回滚，连接还在等 |
| 栈里是 `Stream` / `ResultSet` | 手写 JDBC 忘了 close（**本项目禁止手写 JDBC**）|
| 栈里是业务方法 | 事务方法里做了耗时操作 |

## 3. Redis 规范

### 3.1 核心原则

| 原则 | 说明 |
|---|---|
| **Redis 是辅助存储，不是权威数据源** | Redis 挂了不应导致核心链路不可用 |
| **key 必须有命名空间** | 裸 key（如 `abc123`）会让多业务共用 Redis 时无法治理 |
| **写操作必须带 TTL** | 无 TTL 的 key 会永久占用内存 |
| **不得用 `KEYS` 扫全库** | `KEYS` 是 O(N) 且阻塞 Redis，生产必用 `SCAN` |
| **缓存不可用时要有降级路径** | 见 §3.4 |

### 3.2 key 命名空间

统一格式：`<业务域>:<子域>:<标识>`，各段用 `:` 分隔。

| 段 | 取值 | 约束 |
|---|---|---|
| 业务域 | 如 `captcha` / `refresh` / `email_code` / `rl` | 小写下划线 |
| 子域 | 可选，如 `email_code:register` | 小写下划线 |
| 标识 | 业务主键（用户 ID / 邮箱 / 时间戳 / UUID）| **禁止包含 `:` 以外的分隔符歧义**；邮箱等含特殊字符的**必须做编码** |

**举例：**

| 用途 | key 形态 |
|---|---|
| 图形验证码 | `captcha:<uuid>` |
| 刷新令牌 | `refresh:<userId>:<token>` |
| 邮箱验证码（按用途分）| `email_code:<purpose>:<email>` |
| 发送频率限制 | `rl:<purpose>:<window>:<email>` |

> 📌 **编码要求**：邮箱含 `@`、`.`，作为 key 段虽然技术上可行，
> 但**必须做 URL 编码或 Base64**，否则与分隔符混淆，且可能超出 key 长度限制。

### 3.3 TTL 约定

| 数据类型 | TTL 原则 |
|---|---|
| 验证码 / 一次性令牌 | 短 TTL（分钟级），**用完立即删除** |
| 刷新令牌 | TTL = 令牌有效期；删除用户令牌时**批量清理** |
| 频率限制 | TTL = 限流窗口长度，窗口结束自动失效 |
| 缓存类数据 | TTL 明确设定；**禁止 `set` 不带 TTL** |

**一次性令牌必须「用后即删」**：

```java
// ✅ 正确：校验后立刻删除，防止重放
String stored = redis.opsForValue().get(key);
if (stored == null) throw new BusinessException(400, "验证码已过期");
redis.delete(key);
if (!stored.equalsIgnoreCase(code)) throw new BusinessException(400, "验证码错误");
```

> ⚠️ **「先查后删」之间存在竞态**：两个并发请求可能同时通过校验。
> 高要求场景应改用 `GETDEL`（Redis 6.2+）或 Lua 脚本实现原子取出。

### 3.4 降级要求

**Redis 不可用时的行为必须显式决定**，不能靠默认异常传播：

| Redis 用途 | 降级策略 |
|---|---|
| 缓存 | **放行**——回源查库（可能变慢，但功能正常）|
| 频率限制 | **放行**——宁可少限流，不要全站不可用 |
| 验证码 / 一次性令牌 | **拒绝**——安全相关，宁可不可用 |

> 📌 判断标准：**Redis 挂了，哪个更糟？**
> 少了一次限流（可接受）vs 全站登录不了（不可接受）→ 选前者。

### 3.5 不得使用 `KEYS`

```java
// ❌ 错误：O(N) 且阻塞 Redis，生产环境会拖垮整个实例
Set<String> keys = redis.keys("refresh:" + userId + ":*");

// ✅ 正确：用 SCAN 游标迭代
var cursor = redis.scan(ScanOptions.scanOptions().match("refresh:" + userId + ":*").count(100).build());
```

> 📌 更好的做法：用 **Set** 维护「某用户的令牌集合」，
> 撤销时 `redis.delete(set)` 一次到位——既避免 `KEYS`，也避免逐个删 key。

### 3.6 连接池

Redis 客户端（Lettuce）的连接池**需要 `commons-pool2` 依赖才生效**——
未引入该依赖时，`spring.data.redis.lettuce.pool.*` 会被**静默忽略**。

| 规则 | 说明 |
|---|---|
| 不引入 `commons-pool2` 就**不要**写 `lettuce.pool.*` | 写了也不生效，属于「配置看起来生效实际没生效」的假配置 |
| 引入依赖后必须**同步** `application.yml` 与本节参数表 | 否则规范与实现脱节 |
| Redis 命令本身是单线程的，**连接数不需要很大** | 通常 8~16 足够；连接太多反而增加 Redis 的连接管理开销 |

> 📌 **这是规范里最容易踩的坑**：配置文件里写了一堆池参数，
> 但因为缺依赖全部没生效，排查时却以为「池太小是瓶颈」。
> **配置项的生效前提必须写进文档，且改配置时同步核对。**

## 4. 线程池规范

### 4.1 核心原则

| 原则 | 说明 |
|---|---|
| **禁止 `Executors.new*`** | `newCachedThreadPool()` / `newFixedThreadPool()` 创建的线程**不随 Spring 生命周期关闭**，也不允许配置核心/最大/队列/拒绝策略 |
| **必须由 Spring 创建** | 用 `@Bean` + `ThreadPoolTaskExecutor`，随容器启动 / 关闭 |
| **必须显式命名线程** | `setThreadNamePrefix(...)`，线上排查靠它 |
| **必须显式设置拒绝策略** | 不设就用默认 `AbortPolicy`，任务会静默丢失 |
| **必须优雅关闭** | `waitForTasksToCompleteOnShutdown` + `awaitTerminationSeconds` |

### 4.2 参数说明

| 参数 | 含义 | 设定依据 |
|---|---|---|
| `corePoolSize` | 核心线程数 | 常驻线程数，按 CPU 密集 / IO 密集区分 |
| `maxPoolSize` | 最大线程数 | IO 密集型可大于核心数 |
| `queueCapacity` | 队列容量 | **必须显式设置**（默认 `Integer.MAX_VALUE`，等于无上限）|
| `threadNamePrefix` | 线程名前缀 | 按业务命名，便于 jstack / 日志定位 |
| `rejectedExecutionHandler` | 拒绝策略 | 见 §4.3 |
| `waitForTasksToCompleteOnShutdown` | 关闭时等任务跑完 | `true` |
| `awaitTerminationSeconds` | 最多等多久 | 与停机窗口匹配 |

### 4.3 拒绝策略选择

| 策略 | 行为 | 适用 |
|---|---|---|
| `CallerRunsPolicy` | **由提交线程自己执行** | ✅ **推荐**：任务不丢，且天然限流（提交方变慢）|
| `AbortPolicy`（默认）| 抛 `RejectedExecutionException` | 任务可丢，且调用方需要处理异常时 |
| `DiscardPolicy` | 静默丢弃 | ❌ 危险：任务无声消失 |
| `DiscardOldestPolicy` | 丢最老的 | ⚠️ 队列堆积时才用 |

> ⚠️ **为什么推荐 `CallerRunsPolicy`**：队列满时，提交线程被执行任务，
> 它就**不会继续提交更多任务**——这形成天然的背压。
> 而 `AbortPolicy` 若调用方不处理异常，异常会向上冒泡导致整个请求失败。

### 4.4 异步任务的事务边界

**`@Async` / 线程池执行的任务没有事务上下文**（也不该有）。

| 规则 | 说明 |
|---|---|
| 事务方法只负责「派发」，不负责「执行」 | 把远程调用 / 耗时逻辑挪到独立方法 |
| 异步方法内需要事务时**自己加** `@Transactional` | 线程池任务不在调用方事务里 |
| 异步方法**自己捕获异常** | 异常不会传播回调用方，抛了就等于静默丢失 |
| 异步任务的失败要有兜底（回写状态 / 记日志） | 见 `../纵向分层规范/Service层规范.md` §2.6 |

> 📌 **典型正确结构**：
> ```java
> // 事务方法：只落库 + 派发
> @Transactional(rollbackFor = Exception.class)
> public PoolOperationCreateVO createOp(...) {
>     operationMapper.insert(op);
>     executor.execute(() -> runCollectOperation(op.getId(), ...));  // 事务外执行
>     return result;
> }
>
> // 独立方法：真正干活，自己处理异常
> private void runCollectOperation(...) {
>     try { ... } catch (Exception e) { 回写失败状态 }
> }
> ```

## 5. 外部调用规范

### 5.1 核心原则

| 原则 | 说明 |
|---|---|
| **必须显式设超时** | 不设超时 = 线程被无限期挂住，最终拖垮整个服务 |
| **connect 与 read 超时分开设** | 建连超时短（网络不通立刻失败），读超时按业务耗时 |
| **必须有 fallback** | 外部服务挂掉不能导致本服务 500 |
| **fallback 必须返回合法结构** | 不能返回 `null` 让调用方 NPE |
| **远程调用不在事务内** | 见 §2.3 |

### 5.2 超时设定

| 超时 | 含义 | 设定依据 |
|---|---|---|
| `connect-timeout` | 建立 TCP 连接的最长等待 | 固定较短值（秒级），网络不通时快速失败 |
| `read-timeout` | 等待响应的最长等待 | 按**该接口的正常耗时 P99** 的 2~3 倍设定 |

> ⚠️ **read 超时不宜过长**：一个接口超时 60s，若有 20 个并发线程卡住，
> 整个服务的可用线程就被占光了——**一个慢的依赖会拖垮整个应用**。

### 5.3 fallback 语义

fallback 的返回值必须让调用方能**区分「失败」和「真的没数据」**：

```java
// ✅ 正确：结构合法 + 明确标记不可用
@Override
public Map<String, Object> createTask(...) {
    Map<String, Object> fallback = new LinkedHashMap<>();
    fallback.put("code", 503);
    fallback.put("message", "collector unavailable");
    fallback.put("data", null);
    return fallback;
}
```

| 规则 | 说明 |
|---|---|
| fallback 返回**与正常路径同构**的结构 | 调用方不需要写两套解析逻辑 |
| fallback 必须**明确标记失败** | 用 `code` / `message` 表达「不可用」，而不是伪装成空数据 |
| fallback **不得抛异常** | fallback 里再抛异常等于没 fallback |
| fallback 里**不得做重试** | 重试会放大故障；重试应在调用方显式发起 |

### 5.4 熔断与限流

| 能力 | 作用 | 缺失后果 |
|---|---|---|
| **熔断**（circuit breaker）| 依赖持续失败时快速失败，不再打穿 | 依赖挂掉 → 本服务线程被拖死 |
| **限流**（rate limiter）| 限制对下游的调用速率 | 本服务把下游打挂 |

> 📌 本项目的 `CollectorFallback` 已提供 fallback，但**尚未接入熔断器**——
> 这意味着 collector 慢的时候，本服务仍会等待到 read-timeout。
> 接入熔断前，read-timeout 必须设得足够短（见 §5.2）。

### 5.5 跨语言契约的调用

调用 Python collector 这类**外部系统定义结构**的接口时：

| 规则 | 说明 |
|---|---|
| **不定义 Java DTO** | 跨语言强耦合：Python 改字段 → Java 编译失败 |
| 用 `Map<String, Object>` 透传 | 见 `../纵向分层规范/POJO规范.md` §2.4 |
| 序列化用**注入的 ObjectMapper** | 复用全局 Jackson 配置，**禁止** `new ObjectMapper()`（裸实例不带全局配置，结果与全局约定不一致）|

> 📌 **静态 Converter 需要 ObjectMapper 时怎么办？**
> 本项目的 Converter 统一是「无状态纯函数 + 静态工厂」（见 `../纵向分层规范/POJO规范.md` §4.2），
> 所以 **ObjectMapper 作为方法参数传入**，由 Service 注入后透传：
>
> ```java
> // Service 层：注入 Spring 管理的 ObjectMapper
> private final ObjectMapper objectMapper;   // ← Spring 注入
>
> // Converter 层：作为参数接收（不 new）
> public static PoolOperationVO toVO(PoolOperationPO po, ObjectMapper mapper) { ... }
>
> // 调用
> return PoolConverter.toVO(operation, objectMapper);
> ```
>
> ⚠️ **不要**为了拿 ObjectMapper 就把 Converter 改成 Spring Bean——
> 那会破坏「Converter 是无状态静态工具类」这条全局约定（4 个 Converter 都遵循）。
> **要 ObjectMapper 就传参，不要 new，也不要改 Bean 化。**

## 6. CORS 与安全

### 6.1 CORS 原则

| 原则 | 说明 |
|---|---|
| **允许的源必须显式配置** | 禁止生产环境写死 `*` |
| **`allowCredentials` 与 `allowedOrigins("*")` 不能同时开** | 二者同开 = 任意站点可带着用户凭证调用接口（CSRF 攻击面）|
| **本项目鉴权走 `Authorization` 头，不用 Cookie** | 所以 `allowCredentials` 应为 `false` |
| 只放开 `/api/**` | 非 API 路径不需要跨域 |

> 📌 **为什么「任意源 + 允许凭证」危险？**
> 浏览器会带上目标站点的 Cookie 发出请求，响应也会被恶意站点读走。
> 攻击者只需让受害者打开一个页面，就能以受害者身份调用你的接口。
>
> **本项目规避方式**：token 存在 `localStorage`，通过 `Authorization` 头手动携带，
> 不依赖 Cookie，因此**不需要** `allowCredentials`，直接关掉即可。

### 6.2 前端代理优先

本项目前端与后端的部署形态：

| 环境 | 形态 | 是否触发 CORS |
|---|---|---|
| 本地开发 | Vite dev server 代理 `/api` → `localhost:8080` | ❌ 浏览器看到的是同源 |
| 生产 | nginx 反代 `/api` → 后端容器 | ❌ 同源 |

> 📌 **所以 CORS 只是兜底配置**，正常路径根本不会触发预检。
> 因此**完全没有必要放开全部来源**——把实际的开发端口列出来即可。

## 7. 配置管理原则

### 7.1 配置分层

| 层 | 位置 | 用途 |
|---|---|---|
| **默认值** | `application.yml` 的 `${VAR:default}` | 开发环境开箱即用 |
| **环境变量 / `.env`** | 部署环境注入 | 覆盖默认值，**不提交仓库** |
| **`application.yml`** | 仓库内 | 只放**非敏感**的结构性配置 |

| 规则 | 说明 |
|---|---|
| 敏感值（密码 / secret）**必须**走环境变量 | 仓库里的明文密码等于泄漏 |
| 配置项**必须有默认值** | 缺失时报清晰的启动错误，而不是运行期 NPE |
| 生产环境用**独立 profile** | `application-prod.yml` 覆盖生产差异 |
| **不要**在 `application.yml` 里写死环境相关值 | 换环境要改代码 = 迟早出事 |

### 7.2 配置项命名

| 规则 | 说明 |
|---|---|
| 用 `SPRING_` / 业务前缀 + 大写下划线 | 如 `DB_POOL_MAX_SIZE`、`APP_CORS_ALLOWED_ORIGINS` |
| **同一语义只在一处配置** | 避免「三处不一致」的历史问题 |
| 改配置**必须同步文档** | 本文 §2.2 / §3.6 的参数表就是配置项的索引 |

## 8. Code Review 清单

| # | 检查项 | 违规信号 |
|---|---|---|
| 1 | Service 里 new 线程池？ | `Executors.new*` |
| 2 | 线程池由 Spring 创建？ | 有 `@Bean` + `ThreadPoolTaskExecutor` |
| 3 | 拒绝策略显式设置？ | 没调 `setRejectedExecutionHandler` |
| 4 | 队列容量显式设置？ | 没调 `setQueueCapacity`（默认无上限）|
| 5 | 线程有名字？ | 没调 `setThreadNamePrefix` |
| 6 | 优雅关闭？ | 没调 `waitForTasksToCompleteOnShutdown` |
| 7 | 事务方法内有远程调用？ | `@Transactional` 方法里调 Feign / HTTP |
| 8 | 连接池显式配置？ | `application.yml` 无 `hikari` 段 |
| 9 | 连接超时设了？ | 无 `connection-timeout` |
| 10 | 池大小 ≥ 并发线程数？ | `maximum-pool-size` 明显小于业务线程池并发 |
| 11 | Redis key 有命名空间？ | 裸 key 如 `abc123` |
| 12 | Redis 写有 TTL？ | `set(key, value)` 不带 Duration |
| 13 | 用了 `KEYS`？ | `redis.keys(...)` |
| 14 | 一次性令牌用后即删？ | 校验后没 `delete` |
| 15 | Redis 降级路径明确？ | Redis 异常直接冒泡导致核心链路 500 |
| 16 | HTTP 超时显式设置？ | Feign 无 `connect-timeout` / `read-timeout` |
| 17 | fallback 返回合法结构？ | fallback 返回 `null` |
| 18 | `new ObjectMapper()`？ | 应注入 Spring 管理的 Bean；静态 Converter 则**作为参数传入** |
| 19 | CORS 放开全部来源 + 允许凭证？ | `allowedOriginPatterns("*")` + `allowCredentials(true)` |
| 20 | 敏感值硬编码？ | `application.yml` 里有明文密码 |
