## 2. `.last()` 原生 SQL 片段 —— 已全部清除

**整改前**：34 处，分布如下

| Service 实现 | `.last()` 数量 | 主要问题 |
|---|---|---|
| `DataBoardServiceImpl` | 23 | 15 个数据面各写一次 `LIMIT`；`LIMIT ... OFFSET ...` 手写分页 |
| `KlineServiceImpl` | 5 | `LIMIT` + warmup 查询 |
| `StockInfoServiceImpl` | 3 | `LIMIT 10000` 全量、`LIMIT 1` 取最新 |
| `ConceptServiceImpl` | 2 | `LIMIT` |
| `PoolServiceImpl` | 1 | `LIMIT 5` 取最近操作 |

**整改方案**：引入 MyBatis-Plus 分页插件 + 统一的「取前 N 行」辅助类，Service 层不再出现任何 SQL 字符串。

1. **注册分页插件**（`attribution-app/config/MybatisPlusConfig.java`）

   ```java
   PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.POSTGRE_SQL);
   pagination.setMaxLimit(10000L);
   interceptor.addInnerInterceptor(pagination);
   interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());
   ```

   > ⚠️ `maxLimit` 必须 ≥ 业务允许的最大单次取数（K 线 3650 根 / 股票全量 10000 条），否则会**静默丢数据**。

2. **统一取前 N 行**（`attribution-common/mybatis/TopN.java`）

   ```java
   // ✅ 新写法：Service 层无 SQL 片段
   List<TechKlinePO> rows = TopN.query(techKlineMapper, wrapper, limit);
   List<TechKlinePO> latest = TopN.latest(mapper, wrapper);   // 等价 LIMIT 1
   ```

3. **分页查询改用 `Page<T>`**（`DataBoardServiceImpl.stockList`）

   ```java
   // ❌ 旧写法：手写 OFFSET，绕过插件，页码越深越慢
   wrapper.last("LIMIT " + size + " OFFSET " + offset);

   // ✅ 新写法：走插件，自动优化
   var pageParam = new Page<StockInfoPO>(query.getPage(), query.getPageSize());
   List<StockInfoPO> records = stockInfoMapper.selectPage(pageParam, wrapper).getRecords();
   ```

## 3. 字符串列名 —— 已全部改为 Lambda 引用

**整改前**：`QueryWrapper` 7 处 + 字符串列名引用 21 处，分布：

| Service 实现 | `QueryWrapper` 实例 | 字符串列名引用 |
|---|---|---|
| `DataBoardServiceImpl` | 4 | 12 |
| `ConceptServiceImpl` | 2 | 8 |
| `StockInfoServiceImpl` | 1 | 1 |
| `KlineServiceImpl` / `AuthServiceImpl` / `PoolServiceImpl` / `ScheduleServiceImpl` | 0 | 0 ✅ |

**整改后**：全部改为 `LambdaQueryWrapper` + `PO::getXxx`。

```java
// ❌ 旧写法：列名写死为字符串，编译期无法检查，拼错不报错
new QueryWrapper<ConceptIndexPO>().eq("concept_name", conceptName).ge("trade_date", startDate);

// ✅ 新写法：Lambda 引用，编译期校验，重构安全
new LambdaQueryWrapper<ConceptIndexPO>()
        .eq(ConceptIndexPO::getConceptName, conceptName)
        .ge(ConceptIndexPO::getTradeDate, LocalDate.parse(startDate));
```

> 📌 注意：`trade_date` 等字段在 PO 中是 `LocalDate` 类型，改造时需同步做**类型转换**（`LocalDate.parse(...)`），
> 否则字符串比较在数据库中的行为与预期不符。

## 6. 事务边界 —— 已补齐 `@Transactional`

**整改前**：全项目零 `@Transactional`，多表写操作无原子性。

**整改后**：`PoolServiceImpl` 中 4 个多表写方法加 `@Transactional(rollbackFor = Exception.class)`：

| 方法 | 涉及表 |
|---|---|
| `delete` | `stock_pool_members` + `stock_pools` |
| `addMembers` | `stock_pool_members` |
| `removeMembers` | `stock_pool_members` |
| `memo` | `stock_pool_members`（delete + insert）|

其余模块（auth / market / concept）经核查均为**单表写**，无需事务。

> ✅ **2026-10-29 已完成**：`scheduler` 模块（`attribution-scheduler`）因 `collect_schedule` / `collect_run_log` 两表删除而整体下线，
> 其 Mapper / Service 随之移除。详见 `../../规范文档/拆分方案.md` §3.5。

## 7. 线程池 —— 已交给 Spring 管理

**整改前**：`PoolServiceImpl` 持有 `Executors.newCachedThreadPool()`，不随 Spring 生命周期关闭。

**整改后**：新增 `attribution-user/config/PoolTaskExecutorConfig.java`，通过 `@Bean("poolTaskExecutor")` 提供线程池，
`PoolServiceImpl` 改为构造器注入（显式 `@Qualifier`）。

同时，采集任务的远程调用已移出事务边界 —— `createOp` 只负责派发，实际采集在独立方法 `runCollectOperation` 中执行，
避免远程调用长时间占用数据库连接（见 Service 层规范 §4.2）。
