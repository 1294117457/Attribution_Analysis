## 0. 一句话结论

> **把现在混在一起的 `kind`（"能不能读" + "怎么采"）拆成两个正交字段：**
> **`strategy`（采集方式：增量 / 全量覆盖 / 实时查询）决定前端表单 + 写入语义，`queryable`（能否实时直查）决定 `/query` 端点是否可用。**
> **前端按 `strategy` 渲染三种完全不同的表单；Collector 按 `strategy` 决定走「区间展开」还是「覆盖采集」；`collect_logs.kind` 列直接承载 `strategy`，零 DDL 迁移。**

## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 增量采集：**前端只暴露时间范围**（起止日期） | 选一个 `strategy=incremental` 的 service，右侧面板只有日期选择器 + 一个按钮，无其它参数输入 |
| G2 | 全量覆盖：**前端只有一个按钮**，点击即采集覆盖 | 选一个 `strategy=full` 的 service，右侧面板只有一个「全量覆盖采集」按钮 + 二次确认 |
| G3 | 实时查询：占位实现，后续给业务侧调用 | `strategy=realtime` 的 service 前端显示「建设中」占位，不提供采集入口 |
| G4 | 增量 / 全量**都要写 `collect_logs`** | 历史页能查到两类记录，且能区分采集类型、区间、结果 |
| G5 | 三端链路统一：前端 → Java → Collector | 建任务请求体一致、错误码一致、日志字段一致 |
| G6 | 「全量覆盖」有**真实的覆盖语义** | 全量采集后，库中不存在覆盖域之外的残留行 |

## 2. 现状问题清单（改造的根因）

### 2.1 采集类型维度缺失 / 语义错位

| 项 | 现状 | 问题 |
|---|---|---|
| `kind` 字段 | `collect` / `incremental` / `full` / `realtime` / `both` | `both` 表达的是「既能写库也能 `get()` 实时查」，**与「怎么采」无关**；`collect` 是「没声明」的兜底 |
| `daily_kline.kind` | `"both"` | 前端无法判断它是**增量**采集，因为 `both` 里没这个信息 |
| `stock_basic.kind` | `"both"` | 同上，无法判断是增量还是全量覆盖 |
| `mode` 参数 | `full` / `condition` | 与 `kind` **语义重复**，且 `mode` 实际**没有任何 service 读它** |

### 2.2 `mode` 是死参数 —— "全量采集"目前和"条件采集"行为完全一样

`manager._run` 把 mode 塞进 collect 参数：

```270:275:D:\codes\version2\Attribution_Analysis\collector-python\src\tasks\manager.py
                res = await cls().collect({**p, "mode": mode})
```

但在 `collector-python/src/collectors/**` 全量 grep `params.get("mode")` **零命中** —— 没有任何 service 消费它。

**结论**：前端切「全量采集 / 条件采集」单选框，**只是决定了前端发不发 `default_params`**，服务端行为一模一样。「全量覆盖」这个语义**目前根本不存在**。

### 2.3 落库层没有覆盖语义

| service | 落库方式 | 是否真覆盖 |
|---|---|---|
| `daily_basic` / `moneyflow` / `top_list` / `top_inst` / `block_trade` / `margin` / `limit_list` / `moneyflow_hsgt` / `hsgt_top10` | `DELETE WHERE trade_date = ?` + `INSERT` | ✅ 当日覆盖（区间内逐日即全覆盖） |
| `daily_kline` | `upsert(symbol, date)` | ❌ 区间外旧行残留 |
| `stock_basic` | `upsert(symbol)` | ❌ **退市股 / 已消失的标的永久残留** |
| `concept_list` | `upsert(index_code)` | ❌ 废弃概念永久残留 |
| `name_change` | **完全没有 `_save`** | ❌ 拉到的数据**直接丢弃**（既有 bug） |
| `adj_factor` / `dividend` / `holder_number` / `top10_holders` / `top10_floatholders` / `fin_income` / `stock_concepts` | 多数**根本没落库**（只 `return len(bos)`） | ❌ 空操作 |
| `concept_members` / `concept_index_daily` | **没落库** | ❌ 空操作 |

### 2.4 `mode` 取值三处不一致

| 位置 | 允许值 |
|---|---|
| Java `CollectProxyController.TaskValidator` | `full` / `condition` |
| Python `manager._VALID_MODES` | `condition` / `full` / `schedule` / `manual` |
| DDL `ck_collect_logs_mode` | `condition` / `full` / `schedule` / `manual` |

→ 若把 `mode` 改成 `incremental` 来表达采集类型，`insert_queued` 会撞 CHECK 违例 → **任务被拒绝受理**（`insert_queued` 失败即抛异常）。

## 3. 目标模型

### 3.1 字段拆分

```
facet     = 数据分类（tech/capital/fundamental/news/sentiment）→ 目录一级、决定表前缀
strategy  = 采集方式（incremental/full/realtime）             → 决定前端表单 + 写入语义 + 任务参数
queryable = 是否支持实时直查（bool）                          → 决定 /query 端点可用性
RANGE     = 增量维度描述（仅 incremental 有）                  → 决定前端日期控件形态
```

> **为什么必须拆**：`kind=both` 把「读」和「写」两个正交概念塞进一个字段，导致 `daily_kline` / `stock_basic` 这类既有写又有读的 service **无法表达自己是增量还是全量**。拆开后 `queryable=true` 与 `strategy=incremental` 可以自由组合。

### 3.2 `strategy` 三态定义

| strategy | 语义 | 前端形态 | 参数 | 落库语义 | 是否建任务 | 是否写 `collect_logs` |
|---|---|---|---|---|---|---|
| `incremental` | 按时间范围增量采集 | **只给时间范围** | `start_date` / `end_date` | 区间内 upsert / 追加，区间外不动 | ✅ | ✅ |
| `full` | 一次性覆盖采集 | **只给一个按钮** | 无（或 service 默认值） | 覆盖域内 upsert；覆盖域外残留按 service 规则清理 | ✅ | ✅ |
| `realtime` | 实时直查，不入库 | 占位（建设中） | — | 不入库 | ❌ 拒绝 | ❌ |

### 3.3 `RANGE`（增量维度）

```python
RANGE: ClassVar[Optional[dict]] = None
# 增量 + 区间自理（service 内部处理起止，单次调用）
{"start_key": "start_date", "end_key": "end_date", "granularity": "day"}
# 增量 + 按交易日展开（manager 拆成 N 个交易日，逐日调用）
{"start_key": "start_date", "end_key": "end_date", "granularity": "trade_day"}
```

| granularity | 含义 | manager 行为 | 典型 |
|---|---|---|---|
| `trade_day` | 按**交易日**展开 | 查 `tech_calendar` 取交易日 → N 步，每步一个 `trade_date` | 每日估值、资金流、龙虎榜、停复牌 |
| `day` | 按**自然日区间** | 单次调用，service 内部处理区间 | 日 K 线 |

> 前端**统一提交 `start_date` / `end_date`**，由 `granularity` 决定 collector 侧怎么处理 —— 前端不需要知道交易日历的存在。

### 3.4 全量覆盖的两种模式

| 模式 | 声明 | 行为 | 适用 |
|---|---|---|---|
| `CLEAR_MODE = "none"`（默认） | 不声明 | 只做自然键 upsert 覆盖，**不删残留** | 按标的维度的 service（adj_factor 等）：删残留会毁历史 |
| `CLEAR_MODE = "domain"` | 显式声明 | 先删「覆盖域外残留」，再写 | `stock_basic`（按 `list_status` 域）、`concept_list`（按 index_code 集合） |

**安全红线**：
- `clear()` **必须窄化**：按 `trade_date` / `list_status` / 主键集合，**严禁无条件 `TRUNCATE`**
- `clear()` 与 `collect()` **必须是两次独立事务**，中间不共享 session
- `clear()` 失败 → **任务直接失败**（不继续写，避免半清半写）

### 4.1 `GET /api/collect/services` 目录项

#### 新增字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `strategy` | `'incremental' \| 'full' \| 'realtime'` | 采集方式（**替代 `kind` 的语义**） |
| `queryable` | `boolean` | 是否有 `get()` 入口（**替代 `kind='both'` 的读语义**） |

### 4.3 `collect_logs` 字段口径

|---|---|---|---|
| `kind` | service 声明的 `kind`（`both`/`collect`，无区分度） | **本次执行的 `strategy`**：`incremental` / `full` | ✅ DDL `ck_collect_logs_kind` 已允许这两个值 |
| `mode` | `condition` / `full`（与 kind 重复） | `manual`（人工触发）/ `schedule`（未来调度） | 语义收敛为「编排来源」，**不再表达采集类型** |

| `trigger_user` | 恒 NULL | 本期仍 NULL（Java 取不到登录用户） | 后续补鉴权链路 |
| `total` / `done` / `success` / `fail` | 步数口径 | 不变 | 增量 = N 个交易日步数；全量 = 1 步 |
| `saved_total` | 行数口径 | 不变 | 不变 |

```python
    # ── 采集方式（必须显式声明）──────────────────────
    strategy: ClassVar[str] = "incremental"
    #   incremental : 增量，按 RANGE 描述的时间范围采
    #   full        : 全量覆盖，一次性采集并覆盖
    #   realtime    : 实时直查，不入库（拒绝建任务）
    # ❌ 废弃 kind 的 'both' / 'collect' —— 读能力用 QUERYABLE 表达

    # ── 增量维度（仅 incremental 需要）──────────────
    RANGE: ClassVar[Optional[dict]] = None
    # {"start_key": "start_date", "end_key": "end_date", "granularity": "day"|"trade_day"}

    # ── 是否有实时直查入口 ─────────────────────────
    QUERYABLE: ClassVar[bool] = False

    # ── 全量覆盖的清理模式 ─────────────────────────
    CLEAR_MODE: ClassVar[str] = "none"   # none | domain

    DEFAULT_PARAMS: ClassVar[dict] = {}
    RATE_LIMIT: ClassVar[Optional[tuple[str, int, int]]] = None
    CONCURRENCY: ClassVar[int] = 1

    async def collect(self, params: dict) -> CollectResult:
        ...

    async def clear(self, params: dict) -> int:
        """全量覆盖前的清理钩子；默认 no-op。

        返回清理行数（计入任务 message）。
        ❌ 严禁无条件 TRUNCATE；必须按覆盖域窄化。
        """
        return 0
```

| 规则 | 说明 |
|---|---|
| `strategy` **必须显式声明** | 沿用旧 `kind` 的教训：靠 `getattr` 猜会让 `collect_logs.kind` 一直是空串 |
| `QUERYABLE` 替代 `kind='both'` | 有 `get()` 就设 `True`，与 `strategy` 正交 |
| `RANGE` 只对 `incremental` 有意义 | `full` / `realtime` 必须是 `None` |
| `clear()` 默认 no-op | 老 service 不改也能跑；只有需要真覆盖的才实现 |

#### 改动 1：`mode` → `strategy`（含兼容分支）

|---|---|

#### 改动 3：full 分支走 `clear()` → `collect()`

```python
# full：不走 _expand 的日期展开，直接 1 步

    calls = [dict(params or {})]
else:
    calls = await _expand(cls, dict(params or {}))
```

`_run` 内每个 service 调用前：

```python
if strategy == "full" and getattr(cls, "CLEAR_MODE", "none") == "domain":
    cleared = await cls().clear(p)     # 先清覆盖域外残留；失败 → 该步记 fail 并终止

```

> ⚠️ `clear()` 抛异常 → **该步失败并中断整体**（不继续写），避免「清了一半」的数据状态。已在文档《Python端规范》§6.3 幂等性原则内：`clear` 幂等，重跑安全。

### 5.6 日志状态机（**不变**，直接复用）

```
create_task() → INSERT queued
              → _run() 开始 → UPDATE running
              → 每步 → 只写 Redis（HSET collect:task:{id}）
              → 结束 → UPDATE done | failed | cancelled
```

- 增量任务：`total` = 展开后的**交易日步数**，`done/success/fail` 为步数，`saved_total` 为行数
- 全量任务：`total` = 1（覆盖是 1 步），`saved_total` = 写入行数，`message` 里附加「清理 N 行」

#### 兼容回退函数（灰度期）

```ts
export function resolveStrategy(item: ServiceItem): CollectStrategy {
  if (item.strategy) return item.strategy
  // 旧 collector 只给 kind：both/collect → incremental
  const legacy = (item.kind || 'collect') as string
  if (legacy === 'full') return 'full'
  if (legacy === 'realtime') return 'realtime'
  return 'incremental'
}
```

## 10. 风险与待决策项

| # | 项 | 说明 | 建议 |
