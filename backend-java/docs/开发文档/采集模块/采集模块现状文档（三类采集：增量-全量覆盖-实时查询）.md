##### ★ §4.6 `daily_kline` 的「按交易日整批」采集路径（重要性能约定）

**问题**：原实现是**按 symbol 逐只采集**（`_collect_batch` → 每只股票 1 次 `pro.daily(ts_code=...)`）。
全 A 股 5576 只 → **5576 次接口调用**；在 Tushare 200 次/分钟的限流下，
即使不停也需 ~28 分钟，且一旦命中限流就**长时间无响应**（前端看起来就是「点了没反应」）。

**修复**：改为**按交易日整批**——`pro.daily(trade_date=YYYYMMDD)` 不带 `ts_code` 时
返回**当日全市场**（~5500 行），因此**一个交易日只需 1 次调用**。

| 项 | 逐只路径（旧） | 整批路径（现） |
|---|---|---|
| 接口调用数（7 天区间） | 5576 × 7 ≈ 39000 次 | **7 次**（每交易日 1 次） |
| 限流压力 | 远超 200 次/分 → 必然卡住 | 7 次 → 不触发限流 |
| 实测耗时 | 数十分钟且长时间无反馈 | **~14 秒**（5 交易日 / 27852 行） |

**实现要点**：

| 位置 | 改动 |
|---|---|
| `core/tushare_utils.py` → `TushareKlineParser.parse_many()` | 新增：解析**全市场** DataFrame（symbol 取自行内 `ts_code`） |
| `collectors/tech/DailyKlineTushareFetcher.py` → `fetch_by_date()` | 新增：逐日调用 `pro.daily(trade_date=...)`，一次拿全市场 |
| `collectors/tech/daily_kline_service.py` → `_collect_by_date()` | 新增：无 `symbols` 时走整批路径 |
| `collectors/tech/daily_kline_service.py` → `_save_all()` | 批量 upsert **分块写**（`SAVE_CHUNK_SIZE=2000`），避免 PG 参数上限 |

**为什么逐日调用而不是一次拉整个区间**：
Tushare `daily` 单次最多返回 6000 行 → 一个交易日全市场约 5500 行（勉强够），
但**跨多日区间会被截断**（实测 2 天只回了 6000 行，其中一天仅 569 行）→ 必须逐日调用。

**保留逐只路径**：显式传 `symbols` 时仍走逐只（用于补采单只股票）。

##### ★ §4.7 「可见进度」的实现（`expand_calls` 展开钩子）

**问题（用户实测反馈）**：日 K 采集时前端进度条全程停在 `0/1 步`，只有结束后才有结果。

**根因**：`manager._run()` 的进度刻度是**步数**（`done` / `total`），
而 `total` = `_expand()` 拆出的调用次数。`daily_kline` 声明 `granularity='day'`
→ `_expand` 走「区间自理」分支 → **只有 1 步**；
且天循环发生在 **service 内部**（`fetch_by_date` 的 `while d <= end_date`），
manager 完全看不见 → 整个采集期间 `done` 恒为 0 → 进度条不动。

**修复**：新增 **service 级展开钩子 `expand_calls(params)`**，把天循环从 service 内部
**搬到 manager 层**，与其它 `trade_day` 类 service 口径统一。

```python
# collector-python/src/tasks/manager.py —— _expand() 的 day 分支末尾
    # ★ service 自定义展开钩子（可选）
    #   有些 service 声明 granularity='day'（区间自理），但**同时**支持按天拆分
    #   以获得可见的进度刻度（如 daily_kline：全市场按日整批采集）。
    hook = getattr(cls, "expand_calls", None)
    if callable(hook):
        try:
            calls = await hook(cls(), params)
        ...
        if calls:
            return calls
```

```python
# collector-python/src/collectors/tech/daily_kline_service.py
    async def expand_calls(self, params: dict) -> Optional[list[dict]]:
        """把「全市场 + 日期区间」展开成「每个交易日一次 collect()」。"""
        if params.get("symbols"):
            return None          # ★ 按 symbol 补采不展开（否则同一批 symbol 会被重复采 N 次）
        ...
        days = await trading_days_between(start, end)
        base = {k: v for k, v in params.items()
                if k not in ("start_date", "end_date", "trade_date")}
        return [{**base, "trade_date": d.isoformat()} for d in days]
```

**效果对比**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| `total`（进度分母） | `1` | **= 区间内交易日数**（如 5 天区间 → 5 步） |
| `done` | 全程 0 | **每完成一天 +1** |
| `progress` | 全程 0% | **20% / 40% / 60% / 80% / 100%** |
| 落库粒度 | 全部天攒完一次性 upsert | **逐日独立 upsert**（单日失败不影响其他天） |
| 单日失败影响 | **整批失败** | 只影响那一天（`fail+1`，继续跑剩余天） |
| 上游调用数 | 区间自然日数（**含周末**） | 区间**交易日数**（跳过周末与法定节假日） |

> ⚠️ **按 symbol 补采路径不变**（仍 1 步）：`symbols` 传入时 `expand_calls` 返回 `None`，
> 区间仍由 service 内部处理（`pro.daily(ts_code=..., start_date=..., end_date=...)` 一次拿全区间）。

##### ★ §4.8 交易日历的三级降级（`tech_trade_cal` 原本是空表）

**问题**：`manager._trading_days()` 原本只读本地表 `tech_trade_cal`，
而**该表没有任何 collector 往里写**（实测 0 行）→ 永远走「回退周一~周五」分支：
- 法定节假日被当成交易日 → 白跑一次上游调用（返回空）
- `progress` 的**分母虚高**（自然日 - 周末 ≠ 实际交易日数）

**修复**：改为**三级降级**，并把上游结果**回写本地表**：

| 级别 | 来源 | 说明 |
|---|---|---|
| ① | 本地表 `tech_trade_cal` | 采集过就有，最快、零上游成本 |
| ② | 上游 Tushare `trade_cal` | 本地表空 / 读失败时兜底（`exchange='SSE'`） |
| ③ | 自然日展开（周一~周五） | 上游也不可用时的最后兜底 |

**★ 覆盖度校验（防静默少算）**：本地表是**按需回写**的（只存被查过的区间），覆盖范围天然碎片化。
若只按**比例**判断（例如「覆盖 87% 就信」），区间尾部缺失的日期会被**静默丢弃**
→ 那些交易日永远不会被采集，`progress` 的分母也偏小。
⚠️ **实测踩坑**：本地表覆盖 10-24~11-05（13/15 天 = 87% > 80% 阈值），
结果 11-06、11-07 两个交易日被静默跳过 → 采了 9 步而不是 11 步。
→ **正确做法：要求区间内每一天都有日历行**（含 `is_open=False` 的休市日），
覆盖不全就改走上游补齐。

**★ 休市日也要入库**：回写本地表时把 `is_open=False` 的行一并写入 ——
否则本地表只有交易日行（≈ 自然天数的 70%），会被覆盖度校验判为「覆盖不全」→ 每次都问上游。

**★ 回写用 DO UPDATE 而非 DO NOTHING**：上游的 `is_open` 可能与旧值不同
（例如临时休市调整），`DO NOTHING` 会让旧值**永久留存** → 交易日判定错误。

##### ★ `collect_logs` 时间列的类型约定（易踩坑）

`collect_logs` 的时间列是 **`TIMESTAMPTZ`**（Step 2 DDL 刻意如此：
Python 侧写的是**带时区**的 aware datetime，asyncpg 写 aware → naive 会直接报错）。
而 `attribution` 库其余表（`sys_users` / `sys_roles` / `stock_pools` …）的时间列
仍是 **naive `timestamp`**。

| 表 | 列类型 | Java 类型 |
|---|---|---|
| `collect_logs` | `timestamptz` | ★ `OffsetDateTime` |
| `sys_users` / `sys_roles` / `stock_pools` / `pool_operations` | `timestamp`（naive） | `LocalDateTime` |

**踩坑记录**：

| 用错类型 | 报错 |
|---|---|
| `LocalDateTime` 读 `timestamptz` | `Cannot convert the column of type TIMESTAMPTZ to requested type java.time.LocalDateTime` → `/api/collect/logs` **整个 500** |
| `ZonedDateTime` 做筛选参数 | `Can't infer the SQL type to use for an instance of java.time.ZonedDateTime` → 筛选 500 |
| `LocalDateTime` 做筛选参数 | 时区丢失 → 「某一天」的边界偏 8 小时 |

→ **约定**：读/写 `collect_logs` 的时间列一律 `OffsetDateTime`；
筛选用**固定 `ZoneOffset.ofHours(8)`**（中国无夏令时）。
前端直接拿到 ISO-8601 带时区字符串（`2026-10-29T15:34:56.606077Z`），
用 `new Date(v).toLocaleString()` 转本地时间显示。

### 4.3 ★ 已修复的两个关键 Bug

#### Bug 1：collector 宕机被伪装成「查询成功但无数据」

**旧代码**：

```java
// CollectorService.queryRaw —— 拆掉了 data
Object data = collectorService.queryRaw(name, paramsJson);   // ← data 被拆出
// CollectProxyController.query —— 又包回 200
queryResult.put("code", 200);
queryResult.put("data", data);
```

**故障链**：collector 挂掉 → Feign fallback 返回 `{code:503, message:"collector unavailable", data:null}`
→ `queryRaw` 拆出 `data` = `null` → Controller 包成 `{code:200, message:"success", data:null}`
→ 前端 `unwrap()` 看到 `code=200` → **判定成功** → 页面显示「无数据」。

**结果**：collector 宕机时，用户看到的不是红色报错，而是「这个接口今天没数据」——**故障被彻底掩盖**。

**修复**：Java 侧**不拆信封**，collector 的 `{code, message, data}` 原样透出。
前端 `unwrap()` 按 `code>=400` 判错 → 收到 `code=503` → 明确报错。

#### Bug 2：facet 硬编码白名单挡住新采集源

**旧代码**：

```java
private static final Set<String> FACETS =
        Set.of("tech", "capital", "fundamental", "news", "sentiment");
if (!FACETS.contains(facet)) throw new BusinessException(400, "facet 非法: " + facet);
```

Python 端新增一个 facet 的 service → Java 直接报「facet 非法」→ **采集入口被卡死**，且错误信息完全指错方向。

**修复**：改用 `CollectorCatalogCache`（从 collector 目录动态获取）。
⚠️ **降级语义**：目录**从未成功加载**（collector 挂了）时**不校验**，让请求透传过去由 collector 给权威错误 ——
否则 collector 一挂，所有采集入口都会被 Java 层的「facet 非法」挡住。

```python
class CollectService(Protocol):
    # ── 身份 ───────────────────────────────────
    name: ClassVar[str]          # ★ 全局唯一；日志关联键（collect_logs.name）
    facet: ClassVar[str]         # ★ 五数据面（唯一分组维度）
    label: ClassVar[str] = ""    # ★ 中文显示名
    description: ClassVar[str] = ""

    # ── 采集方式（必须显式声明）──────────────────────
    strategy: ClassVar[str] = "incremental"
    #   incremental : 增量，按 RANGE 描述的时间范围采
    #   full        : 全量覆盖，一次性采集并覆盖
    #   realtime    : 实时直查，不入库（拒绝建任务）
    # ❌ 废弃 kind 的 'both' / 'collect' —— 读能力用 QUERYABLE 表达

    # ── 增量维度（仅 incremental 需要）──────────────
    RANGE: ClassVar[Optional[dict]] = None
    # {"start_key": "start_date", "end_key": "end_date", "granularity": "day"|"trade_day"}

    # ── 是否有实时直查入口 ─────────────────────────
    QUERYABLE: ClassVar[bool] = False

    # ── 全量覆盖的清理模式 ─────────────────────────
    CLEAR_MODE: ClassVar[str] = "none"   # none | domain

    # ── 目录可见性 / 限流 / 并发 ────────────────────
    hidden: ClassVar[bool] = False
    RATE_LIMIT: ClassVar[Optional[tuple[str, int, int]]] = None
    CONCURRENCY: ClassVar[int] = 1

    async def clear(self, params: dict) -> int:
        """全量覆盖前的清理钩子；默认 no-op。"""
        return 0
```

### 5.4 ★ 已修复：Redis 限流器「窗口永不重置」导致采集永久卡死

**旧代码**（`core/redis.py` → `check_rate_limit`）：

```python
async with redis.pipeline(transaction=True) as pipe:
    await pipe.incr(key)
    await pipe.expire(key, window_seconds)   # ★ 每次调用都把 TTL 重置回 60s
    count, _ = await pipe.execute()
```

**Bug**：每次 `INCR` 都跟着 `EXPIRE 60` → **TTL 永远被重置回 60s** →
键在持续请求下**永不过期** → 计数器**只增不减**。

**症状**（本次实测）：
`collect:rl:tushare` 计数卡在 **235** 不再增长（上限 200），任务永远 `running`，
前端表现就是「**点了没反应**」。

**修复**：

| 项 | 旧 | 新 |
|---|---|---|
| `EXPIRE` 时机 | **每次**调用都执行 | **只在窗口首开时**（`count == 1`）执行 → TTL 自然倒数到 0 → 窗口按预期重置 |
| 超限后的等待 | 固定 `sleep(window)`（60s） | 读 Redis 真实 **TTL**，睡到窗口**真正归零**（可能只剩 1s 就重置 → 不白等 59s） |
| 并发 worker | N 个 worker 各自 sleep 60s，醒来时又被彼此推高 → **集体卡死** | 醒来后复查计数，仍超限则再等一个窗口，保证拿到配额 |

**验证**（间隔 3s 连续调用 3 次）：

| 实现 | TTL 变化 | 结论 |
|---|---|---|
| 新（`count==1` 才 EXPIRE） | 60 → 57 → 54 | ✅ 窗口正常重置 |
| 旧（每次 EXPIRE） | 60 → 60 → 60 | ❌ 窗口永不重置（Bug 复现） |

> ⚠️ **配套教训**：`daily_kline` 原先「按 symbol 逐只采集」需要 5576 次调用，
> 在这个限流 Bug 下必然长期卡住（即使限流器正常，也要 ~28 分钟）。
> → 限流器修好后，**同时**把采集路径改成「按交易日整批」（见 §4.6），才真正可用。

### 5.6 ★ 全量覆盖的安全红线

| 红线 | 实现 |
|---|---|
| **严禁无条件 `TRUNCATE`** | `clear()` 一律窄化：`list_status` 域 / `index_code` 集合 / `(symbol, start_date)` 集合 |

### 6.2 ★ 旧前端的核心问题与修复

**旧问题**：把「全量 / 条件」做成**前端单选**，同一个 service 能在两种语义之间自由切换。
后果有三：

1. **后端无法判断写入语义** —— 同一个 `daily_kline`，前端选「全量」还是「条件」，写库行为完全不同，但请求体长得一样；
2. **审计日志记不清采集方式** —— `collect_logs.kind` 记的是 service 的固有属性，不是**本次实际执行的采集方式**；
3. **前端表单有 16 种参数控件** —— 用户可以填 `symbols` / `trade_date` / `list_status` 等，但绝大多数参数要么被 service 忽略，要么造成「参数已生效」的错觉。

**修复**：采集方式由 **collector 的 service 声明唯一决定**，前端只负责**选对形态**。
用户不能再切换语义 —— 语义是数据源的事实，不是用户的偏好。

## 10. 五条必须记住的规则

> **① 采集方式由数据源决定，不由用户决定。**
> `strategy` 由 collector 的 service 显式声明，前端只负责选对形态。用户不能在增量/全量之间切换 —— 那是数据源的事实，不是用户的偏好。

> **② 「全量覆盖」的两个前提：窄化 + 空集不删。**
> `clear()` 必须窄化到覆盖域（`list_status` 域 / `index_code` 集合 / 主键集合），**严禁无条件 `TRUNCATE`**；
> 上游返回空时**绝不清理** —— 否则一次上游抖动就能清空整表。

> **③ 审计的量纲要一致。**
> `total/done/success/fail/skip` 是**步数**（一次 `collect()` = 1 步），`saved_total` 是**行数**。
> 绝不透传 `CollectResult.total/success/fail/skip` —— 那 28 个 collector 语义各不相同，透传会让审计量纲漂移。

> **④ ★ `facet` 是唯一的分组维度，三端同名同义。**
> service 类属性、`collect_logs.facet` 列、前端目录树第一层 —— 全部叫 `facet`，
> 全部指「五数据面」（tech / capital / fundamental / news / sentiment）。
> **不要再引入 `category` / `sub_facet` 这类同义异名** —— 同义异名是三端对不齐的根源。

> **⑤ ★ 远端表的实际结构优先于本地代码的历史命名。**
> 改表名 / 改列前**先查远端**（`information_schema.columns`），
> Python `__tablename__` 与 Java `@TableName` **必须同步改**，否则两端指向不同的物理表。
> 时间列统一 `timestamptz`，naive 值按 `AT TIME ZONE 'Asia/Shanghai'` 转换（**不是 `'UTC'`**）。

> **⑥ ★ 采集表只读，变更走 Collector。**
> `raw_data` 库的 29 张表由 Collector 独占写入，Java 侧**只读**（`@DS("raw")` 路由）。
> Java 直接写采集表 = 绕过采集链路 → 数据来源不可追、口径不可控。
> 需要变更基础信息（如股票列表）→ 走 `POST /api/stocks/sync` 触发采集，**不是**直接 INSERT/UPDATE。
>

> **一条 SQL 只涉及一个库；跨库关联在 Service 层内存 join。**
