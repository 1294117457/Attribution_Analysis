## 1. 现象与结论

股票面板（`frontend/src/views/stock-info/StockInfoList.vue`「净利润率%」列）全部显示 "—"。

**结论：缺数据，不是查询写错。** 净利润率由面板查询从 `fin_reports` 实时计算，但这张表是空的（0 行），因为从来没有代码调用过 Tushare 利润表接口。

## 3. 数据源确认

使用 Tushare Pro **利润表**接口（已确认积分足够）：

| 接口 | 维度 | 积分 | 用途 |
|---|---|---|---|
| `income` | 按单只股票（`ts_code`）拉历史 | ≥ 2000 | 单股补数 / 调试 |
| `income_vip` | 按报告期（`period`）拉全市场 | ≥ 5000 | **主力：回填 + 季度增量** |

不用 `fina_indicator`：它只返回算好的比率（`netprofit_margin` 等），没有 `revenue` / `n_income` 原始字段，与现有表结构和面板公式不匹配。

### 字段映射（`income` → `fin_reports`）

| Tushare 字段 | 表字段 | 说明 |

## 4. 关键问题与处理

### 4.1 同一报告期返回重复行（必须处理）

Tushare 对同一 `(ts_code, end_date, report_type)` 可能返回多行（财报更正后新旧两版并存，`update_flag` 区分）。直接批量 upsert 会触发 PostgreSQL 错误：

```
ON CONFLICT DO UPDATE command cannot affect row a second time
```

**去重规则**（在 Fetcher 解析后、返回 BO 前完成）：按 `(symbol, end_date, report_type)` 分组，保留：

1. `update_flag == '1'` 的行优先；
2. 仍有多行时取 `f_ann_date` 最大的；
3. 再相同取 `ann_date` 最大的。

### 4.2 `income_vip` 单次返回行数上限

全市场一个报告期约 5,500 行，可能超过接口单次返回上限。实现时：

- 调用带 `report_type='1'`，减少行数；
- 用 `limit` / `offset` 分页循环，直到返回行数 < limit；
- 若分页参数不生效，退化为按 `comp_type` 或交易所拆分调用。

实现前先用一个报告期实测返回行数，确认上限。

### 4.3 字段注释错误

`models/fin_report.py` 中 `report_type` 注释写的是"1=合并报表/2=母公司报表"，与 Tushare 定义不符（2 = 单季合并，6 = 母公司报表）。改为：

```python
comment="报表类型(Tushare): 1=合并报表 2=单季合并 6=母公司报表 …，本项目只采 1"
```

`comp_type` 注释同步改为 "1=一般工商业 2=银行 3=保险 4=证券 7=多元金融"。

只改注释（`comment`），不涉及 DDL 迁移。

### 4.4 净利润率口径

| 选项 | 公式 | 含义 |
|---|---|---|
| **A（推荐，保持现状）** | `n_income / revenue × 100` | 销售净利率，与 Tushare `fina_indicator.netprofit_margin` 口径一致 |
| B | `n_income_attr_p / revenue × 100` | 归母净利率 |

推荐 A，面板查询不用改。两列都入库，将来要切换只改查询。

金融类公司（`comp_type` 2/3/4）的 `revenue` 口径与一般企业不同（利息 / 保费 / 手续费收入），净利率可比性差，但数值仍有意义，本次不特殊处理；如需区分，前端可按 `comp_type` 加提示。

### 4.5 异常不能吞掉

现有 `fetch_daily_basic` 在接口异常时 `return []`，任务会把失败记成"无数据/跳过"。`fetch_income` **应抛出异常**，由任务层记为失败单元，避免限流或权限问题被静默掩盖。

## 6. 采集任务设计

**单元维度：报告期**（一个 `period` 一个单元，调用 `income_vip`）。

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `periods` | — | 显式指定，如 `["20260630","20260331"]` |
| `years` | — | 回填最近 N 年的全部报告期（N × 4 个单元） |
| 都不传 | 最近 4 个已过去的报告期 | 日常增量 |
| `symbol` | — | 单股模式：改用 `income(ts_code=…)` 拉该股全部历史，单元数 = 1 |

报告期 = 每年 `0331 / 0630 / 0930 / 1231`，只取 `<= 今天` 的。

以 2026-09-28 为例，默认 4 期为 `20260630、20260331、20251231、20250930`。重复拉已有报告期是安全的（upsert），也能收进更正后的新数据。

### 流程

```
resolve_periods(params)
for period in periods:
    检查取消
    bos = to_thread(fetcher.fetch_income, period)   # 分页 + 去重 + 异常上抛
    空结果 → skipped（报告期还没人披露）
    否则   → FinReportRepoImpl.save_batch → on_unit_done(saved_count)
失败单元 2 秒后重试 1 次（同 concept 任务的 _run_units 做法）
TaskSummary: "完成: 报告期 X 个，写入 Y 条，失败 Z"
```

### 量级

- 回填 3 年：12 次 `income_vip` 调用（含分页可能 20~30 次），约 6 万行，分钟级完成。
- 日常增量：4 次调用。

### 调度建议（配合后续"采集配置"改造）

财报集中在 4/30（年报 + 一季报）、8/31（半年报）、10/31（三季报）前披露。建议：

- 披露季（4 月、8 月、10 月）每天盘后跑一次默认 4 期；
- 其余时间每周一次。

## 7. 测试与验收

### 单测（monkeypatch Tushare，不打外网）

1. **去重：** 同键两行（`update_flag` 0/1）只保留 `'1'`；都没有 flag 时保留 `f_ann_date` 最新的。
2. **解析：** `ts_code → symbol`，日期解析，NaN → None。
3. **分页：** 模拟第 1 页满、第 2 页不满，合并结果正确。
4. **报告期解析：** 默认 4 期、`years=3` 得 12 期、不含未来日期。
5. **任务：** 空结果记为 skipped；异常记为 fail 并重试 1 次；`saved_count` 汇总正确。
6. **仓储 upsert：** 重复执行同一批不报错、不产生重复行，且不覆盖资产负债 / 现金流列。

### 实跑验收

```powershell
python .\scripts\trigger_collect.py fin_report --param years=3
```

```sql
-- 1. 覆盖率：大部分在市股票应有最新一期
SELECT count(DISTINCT symbol) FROM fin_reports WHERE report_type = '1';

-- 2. 无重复键
SELECT symbol, end_date, report_type, count(*) FROM fin_reports
GROUP BY 1,2,3 HAVING count(*) > 1;

-- 3. 抽查：600519 最新一期净利率（贵州茅台约 50% 左右量级）
SELECT end_date, revenue, n_income, round((n_income / NULLIF(revenue,0) * 100)::numeric, 2)
FROM fin_reports WHERE symbol = '600519' AND report_type = '1'
ORDER BY end_date DESC LIMIT 4;
```

前端：刷新股票面板，「净利润率%」列有值；亏损股显示绿色负数；新股 / 无财报股仍显示 "—"。
