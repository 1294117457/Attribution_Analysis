## 四、未写入数据的项说明

### 4.1 Tushare 账号权限受限（2 项）——非代码缺陷

`limit_list_d`（涨跌停板）与 `news`（快讯）两个接口，Tushare 返回：

> 抱歉，您没有接口(`limit_list_d`)访问权限，权限的具体详情访问：https://tushare.pro/document/1?doc_id=108

**性质**：账号积分等级限制，**重试无用**，代码逻辑本身正确。

**本次改进**：新增 `SourceNotPermitted` 异常类型，把「无权限」与「临时故障」区分开：

- 旧行为：抛出 `SourceUnavailable` → 任务终态 `failed` → 前端显示「采集失败」→ **误导运维**
- 新行为：捕获后记为 **skip** → 任务终态 `done` + message 明确说明「上游接口无访问权限，已跳过」

相关代码：`core/errors.py`（`SourceNotPermitted`）、`core/tushare_client.py`（按报文特征串识别）、`collectors/base.py`（`fetch_with_retry`）。

**后续解法**：升级 Tushare 积分后即可正常采集，代码无需改动。

### 4.2 上游接口间歇性返回空（3 项，已修复）

`concept_list` / `concept_members` / `stock_concepts` 依赖同花顺（adata）接口，存在两个上游问题：

1. **问财接口 token 过期** → `all_concept_code_ths()` 的 `index_code` 整列变成 NaN
2. **页面接口按 IP 限流** → 静默返回空 DataFrame（不抛异常）

**修复措施**：

| 措施 | 位置 | 作用 |
|---|---|---|
| `concept_code` 兜底当业务键 | `ConceptListAdataFetcher` | index_code 缺失时用 308xxx 兜底，清单不再采成 0 行 |
| 重试放在 **service 层**（每轮过 Redis 限流） | `ConceptListService._fetch_with_retry` | 避免 fetcher 内重试放大请求数、触发更严的 IP 限流 |
| 残缺覆盖保护 | `ConceptListService.clear` | 覆盖集 < 50 条时跳过 `delete_outside`，防止误删全表 |
| 成员关系自愈 | `concept_members` / `stock_concepts` 的 `_save` | 匹配不到概念时自动补写主表（真实 885xxx 指数码），链路自洽 |

### 4.3 `concept_members` / `stock_concepts` 的代码写入目标

两者都写入 `fundamental_concept_member`（成员关系表），而非 `fundamental_stock_concept`：
- `concept_members`：从**概念维度**采（某概念有哪些成分股）
- `stock_concepts`：从**股票维度**采（某股票属于哪些概念）+ 入选理由 `reason`

二者互补、共用同一张表，故 `fundamental_stock_concept` 表恒为 0（该表为历史遗留，当前无 service 使用）。

## 五、本轮修复的问题清单

端到端验证首次运行仅 **4 / 27** 通过，暴露 6 类系统性缺陷，全部已修复并复验：

### 5.1 PG 参数上限溢出（8 个 service 失败）

**现象**：`PSQLException: the number of query arguments cannot exceed 32767`

**根因**：PostgreSQL 单条 prepared statement 最多 32,767 个参数。全市场单日数据行数多、列数多（如 `moneyflow` 5,576 行 × 20 列 = 111,520 参数）直接超限。

**修复**：在 `collectors/base.py` 新增两个共享 helper

- `chunk_rows_for_insert(model, rows)` —— 按「行数 × 列数 ≤ 29,490」自动分块
- `replace_rows_for_date(model, rows, date_col, date_value, conflict_cols)` —— 「先删当日、再分块写入」的标准增量落库动作

改造的 service：`moneyflow`、`margin`、`daily_basic`、`limit_list_d`、`top_list`、`top_inst`、`block_trade`、`hsgt_top10`、`moneyflow_hsgt`、`concept_list`、`news`、`daily_kline`、`adj_factor`、`stock_basic`。

### 5.2 ON CONFLICT 同批次内重复键（3 个 service 失败）

**现象**：`CardinalityViolationError: ON CONFLICT DO UPDATE command cannot affect row a second time`

**根因**：上游本身返回重复的自然键。实测：`fin_income` 单只股票 16~63 个重复键；`holder_number` 7 个；`top10_floatholders` 1 个。PostgreSQL 不允许同一条 `INSERT ... ON CONFLICT DO UPDATE` 内出现两行相同冲突键。

**修复**：新增 `dedupe_rows(rows, conflict_cols)` —— 按冲突键去重（保留最后一条，即更新的那条）；`upsert_rows` 与 `replace_rows_for_date` 统一调用。

### 5.3 BO / dict 类型不匹配导致数据全丢（`adj_factor`）

**现象**：`NotNullViolationError: null value in column "symbol"`；实际 6,000 行数据被静默丢弃。

**根因**：`AdjFactorTushareFetcher` 返回 pydantic BO（`BaseAdjFactorBO`），但 `AdjFactorRepository.save_batch` 按 dict 处理 —— `r.items()` 在 pydantic 对象上不可用，`"symbol" in bo` 恒为 `False` → `clean` 变空列表 → SQLAlchemy 退化成 `INSERT ... DEFAULT VALUES` → 插入一条 `symbol=NULL` 的垃圾行 → 整任务失败。

**修复**：统一先 `model_dump()` 归一化成 dict，再做字段过滤 + 分块 + 去重。

### 5.4 Date 列收到字符串（`stock_basic`）

**现象**：`DataError: invalid input for query argument $8: '2026-09-17' ('str' object has no attribute 'toordinal')`

**根因**：`_stock_basic_to_dict` 把 `list_date` / `delist_date` 调用了 `.isoformat()` 转成字符串，但表列类型是 `Date` → asyncpg 无法转换。

**修复**：改为直接传 `date` 对象。

### 5.5 Fetcher 忽略 symbol 参数（`dividend`）

**现象**：`tushare.dividend: 参数校验失败, ts_code/ann_date/record_date/ex_date/imp_ann_date参数不能都为空`

**根因**：`DividendTushareFetcher.fetch` 调 `pro.dividend()` 时**不传任何参数**，且完全忽略传入的 `symbol`。Tushare 要求至少给一个过滤条件。

**修复**：传 `ts_code`（带交易所后缀）；无 symbol 时用 `ann_date` 近一年兜底。

### 5.6 数据源可用性与上游格式（3 个实时查询 + 1 个采集）

| 问题 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 通达信「空站」 | 分 K 线查询恒返回 0 行，无任何报错 | 部分通达信镜像能连上、能应答协议（`get_security_count` 返回 27,784），但行情类接口一律返回空；原实现只在**连接失败**时才换主机 → 永远卡在这个空站 | `core/pytdx_client.py` 新增 `run_with_failover()`（空结果换主机重试）+ `mark_empty_response()`（空响应计数）+ 调整 `TDX_HOSTS` 顺序（`shtdx.gtjas.com` 实测可用）；取不到数据时**明确抛错**而非静默返回空 |
| DataFrame 真值歧义 | 分 K 线查询 500 | `if result:` 对 DataFrame 抛 `ValueError: The truth value of a DataFrame is ambiguous` | 新增 `_is_empty()` 统一判空（兼容 DataFrame / list / None / dict） |
| adata 概念代码格式 | `ValueError: substring not found` → 任务失败 | `index_code` 传了带后缀的 `885001.TI`；adata 只接受纯 6 位数字（`885996`） | 剥离后缀；实测 `index_code` 传数字稳定返回（4/4 次一致：87 条 / 15 条），而 `concept_code`（308xxx 网页代码）恒返回 0 条 |

## 六、验证方法与可复现步骤

### 6.1 自动化验证脚本

验证脚本位于 `collector-python/src/_tmp_collect_e2e.py`（临时文件，可按需转正）：

```bash
cd collector-python/src
python _tmp_collect_e2e.py --list     # 列出全部用例
python _tmp_collect_e2e.py             # 跑全部（24 采集 + 3 查询）
python _tmp_collect_e2e.py tech        # 只跑某个 facet
```

**判定逻辑**（不是只看任务状态，而是校验数据库真实行数增量）：

1. 记录目标表采集前行数
2. `POST /api/collect/tasks/{facet}/{name}` 建任务
3. 轮询 `GET /api/collect/tasks/{task_id}` 直到终态
4. 读目标表采集后行数
5. 判定：`status == "done"` 且无异常 → 通过；行数增量与 `saved_total` 一致 → 落库正确

### 6.2 单项手工验证示例

```powershell
# 建任务
$body = @{ facet="tech"; name="daily_kline"; strategy="incremental";
           params=@{ start_date="2026-10-27"; end_date="2026-10-29" } } | ConvertTo-Json -Depth 5
$tid = (Invoke-RestMethod -Uri "http://localhost:8001/api/collect/tasks/tech/daily_kline" `
        -Method Post -ContentType "application/json" -Body $body).data.task_id

# 轮询
Invoke-RestMethod -Uri "http://localhost:8001/api/collect/tasks/$tid"

# 实时查询
Invoke-RestMethod -Uri "http://localhost:8001/api/collect/query/minute_kline?params=%7B%22symbol%22%3A%22600519%22%2C%22interval%22%3A%225min%22%2C%22days%22%3A1%7D"
```
