是否持久化
    持久化考量角度
        一方面是比如日k，这种大量的数据，不能每次都实时查询，性能太差
        另一方面，后续想引入ai分析，需要能将必要数据入库，ai更易获取
    分k，实时概念行情变化波动大没必要持久化，实时查询+redis缓存
    实时咨询，虽然是实时获取，还是觉得有必要入库，后续可以让ai分析学习

## 三、context 拆分与数据归属

> `context/` 目录下划分业务上下文。**采集得到的数据进 `raw_data_db`，业务对象进 `attribution_db`**。

```
context/
├── auth        # 用户认证（attribution_db）
├── user        # 自选股池（attribution_db）
├── collect     # 采集元数据/方案/job（attribution_db）
├── data        # 数据领域服务（消费 raw_data_db + attribution_db）
├── market      # 技术面 + 资金面 + 基本面（含 stock_info）→ raw_data_db
├── concept     # 概念（采集自同花顺）→ raw_data_db
├── news        # 新闻面（待实现）→ raw_data_db

```

## 六、关键注意事项

| 问题 | 说明 |
|:--|:--|
| **复权** | `daily` 是未复权行情，算指标前需自己处理；`tech_adj_factor` 提供复权因子 |
| **财务修正** | `fundamental_report` 用 `report_type=1`（合并报表）；同 `end_date` + `report_type` 唯一 |
| **PE/换手率同源** | `daily_basic` 同一接口同时含 PE 和换手率，存表时**都进 `fundamental_daily_basic`**，应用层按字段归类 |
| **数据延迟** | `capital_margin` T+1 更新；深交所/北交所周五数据下周一上午才更新 |
| **停牌** | `tech_kline_daily` 停牌期间不提供；查询时要 LEFT JOIN `tech_suspend` 补空行 |
| **采集库 vs 业务库** | `data_board` 14 个查询走 `raw_data_db`；用户/池查询走 `attribution_db`；跨库 join 在应用层做 |
