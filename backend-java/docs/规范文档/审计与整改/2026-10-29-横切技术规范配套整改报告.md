## 3. 设计决策记录

### 3.1 Converter 保持静态工具类，不改 Spring Bean

**问题**：`PoolConverter` 需要 `ObjectMapper`，最直觉的做法是改成 `@Component` 注入。

**结论**：❌ 不改。

**理由**：`POJO规范.md` §4.2 明确规定 Converter 是「无状态纯函数 + 静态工厂」，
且现有 4 个 Converter（`MarketConverter` / `DataBoardConverter` / `ConceptConverter` /
`PoolConverter`）**全部**是静态工具类。为 1 处需求破坏全局约定不值得。

**做法**：`ObjectMapper` 作为**方法参数**传入，由 Service 注入后透传：

```java
// Service 层
private final ObjectMapper objectMapper;   // ← Spring 注入

// Converter 层（保持 static）
public static PoolOperationVO toVO(PoolOperationPO po, ObjectMapper mapper) { ... }

// 调用
return PoolConverter.toVO(operation, objectMapper);
```

**新增规则**：写入 `POJO规范.md` §4.3.1（Converter 需要 ObjectMapper 时：传参，不要 new）。

> ⚠️ 序列化与反序列化必须用**同一个** `ObjectMapper` 实例，
> 否则写入格式与读取格式可能不一致。

### 3.2 Redis 连接池配置不写入 `application.yml`

**问题**：原本按规范加了 `spring.data.redis.lettuce.pool.*`。

**结论**：❌ 移除。

**理由**：Lettuce 的连接池**需要 `commons-pool2` 依赖**才生效。
本项目**未引入**该依赖 → 这段配置会被**静默忽略**，
形成「看起来配了、实际没生效」的假配置。

**做法**：`application.yml` 与 `.env.example` 中保留注释说明前提条件，
并在 `基础设施规范.md` §3.6 写明该前提。

> 📌 **教训**：配置项的**生效前提**必须写进规范。
> 否则排查时会误以为「池太小是瓶颈」，而实际是配置根本没生效。

### 3.3 目录重命名：`工程架构分层规范/` → `纵向分层规范/`

原目录名「工程架构分层规范」与新增的「横切技术规范」在语义上不平行
（一个是「纵向分层」，一个是「横切关注点」）。

重命名后目录关系清晰：

```
规范文档/
├── 纵向分层规范/    ← 各层职责（纵向切分）
├── 横切技术规范/    ← 跨层关注点（横向切分）
└── 审计与整改/      ← 历史快照
```

同步更新了全部引用（4 个 Java 文件注释 + 7 个 Markdown 文档）。

## 5. 新增配置项

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DB_POOL_MAX_SIZE` | 20 | HikariCP 最大连接数 |
| `DB_POOL_MIN_IDLE` | 5 | 最小空闲连接 |
| `DB_POOL_CONNECTION_TIMEOUT` | 30000 | 获取连接超时（毫秒）|
| `DB_POOL_IDLE_TIMEOUT` | 600000 | 空闲连接回收（毫秒）|
| `DB_POOL_MAX_LIFETIME` | 1800000 | 连接最大存活（毫秒）|
| `DB_POOL_LEAK_DETECTION` | 60000 | 泄漏检测阈值（毫秒）|
| `APP_CORS_ALLOWED_ORIGINS` | `http://localhost:3000,http://127.0.0.1:3000` | CORS 允许源（逗号分隔）|

全部可通过环境变量覆盖，默认值写在 `application.yml`。
