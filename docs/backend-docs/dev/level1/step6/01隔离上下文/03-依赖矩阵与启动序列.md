## 2. import 规则（强约束）

### 2.1 跨 context 的 import 规则

```
问：在 contexts/A/xxx.py 里要 import contexts/B/yyy.py
答：分情况
├─ A 的 application/service 里要 import B 的东西：
│   ├─ 只 import B 的 port（contexts.B.application.port.*）✅
│   └─ import B 的 domain（contexts.B.domain.*）❌（阶段 1 允许 + TODO；阶段 3 强制不允许）
├─ A 的 domain 里要 import B 的东西：
│   └─ 不允许 ❌（domain 是业务核心，不能反向依赖）
├─ A 的 infrastructure 里要 import B 的东西：
│   └─ 只 import B 的 port 或 B 的 domain（实现 port 需要）✅
├─ A 的 interface 里要 import B 的东西：
│   ├─ 只 import A 的 application/service（不跨 context）✅
│   └─ 跨 context 走 A 自己的 application/service 编排 ❌（直接调 B 的 port）
└─ shared 内的东西：
    └─ 任何 context 都可以 import（但尽量少用）⚠️
```

## 3. 启动序列

### 3.1 启动时序图

```
app/lifespan()
│
├─ ① shared 初始化
│   ├─ key_manager.warmup()             # auth/security（启动最早，密钥要预热）
│   ├─ ensure_schema()                  # shared/persistence（表结构校验）
│   └─ get_settings()                   # 配置读取
│
├─ ② data context 初始化
│   ├─ setup_data()                     # 注册所有 DataPort 的 Adapter
│   └─ （data 不依赖其他业务 context）
│
├─ ③ market context 初始化
│   ├─ ensure_default_pool()            # 首次启动创建"我的自选"（注意：实际是 user 的）
│   └─ （market 依赖 data，已就绪）
│
├─ ④ concept context 初始化
│   └─ （concept 依赖 data，已就绪）
│
├─ ⑤ user context 初始化
│   ├─ ensure_default_pool()            # 用户的默认自选池
│   └─ （user 不依赖其他业务 context）
│
├─ ⑥ auth context 初始化
│   └─ ensure_initial_admin()           # 首次启动创建 admin
│
├─ ⑦ collect context 初始化
│   ├─ build_collect_context()          # CollectContext 组装（注入 data/market/concept 的 port）
│   ├─ setup_collect()                  # 注册 23 个任务
│   ├─ sync_fetcher_catalog()           # collect_fetchers 表对账
│   └─ scheduler 启动（如果启用）       # collect 自带调度器
│
└─ yield → 应用就绪
```

### 3.2 启动代码示例

```python
# app/lifespan.py（草稿）

from contextlib import asynccontextmanager
from fastapi import FastAPI
import logging

from contexts.shared.infrastructure.config.settings import get_settings
from contexts.shared.infrastructure.persistence.connection import close_db
from contexts.shared.infrastructure.persistence.schema_init import ensure_schema
from contexts.auth.infrastructure.security import key_manager

logger = logging.getLogger(__name__)

@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()
    
    # ① shared 初始化
    key_manager.warmup()
    await ensure_schema()
    
    # ②~⑥ 各 context 初始化（顺序由各 context 的 setup_xxx 完成）
    from contexts.data.bootstrap import setup_data
    from contexts.market.bootstrap import setup_market
    from contexts.concept.bootstrap import setup_concept
    from contexts.user.bootstrap import setup_user
    from contexts.auth.bootstrap import setup_auth
    from contexts.collect.bootstrap import setup_collect
    
    setup_data(app)
    setup_market(app)
    setup_concept(app)
    setup_user(app)
    setup_auth(app)
    setup_collect(app)
    
    logger.info("应用启动完成")
    
    yield
    
    # 反序关闭
    from contexts.collect.application.service import cancel_background
    await cancel_background()
    await close_db()
```

### 3.3 启动顺序的关键约束

| 顺序 | 约束 | 违反后果 |
| :-- | :-- | :-- |
| **shared → data** | shared 的 settings 必须先 ready，data 的 setup_data 读 settings | 启动报错（配置未加载） |
| **data → market/concept** | market/concept 的 collect 任务需要 `DataGatewayPort` | 采集启动后找不到 port |
| **auth → collect** | collect 的某些任务可能受权限保护（暂未，未来） | 任务无法启动 |
| **任何 → collect** | collect 启动时校验 `collect_fetchers` 表，要所有 23 个任务都已注册 | 对账失败 |
| **scheduler → 业务路由** | scheduler 在 lifespan 末尾启动，确保业务路由已注册 | 调度触发时找不到 handler |

> 简记：**`shared → data → {market, concept} → user → auth → collect → scheduler`**。

## 5. 跨 context 调用的 3 种形式

### 5.1 形式 A：服务内部直接 import 对方 domain（**阶段 1 形态**）

```python
# contexts/market/application/service/stock_info_service.py
from contexts.concept.domain.repository import ConceptRepository  # ⚠️ 跨 context domain
from contexts.concept.domain.service.concept_brief_service import ConceptBriefService
# TODO(隔离): 阶段 3 改为 ConceptQueryPort
```

**问题**：
- market 和 concept 编译期耦合
- 单元测试要 mock 整个 concept domain
- 改 concept 的 domain 影响 market

### 5.2 形式 B：通过对方 port 注入（**阶段 3 形态**）

```python
# contexts/market/application/service/stock_info_service.py
from contexts.concept.application.port.query import ConceptQueryPort  # ✅ 走 port

class StockInfoService:
    def __init__(
        self,
        ...,
        concept_port: ConceptQueryPort,  # 由 DI 注入
    ):
        self._concept = concept_port
    
    async def list_stocks_with_main_concept(self, ...):
        # 通过 port 调用，不直接 import 对方 domain
        briefs = await self._concept.list_for_symbol(symbol)
        ...
```

**好处**：
- market 只看 concept 的 port 形状
- 单元测试只 mock port
- concept 改 domain 不影响 market（只要 port 不变）

### 5.3 形式 C：事件订阅（**阶段 4 形态**）

```python
# contexts/market/application/port/event.py
class MarketEventSubscriber(Protocol):
    async def on_member_added(self, event: MemberAdded) -> None:
        """user 那边股票加入池时，market 自动加入面板"""
        ...

# app/wiring.py
def wire_events(bus):
    bus.subscribe(MemberAdded, market_subscriber.on_member_added)
```

**好处**：
- 业务方不感知（user 加股票后，market 自己响应）
- 失败不传播（market 的 handler 失败不影响 user 的加股票流程）

> 本期（阶段 1）= 形式 A + TODO 标记。
> 阶段 3 = 形式 B（同步调用）。
> 阶段 4 = 形式 C（事件解耦）。

## 6. 关键决策（再次确认）

| 问题 | 决策 | 理由 |
| :-- | :-- | :-- |
| 跨 context 调用默认形式？ | A → B → C 三步走 | 阶段 1 不破坏代码，阶段 3 引入 port 解耦 |
| DI 集中点？ | `infrastructure/config/di.py` 暂保留（在 shared 内） | 渐进式，不一次性大改 |
| 启动顺序的契约？ | shared → data → {market/concept} → user → auth → collect → scheduler | data 是底座，collect 是顶层协调者 |
| shared 与 context 边界？ | `shared/` 只放**真的有跨 context 价值**的；具体 type / 通用框架放 shared | 避免 shared 膨胀 |
| collect 是否能 import market/concept 的 port？ | 阶段 3 引入 KlineCommandPort、ConceptCommandPort | 采集中转数据要写对方库 |
| market 是否能 import collect？ | **不能** | 业务不能反向依赖采集 |
| auth 是否能 import 其他业务 context？ | **不能** | 鉴权是横切，不感知业务 |
