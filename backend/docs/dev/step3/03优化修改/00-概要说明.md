### Q1：登录失败的"友好提示"粒度

- 当前后端 `AuthAppService.login()` 在以下三种情况抛异常：
  1. 邮箱不存在 / 密码错 → `InvalidCredentialsError`（合并为同一种异常，避免账号枚举攻击）
  2. 账号禁用 → `UserInactiveError`
  3. 图形验证码错 → `InvalidCaptchaError`（如有）
- 前端现在 3 种情况都走同一个 catch（`console.warn` + 刷新图形验证码）
- **不确定**：你想区分"账号/密码错 vs 图形验证码错 vs 账号禁用"吗？
  - **方案 A**（推荐）：统一弹 `ElMessage.error('邮箱或密码错误，或图形验证码错误')`，无差异化（更安全，避免账号枚举）
  - **方案 B**：前端根据后端 `code` 区分弹不同文案（友好但有账号枚举风险）
  - 见 `01-登录失败提示.md` §3

### Q2：概念看板"按类型筛选"语义

- 当前后端 `type_filter=industry` 会 SQL `WHERE concept_type='industry'`
- 前端 `ConceptCardGrid.vue` 又按 `concept_type === t` 再分一次组
- 用户选了"行业概念"后只看到 1 个分组（"行业概念（N 个）"），符合设计，但**视觉上不像"卡片区没数据"**
- **不确定**：用户希望的是哪种？
  - **方案 A**（最小修改）：筛某类型时，卡片区**不再分组**，直接平铺所有该类型卡片
  - **方案 B**：保留分组，但视觉上对单 type 隐藏"分组标题"（只展示平铺卡片）
  - **方案 C**：前端把筛选与分组解耦 — 筛某 type 时，进**纯列表视图**（类似股票列表）而非卡片网格视图
- 数据上**完全没问题**（DB 里 6 种 type 都有数据），只是前端分组逻辑与"筛选"语义有冲突
- 见 `02-概念看板筛选空数据.md` §2

### Q3：概念日 K 的数据完整性

- `ConceptIndexTHDB` 表存在；但**当前没有任何前端/路由在调用它**
- 数据是否齐全（所有 390 个概念都覆盖到了？）— 需要查 `concept_index_ths` 表的 `COUNT(DISTINCT index_code)`
- **不确定**：是否要先去采集历史日 K？还是先用现有数据写 UI？
- 见 `03-概念日K+实时行情.md` §2.2

### Q4：service 重构的代价

- `application/service/` 现有 9 个文件（auth / collect / concept / kline / panel / pool / pool_operation / stock_analysis / stock），单文件 150-460 行
- DI 注册在 `infrastructure/config/di.py` 全部 hardcode，**切目录需要同步改 DI**
- 现有前端业务模块（views/*）有 7 个：auth / stock-info / collect-manage / concept-board / stock-pool / market / Dashboard
- **不确定**：
  - 重构粒度？是"全量重组"还是"渐进迁移"（仅把概念大盘单拎出来？）
  - 是否保留 `_app_service.py` 后缀？还是用 `_service.py`？
  - 是否兼容旧的命名空间（避免 DI 改动过大）？
- 见 `05-业务模块化service重构.md` §4

### Q5：日志清理是否要入 `.gitignore`

- `.b1.err/.b1.log/.b8.err/.vite.log` 都是临时产物，但用户每次重启进程都会重新生成
- **方案 A**：把它们加入 `.gitignore`（推荐），但开发中还是会出现在工作区
- **方案 B**：改后端/前端启动脚本，用 `%TEMP%` 目录代替 backend 目录
- **方案 C**：只清理本次，不入 gitignore（下次还会再次生成）
- 见 `04-临时日志清理.md` §3
