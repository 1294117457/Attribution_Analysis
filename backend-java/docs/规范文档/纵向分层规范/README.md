## 分层总览

```
┌──────────────────────────────────────────────────────────────┐
│ Controller  HTTP 协议、参数绑定、@Valid 校验、组装 ApiResponse │
│   ↕ DTO(Query) / VO                                          │
├──────────────────────────────────────────────────────────────┤
│ Service     ★ 业务编排层 ★                                   │
│             · 业务规则校验   · 调用 Mapper                    │
│             · PO → VO 转换   · 事务边界                      │
│   ↕ PO / Row                                                 │
├──────────────────────────────────────────────────────────────┤
│ Mapper      ★ 持久化唯一入口 ★                               │
│             · 单表 CRUD / 联表聚合 / 批量                     │
│   ↕                                                           │
├──────────────────────────────────────────────────────────────┤
│ DB          表                                                 │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 唯一职责 | 判断标准 |
|---|---|---|
| **Controller** | 协议适配 | 代码里出现 `@RequestParam` / `@PathVariable` / `ApiResponse` |
| **Service** | 业务编排 | 代码里出现查库后的 `if`、多 Mapper 协作、`@Transactional` |
| **Mapper** | 数据存取 | 代码里只有查询条件与结果映射，**无业务判断** |
| **Converter** | 数据搬运 | 代码里只有 `po.getXxx()` → `vo.setXxx()` |
| **Util** | 无状态计算 | 代码里只有数学 / 指标计算，无 IO |

## 三条核心原则

1. **数据形状看 `POJO规范.md`** —— 用「谁的字段」判断，不看字段数量。
2. **职责边界看分层规范** —— 一段逻辑只属于一层，不跨层。
3. **依赖方向单向** —— Controller → Service → Mapper → DB，反向调用即违规。

## 文档定位：规范 vs 审计

本目录（`纵向分层规范/`）里的文档是**规范**——只写「应该长什么样」，**不含任何现状计数**。

| 类型 | 位置 | 内容 | 是否会过期 |
|---|---|---|---|
| **规范** | `纵向分层规范/` | 规则、模板、决策流程、Code Review 清单 | **不会**（规则变了才需要改）|
| **规范** | `../横切技术规范/` | 跨层的异常、响应、连接池、Redis、线程池、CORS | **不会**（规则变了才需要改）|
| **审计快照** | `../审计与整改/` | 某次整改的实测数字、待整改清单 | **会**，但**归档不更新** |

> 📌 **写规范的规矩**：不要在规范文档里写「当前有多少处」「某个文件现在怎样」。
> 这类信息会随代码变化而失真，一旦失真就没人信它了。
> 需要记录现状时，写进 `审计与整改/` 下带日期的快照文件。
