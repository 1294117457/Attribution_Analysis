# 异常与响应规范

> 适用范围：`backend-java` 全部 Maven 模块
> 核心原则：**异常只抛一次，转换只做一次，响应永远一个形状。**
> 配套文档：`../纵向分层规范/Service层规范.md`（谁抛异常）、`../纵向分层规范/Controller层规范.md`（协议层）、`../纵向分层规范/Mapper层规范.md`（持久化异常）

---

## 0. 一句话结论
> **Service 抛 `BusinessException`，`GlobalExceptionHandler` 转 HTTP 响应，Controller 和 Controller 之外的任何地方都不许 try-catch 业务异常。**
> **异常细节只进日志，不进响应体。**

---

## 1. 职责速查

```
业务代码                     转换中枢                    前端
────────────────────────────────────────────────────────────────
Service                      GlobalExceptionHandler      Axios 拦截器
  │                                │                        │
  ├─ 抛 BusinessException(code) ──▶│──▶ HTTP code = code    │
  │   （code 即 HTTP 状态码）      │    body = {code,message,data}
  │                                │
  ├─ 抛 RuntimeException ─────────▶│──▶ HTTP 500            │
  │   （不该发生 = 编码错误）        │    body.message = 通用文案
  │                                │    原始异常 → 日志
  │                                │
  └─ 不 catch，不包装 ────────────▶│                        │
                                    └──────▶ 拦截器按 code 弹提示
```

| 角色 | 唯一职责 | 判断标准 |
|---|---|---|
| **Service** | 判断「是不是业务错误」，是就抛 `BusinessException` | 代码里出现 `throw new BusinessException(...)` |
| **GlobalExceptionHandler** | 把异常映射成 HTTP 响应 | 代码里出现 `@ExceptionHandler` |
| **Controller** | **不碰异常**，让异常自然冒泡 | 代码里**没有** `try-catch` |
| **Mapper** | 不吞异常；DB 异常直接上抛 | 代码里没有 `catch (Exception)` |

> ⚠️ **反向自检**：Controller 里出现 `try-catch` → 几乎总是错的。
> 唯一例外是「读 body 的流且必须关闭」这类资源管理场景，本项目不存在。

## 2. 异常分类

### 2.1 异常体系

项目只有**一种业务异常** + Spring 框架异常：

| 类型 | 来源 | 用途 |
|---|---|---|
| `BusinessException` | Service 主动抛出 | **业务规则不满足**（资源不存在、状态冲突、权限不足、参数非法）|
| `MethodArgumentNotValidException` | Spring MVC（`@Valid` 校验失败）| **格式校验失败**（长度、正则、范围、必填）|
| `DataAccessException` / `PersistenceException` | MyBatis-Plus / JDBC | 数据库层错误，**不捕获**，走 500 |
| 其他 `RuntimeException` | 代码 bug（空指针、类型转换失败等）| 走 500 |

> 📌 **不要自造异常体系**。需要区分错误类型时，用 `BusinessException` 的不同 `code` 表达，
> 不要建 `XxxBusinessException extends RuntimeException` 的继承树——那会让
> `GlobalExceptionHandler` 的映射表不断膨胀。

### 2.2 错误码约定

**`BusinessException.code` 直接就是 HTTP 状态码**——不另设一套业务错误码体系。

| code | HTTP 语义 | 典型场景 | 前端表现 |
|---|---|---|---|
| `400` | Bad Request | 参数非法、验证码错误、邮箱格式错误 | 弹 message |
| `401` | Unauthorized | 未登录、token 失效、密码错误 | 跳登录（拦截器自动处理）|
| `403` | Forbidden | 已登录但无权限、账号停用 | 弹「没有权限访问」 |
| `404` | Not Found | 资源不存在（池不存在、股票不存在、操作不存在）| 弹 message |
| `409` | Conflict | 状态冲突（重名、已有进行中任务）| 弹 message |
| `422` | Unprocessable Entity | Bean Validation 校验失败（**由框架 handler 产生，不手动抛**）| 弹全部字段错误 |
| `500` | Internal Server Error | 未预期异常 | 弹「服务器错误」 |

```java
// ✅ 正确：code 直接用 HTTP 语义
if (pool == null) throw new BusinessException(404, "池不存在");
if (!Boolean.TRUE.equals(user.getIsActive())) throw new BusinessException(403, "账号已停用");
if (nameExists) throw new BusinessException(409, "池名称已存在");

// ❌ 错误：自造错误码体系
if (pool == null) throw new BusinessException(10001, "池不存在");
```

> 📌 **为什么不用自定义错误码？**
> 前端拦截器已按 `code >= 400` 统一处理（见 `../纵向分层规范/Controller层规范.md` §2.5）。
> 自造 5 位数错误码会要求前端同步维护一张映射表，且**新增错误码时前端不改就静默失效**。

### 2.3 `BusinessException` 用法

```java
// ✅ 正确：单参数构造 → 默认 400
throw new BusinessException("验证码错误");

// ✅ 正确：双参数构造 → 显式指定 code
throw new BusinessException(404, "池不存在");
```

| 规则 | 说明 |
|---|---|
| `code` **必须**是合法 HTTP 状态码 | 否则 `ResponseEntity.status(code)` 会抛 `IllegalArgumentException` |
| `message` 是**面向用户的中文提示** | 会原样显示在前端弹窗里 |
| `message` **不得**包含内部细节 | 不写「表 stock_pools 无记录」「NullPointerException at xxx」|
| **不要**把异常对象塞进 message | `throw new BusinessException(500, e.getMessage())` 是错的——500 应由 handler 统一产生 |
| **不要**在 Service 里 `catch` 后重新抛 `BusinessException` | 那样会丢失原始堆栈，排查困难 |

## 3. `GlobalExceptionHandler` 规范

### 3.1 映射表

`GlobalExceptionHandler` 是**唯一的异常→响应转换点**，映射关系固定：

| 异常 | HTTP code | 响应 message | 日志级别 | 是否带堆栈 |
|---|---|---|---|---|
| `BusinessException` | `ex.getCode()` | `ex.getMessage()` | `warn` | ❌ |
| `MethodArgumentNotValidException` | `422` | 全部字段错误拼接 | `warn` | ❌ |
| 其他 `Exception` | `500` | **通用文案** | `error` | ✅ |

### 3.2 兜底 handler 不得泄漏内部细节

```java
// ✅ 正确：原始异常与堆栈进日志，响应只有通用文案
@ExceptionHandler(Exception.class)
public ResponseEntity<ApiResponse<?>> unexpected(Exception ex) {
    log.error("未预期异常", ex);
    return ResponseEntity.status(500).body(ApiResponse.fail(500, "服务器内部错误，请稍后重试"));
}

// ❌ 错误：ex.getMessage() 可能含 SQL 语句、表名、字段名、内部路径
@ExceptionHandler(Exception.class)
public ResponseEntity<ApiResponse<?>> unexpected(Exception ex) {
    return ResponseEntity.status(500).body(ApiResponse.fail(500, "server error: " + ex.getMessage()));
}
```

> ⚠️ **为什么这条是硬规则？**
> `ex.getMessage()` 对 `DataAccessException` 来说会包含**完整 SQL 语句和参数值**。
> 用户触发的 500 如果把 SQL 回给前端，等于把数据库结构公开。
> 同时它也是**信息泄漏**（表名、内部服务名、文件路径）。

### 3.3 校验失败要一次返回全部错误

```java
// ✅ 正确：收集全部字段错误
String message = ex.getBindingResult().getFieldErrors().stream()
        .map(error -> error.getField() + ": " + error.getDefaultMessage())
        .collect(Collectors.joining("; "));
```

> 只返回第一个错误会让用户「改一个报一个」，体验差且往返多。

### 3.4 不在 handler 里做业务判断

```java
// ❌ 错误：handler 里开始分支判断业务语义
if (ex instanceof SomeException && user.isAdmin()) { ... }

// ✅ 正确：handler 只做「异常类型 → HTTP 响应」的机械映射
```

> 若某类错误需要**不同的响应体结构**（而非不同 code / message），
> 应先在 Service 层转成 `BusinessException` 表达，而不是在 handler 里加分支。

## 4. 响应体契约

### 4.1 统一结构

**所有** HTTP 响应（成功与失败）都是同一形状：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | **等于 HTTP 状态码**（成功时 200 / 201）|
| `message` | string | 成功时 `success` / `创建成功`；失败时是面向用户的提示 |
| `data` | any | 业务数据；无返回体时为 `null` |

> 📌 **为什么 `code` 冗余等于 HTTP 状态码？**
> 前端拦截器统一读 `body.code` 判断成败，这样即使网关改写了 HTTP 状态码，
> 前端逻辑仍然一致。详见 `../纵向分层规范/Controller层规范.md` §2.5。

### 4.2 工厂方法

| 方法 | 使用场景 | HTTP |
|---|---|---|
| `ApiResponse.ok(data)` | 查询 / 更新 / 删除成功 | 200 |
| `ApiResponse.ok()` | 无返回体（`ApiResponse<Void>`）| 200 |
| `ApiResponse.created(data)` | **真正创建资源** | 201 |
| `ApiResponse.fail(code, message)` | **仅限 Controller 自身的格式性拒绝** | 由 `code` 决定 |

> ⚠️ `ApiResponse.fail` 在 Controller 里**几乎不该出现**——
> 业务失败应该是 Service 抛 `BusinessException`，由 handler 统一转。
> Controller 里唯一的合理用法是「入参在进入 Service 前就被拒绝」的纯格式校验。

### 4.3 分页响应

分页出参统一 `PageResult<T>`，**禁止**自定义字段名、禁止裸 `Map`：

```java
public class PageResult<T> {
    private long total;
    private List<T> list;
    private int page;
    private int pageSize;
}
```

> 📌 前端分页组件读的是 `total` + `list`，改动会**静默**导致列表空白。
> 序列化后字段名为 `total` / `list` / `page` / `page_size`（`SNAKE_CASE` 策略）。

## 5. 日志规范

### 5.1 日志与响应的分工

| 信息 | 日志 | 响应 |
|---|---|---|
| 业务失败原因（"池不存在"）| ✅ warn | ✅ 给用户看 |
| 未预期异常类型与堆栈 | ✅ error | ❌ 只给通用文案 |
| 用户 ID / 请求 ID / 关键业务标识 | ✅ | ❌ |
| SQL 语句、内部路径、配置值 | ✅ | ❌ **绝不** |

### 5.2 记日志的时机

| 场景 | 记不记 | 在哪记 |
|---|---|---|
| Service 判定业务失败并抛异常 | 记 `warn` | `GlobalExceptionHandler`（**不要**在 Service 里重复记）|
| Service 内部 catch 后降级 | 记 `warn` + 降级语义 | **Service 内**（handler 看不到）|
| 未预期异常 | 记 `error` + 堆栈 | `GlobalExceptionHandler` |
| 远程调用超时 | 记 `warn` | Service 内 |
| 正常业务流程 | ❌ 不记 | — |

> ⚠️ **不要双重记录**：Service 里 `log.error(...)` 后又 `throw`，handler 又 `log.error(...)`，
> 同一个异常会在日志里出现两遍，反而干扰排查。

### 5.3 降级处的日志必须带语义

```java
// ✅ 正确：说明「为什么可以忽略」
} catch (Exception ignored) {
    log.warn("概念 {} 元信息查询失败，跳过该条", conceptName);
}

// ❌ 错误：没有任何上下文
} catch (Exception ignored) {
}
```

> 📌 `catch (Exception ignored)` 只允许出现在**有明确降级兜底**的外部调用场景
> （见 `../纵向分层规范/Service层规范.md` §3.4），且**必须**有注释或日志说明降级语义。

### 5.4 日志格式

| 项 | 约定 |
|---|---|
| 框架 | SLF4J（`@Slf4j` 或 `LoggerFactory`）|
| 参数化占位符 | `log.warn("池不存在: {}", poolId)`，**禁止**字符串拼接 |
| 异常对象 | 放**最后一个参数**，不要 `e.getMessage()` 拼进文案 |
| 级别 | `error`=需要人介入；`warn`=预期内的失败；`info`=关键业务节点；`debug`=排查用 |

## 6. 决策流程

```
我要处理一个异常
  │
  ├─ 是「业务规则不满足」？
  │   └─ 是 → Service 抛 BusinessException(code, 中文提示)
  │            code 用 HTTP 语义（400/401/403/404/409）
  │            message 不含内部细节
  │
  ├─ 是「格式校验失败」？
  │   └─ 是 → DTO 加 @Valid 注解，不要手写 if
  │
  ├─ 是「外部调用失败」？
  │   └─ 是 → Service 内 catch + 降级 + log.warn（不抛）
  │            降级不了才抛 BusinessException(503, ...)
  │
  ├─ 是「DB 异常」？
  │   └─ 是 → 不捕获，直接上抛 → handler 转 500
  │
  └─ 是「代码 bug」（NPE / ClassCast）？
      └─ 是 → 不捕获 → handler 转 500 + error 日志
```

## 7. Code Review 清单

| # | 检查项 | 违规信号 |
|---|---|---|
| 1 | Controller 有 try-catch？ | `catch (Exception e) { return ApiResponse.fail(...) }` |
| 2 | 500 响应带原始 message？ | `ApiResponse.fail(500, ex.getMessage())` |
| 3 | 业务异常用自定义错误码？ | `BusinessException(10001, ...)` |
| 4 | code 不是合法 HTTP 状态码？ | `BusinessException(999, ...)` |
| 5 | message 含内部细节？ | message 里有 SQL / 表名 / 堆栈 |
| 6 | 异常被 Service catch 后吞掉？ | `catch (Exception ignored) { }` 且无降级语义 |
| 7 | 降级处没有日志？ | `catch (Exception ignored) {}` 空块 |
| 8 | 同一异常记两遍日志？ | Service `log.error` + handler `log.error` |
| 9 | 自造异常继承树？ | `XxxBusinessException extends RuntimeException` |
| 10 | 响应体形状不统一？ | 某接口返回裸对象而不是 `ApiResponse` |
| 11 | 分页用自定义字段名？ | 不是 `PageResult<T>` |
| 12 | `ApiResponse.fail` 被 Controller 滥用来表达业务失败？ | Service 该抛异常却返回 `fail(...)` |

## 8. 技术前提（环境事实，长期有效）

| 项 | 值 | 来源 |
|---|---|---|
| 统一响应 | `ApiResponse<T>` = `{code, message, data}` | `attribution-common/response/ApiResponse.java` |
| 分页出参 | `PageResult<T>` = `{total, list, page, page_size}` | `attribution-common/response/PageResult.java` |
| 业务异常 | `BusinessException(code, message)`，`code` 即 HTTP 状态码 | `attribution-common/exception/BusinessException.java` |
| 全局异常处理 | `GlobalExceptionHandler`（`@RestControllerAdvice`）| `attribution-common/exception/GlobalExceptionHandler.java` |
| 校验框架 | Jakarta Bean Validation，`@Valid` 触发 | `pom.xml` |
| 校验失败 | 422，返回**全部**字段错误 | `GlobalExceptionHandler` |
| 兜底 500 | 响应只有通用文案，原始异常进 `error` 日志 | `GlobalExceptionHandler` |
| 日志框架 | SLF4J（Spring Boot 内置 Logback）| `spring-boot-starter-logging` |
| JSON 命名策略 | `SNAKE_CASE` | `application.yml` |
| 前端拦截器 | 按 `body.code >= 400` 判定失败并弹提示 | `frontend/src/common/utils/http.ts` |
