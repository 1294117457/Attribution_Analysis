## 一、三类模式，各解决什么

设计模式按用途分三类：

- 创建型：对象怎么造出来、谁来造。例如工厂、注册表、单例。
- 结构型：对象之间怎么拼装、怎么包一层。例如适配器、门面、装饰器、代理。
- 行为型：运行时怎么分工、怎么选。例如策略、模板方法、责任链、命令。

很多人觉得这些模式"差不多"，是因为写出来的代码形状很像，都是一个接口加几个实现类。真正的区别在于意图。

## 二、逐个说明，并对应到这个项目

### 1. 适配器：把"不一样的接口"转成"我要的接口"

- 解决的问题：tushare 返回 DataFrame，字段叫 `ts_code`、`trade_date`、`vol`；adata 返回另一种结构；pytdx 是 socket 加列表。你的业务只想要 `list[KlineBO]`，股票代码只用 6 位的 `symbol`。
- 项目里：每个 Provider 本质上就是一个适配器。现在的 `TushareKlineParser`、`symbol_to_ts_code` 就是适配逻辑。
- 特点：在写代码的时候就确定了"把谁转成谁"。它关心的是接口形状对不上。

### 2. 策略：同一件事有多种做法，运行时选一种

- 解决的问题：日 K 可以从 tushare、akshare（东财）、adata 取，三者对外都是 `fetch(params) -> list[KlineBO]`，具体用哪个由配置或参数决定。
- 项目里：`gateway.invoke("daily_kline", params, source="akshare")`，或者按 `priority` 自动选一个。
- 特点：各实现之间可以互相替换。它关心的是选哪一个。

### 3. 适配器和策略的区别（最容易混）

在这个项目里，同一个 Provider 类两种角色都有：

- 从实现的角度看，它是适配器：把 tushare 的接口转成 `DailyKline` 契约。
- 从使用的角度看，它是策略：Gateway 在 tushare、akshare、adata 之间挑一个。

所以不是二选一。先用适配器把它们变成同一种接口，才能把它们当策略来互换。如果没做适配，签名不统一（就像现在的 `fetch` / `fetch_daily_basic(trade_date)` / `fetch_minute_klines`），就做不了策略选择。

### 4. 工厂、注册表：解决"谁来创建、去哪拿"

有三种常见形式：

- 简单工厂：`if source == "tushare": return TushareXxx()`。每加一个数据源就要改这段 `if`，违反开闭原则。
- 工厂方法：子类决定创建什么。适合"一个框架、多种产品"，在这个项目里没必要用。
- 注册表式工厂：用 `dict` 存"名字或类型 → 构造函数"，新增数据源只需要注册一下。你现在的 `FetcherRegistry`（`register_instance` / `register_factory` / `create`）就是这种。

它和策略的区别：工厂负责怎么得到对象，策略负责用哪个对象干活。项目里注册表就是策略的"仓库"，Gateway 从注册表里取出所有候选，再按策略规则挑一个。

### 5. 抽象工厂：这里不推荐

- 它的意图：一个工厂产出"一整套配套产品"，比如 `TushareFactory` 产出日 K、估值、资金流等全部实现，`AkshareFactory` 产出另一整套。
- 不合适的原因：各家能覆盖的数据集差别很大（pytdx 只有行情，adata 主要是同花顺概念）。你还希望每份数据单独选源，比如日 K 用 tushare、概念用 adata。抽象工厂会把"按厂商成套切换"写死，正好和需求相反。

### 6. 门面：给复杂子系统一个简单入口

- 项目里：`DataGateway`。调用方不需要知道注册表、选源、限流、缓存这些细节，只要调用 `invoke(name, params)`。
- 和适配器的区别：适配器是"一对一转换接口"；门面是"把一堆东西包成一个简单入口"。

### 7. 装饰器 / 代理 / 中间件：接口不变，在外面加功能

- 项目里：限流、重试、缓存、调用统计。现在每个采集任务都复制一份 `_fetch_with_rate_limit`，换成装饰器后，只要包在 Provider 外面一次。

- 几个相近模式的区别：

  | 模式   | 接口变不变 | 意图                           |
  | :----- | :--------- | :----------------------------- |
  | 适配器 | 变         | 转换接口                       |
  | 装饰器 | 不变       | 叠加功能，可以层层套           |
  | 代理   | 不变       | 控制访问（缓存、权限、懒加载） |

- 在 Python 里，这三者常常写成同一种"中间件链"：`Retry(RateLimit(Cache(provider)))`。现在的 `RealtimeQueryFramework`（缓存、单飞、降级）本质上就是代理加装饰器。

### 8. 责任链：一个一个试，直到有人处理成功

- 项目里：数据源失败自动切换。先试 tushare，限频或报错就换 akshare，再不行换 adata。
- 和策略的区别：策略是"一开始就挑定一个"；责任链是"按顺序尝试，前一个失败才轮到下一个"。实际做法是两者组合：默认用责任链兜底，调用方显式指定 `source` 时退化成单一策略。

### 9. 模板方法：流程骨架固定，个别步骤由子类填

- 项目里：`BaseCollectTask.execute_task` 已经是模板方法。流程固定为"列出单元 → 过滤已有 → 并发采集 → 重试 → 记录进度"，子类只实现 `list_units` / `collect_one` / `existing_units`。
- 和策略的区别：模板方法靠继承，替换的是流程中的某几步；策略靠组合，替换的是一整段算法。
- 建议：采集流水线骨架保留模板方法。但"按交易日拆""按股票拆"这类可替换的步骤，改成注入的策略对象（规划器），就不用为每种拆法写一个子类。

### 10. 命令：把"一次调用"变成一个对象或一条数据

- 项目里：`{"name": "daily_kline", "params": {...}}`。有了它，这次调用就可以排队、存进数据库（采集方案、采集历史）、重试、定时触发，也可以通过 HTTP 或 Agent 发过来。
- 意义：这是"按名调用第一层统一入口"背后的模式。你的采集方案项、`collect_tasks` 表其实已经是命令的持久化形式。

## 三、这个方案里各层用什么

| 层 / 位置                   | 主要模式              | 作用                                             |
| :-------------------------- | :-------------------- | :----------------------------------------------- |
| Provider（第三层）          | 适配器                | 把各家 SDK 转成统一契约                          |
| 选择数据源                  | 策略 + 责任链         | 指定数据源就用它，不指定就按优先级尝试、失败切换 |
| 注册中心                    | 注册表式工厂          | 新增数据源只需注册，不改已有代码                 |
| `DataGateway`（第一层入口） | 门面 + 命令           | 按"名字 + 参数"统一调用                          |
| 限流 / 重试 / 缓存 / 统计   | 装饰器（中间件链）    | 横切逻辑只写一处                                 |
| 采集入库流程                | 模板方法 + 注入的策略 | 骨架固定，单元规划、增量判断、落库可替换         |
| 采集方案 / 定时 / Agent     | 命令                  | 调用可存储、可排队、可重放                       |

如果只能记一句：用适配器统一接口，用策略选实现，用工厂注册实现；其他模式都是在这个骨架外面加功能或加入口。

## 四、避免的坑

- 不要用单例类（类里写 `_instance`）。用注册表管理实例的生命周期，测试时更容易替换。
- 不要用抽象工厂按厂商成套切换，理由见上文。
- 不要用一条很深的继承链把"数据接口、实现、采集、缓存"串起来。继承最多两层，其他都用组合。不然一改基类，所有接口一起受影响，又会回到现在"乱"的状态。


也就是
  创建：采用注册表式工厂，
  结构：纵向结构采用适配器统一底层sdk、具体接口的横向结构用适配器模式修饰接口（限流、重试、缓存）
  行为：核心调用时命令模式，根据入参选择此次调用接口；后续重试等采用责任链

  表层用DataGateway约束简化门面对吗
