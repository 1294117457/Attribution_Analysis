### Q5 · 🟡 `stop_on_fail` 的中断条件要不要加失败率阈值？

**背景**（`02` §2.4）：现在 `stop_on_fail` 几乎不生效，因为
`_decide_status` 只在"一个都没成功"时返回 `failed`。

```475:479:D:\codes\Attribution_Analysis\backend\src\infrastructure\adapter\scheduler\collect\base.py
def _decide_status(summary: TaskSummary) -> str:
    """根据 summary 决定最终 status（兼容既有"部分失败也算成功"的语义）"""
    if summary.success == 0 and summary.fail > 0:
        return "failed"
    return "success"
```

**这意味着**：`stock_basic` 跑 5000 个股票，失败 4900 成功 100 →
`status=success` → **链条不中断** → 接着跑 `daily_kline` 4900 个必然失败的单元。

| 方案 | 判断条件 | 说明 |
|------|---------|------|
| **A. 只拦"完全失败"**（`03` §5.4 的默认写法） | `status in (failed, cancelled)` 或 `success_count == 0 and fail_count > 0` | 改动最小；对"4900 失败 / 100 成功"仍不中断 |
| **B. 加失败率阈值字段** | `collect_plans` 加 `fail_rate_threshold: float`（默认 1.0）<br>中断条件：`fail_count / (success+fail) > 阈值` | 可配；默认 1.0 = 等价于 A；调到 0.1 就是"失败超 10% 中断" |
| C. 不改 | 保持只看 `status` | 等于没修 |

**我建议 B，但默认阈值设 1.0**（等价于 A，行为不变），
这样你需要时可以在 UI 上调，不用改代码。

**需你确认**：A / B / C？选 B 的话字段名用 `fail_rate_threshold` 还是别的？

### Q7 · 🟡 定频下限设多少？

**我的建议**：30 秒。

**依据**：`fin_top10_floatholders` 实测 5572 个单元要跑 1.5 小时。
间隔设成 10 秒或 60 秒，都会出现"任务永远跑不完、每次触发都跳过"的情况。

| 选项 | 效果 |
|------|------|
| 30 秒 | 能覆盖"分钟级补数"需求，挡住明显不合理的配置 |
| 60 秒 | 更保守，适合只有 Tushare 配额的数据源 |
| 不设下限 | ❌ 不推荐，容易被误配置打爆数据源 |

**你有 Tushare 的调用频次限制认知吗？** 如果每分钟有硬性上限，下限应该设 60 秒。

**需你确认**：30 秒还是 60 秒？

### Q8 · 🟡 定时模式是否要支持"工作日"？

| 方案 | 行为 | 代价 |
|------|------|------|
| **A. 纯每日**（当前设计） | `09:30` = 每天 9:30，周末也跑 | 非交易日会拉到空数据（多数接口返回空 list，任务标 success + skip，**不报错但浪费调用**） |

**我建议先做 A**，因为：
- 你明确说了"仅交易日暂时不要"
- 非交易日多数接口返回空，走 `skipped` 分支，不会污染数据：


**需你确认**：如果希望周末别跑，我加一个独立的"仅工作日"开关（B）。
