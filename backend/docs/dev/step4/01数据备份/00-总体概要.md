## 0. TL;DR（一分钟看完）

| 项 | 选型 | Why |
|---|---|---|
| 备份文件格式 | **纯 SQL 文本（`.sql`）** | 人类可读、与项目迁移风格一致、跨 PG 版本 |
| 渲染方式 | **SQLAlchemy `CreateTable` + `INSERT` 渲染** | **不调 `pg_dump.exe`**，避 Windows 路径坑 |
| 数据写入 | **PostgreSQL `COPY FROM stdin`** | 比 `INSERT` 快 10-20 倍，**10 万行/秒** |
| 备份粒度 | **schema-only / data-only / full** | 三种场景覆盖 |
| 表选择 | **全表 / 多选子集** | 全表一键 + 选表灵活 |
| 备份路径 | **前端配置 + 后端 ENV 双层** | 前端传 `output_dir`；后端用 `BACKUP_DIR` 环境变量兜底 |
| 导入方式 | **全量覆盖 / 增量（已存在则跳过）** | 两档覆盖恢复场景 |
| 导入路径 | 同上，前后端均支持 `input_dir` 或上传文件 | |
| 异步执行 | **后台 `asyncio.create_task`** + 前端轮询 | 大表不阻塞 API |
| 鉴权 | `system:backup` 权限 | 仅管理员可操作 |
| 数据库 | **复用现有 PostgreSQL**，新增 2 张 `sys_*` 表 | |
| 现有代码改动 | **后端 14 新增 + 4 修改 / 前端 10 新增 + 2 修改** | 最小侵入，DDD 分层完全合规 |
| DDD 合规 | 基础设施层直接 `datetime.now()`（v1 业务简单，不拆 ClockPort）；路径策略直接 PathResolver 单类（v1 单实现，不拆 Protocol）| |
| 前端规范 | 严格遵循 [`frontend/docs/page-development-guide.md`](../../../../frontend/docs/page-development-guide.md)：`<PageWrapper>` + 4 密度锚点 + `bkup-` 前缀 + `colW(px)` 列宽 | 不破坏全局密度方案 |

## 1. 设计原则

1. **贴合现有 DDD 分层**：`route → application → infrastructure`，与 `stock / pool / kline / auth` 模块一致。**严格遵循 `backend/docs/config/DDD.md`**，特别是：
   - DTO 放 `route/dto/{request,response}/`（不在 application 层）
   - 时钟/路径策略通过 `application/port/` 接口 → `infrastructure/adapter/` 实现
   - Adapter 层只放"外部 SDK/命令适配"，不写业务规则
2. **复用现有基础设施**：PostgreSQL、AsyncSession、NullPool、TimestampMixin、_response 统一响应、register_exception_handlers、bcrypt 鉴权 Depends。
3. **复用前端基础设施**：Pinia、Element Plus、PageWrapper、LeftBar、TopBar、Vue Router、axios 拦截器。**严格遵循 `frontend/docs/page-development-guide.md`**：每个页面用 PageWrapper + 4 密度锚点 + `bkup-` 前缀。
4. **路径双层配置**：前端运行时可在 UI 上改路径；后端 ENV 是部署兜底，前端没传时用 ENV。
5. **不调 `pg_dump.exe`**：纯 Python 渲染 SQL + `COPY FROM stdin`，避免 Windows 路径和 PG 版本依赖。
6. **高危操作二次确认**：恢复（覆盖）是破坏性操作，UI 弹窗 + 服务端强校验 `confirm=True`。**v1 不做自动 pre-restore 备份**（v2 再加）。
7. **单一职责**：backup 模块只管"导出/导入数据库内容"；不耦合采集、不耦合权限体系。

## 4. 关键决策 FAQ

| 问 | 答 |
|---|---|
| 为什么不用 `pg_dump`？ | `pg_dump.exe` 在 Windows 部署路径坑多；不同 PG 版本生成的 `.dump` 不兼容；且与项目 SQLAlchemy 风格不一致 |
| 为什么用纯 SQL 而不是 `.dump` 二进制？ | 人类可读、git 友好、`psql -f` 一行恢复、跨 PG 大版本兼容；性能损失对当前规模（< 100 万行）可接受 |
| 为什么不接 Alembic？ | 用户决定不引入；本方案不依赖 |
| 备份含 `sys_*` 表吗？ | **含**。备份是"整库快照"，必须含 `sys_users / sys_roles / sys_permissions / sys_backup_records` 等 |
| 备份含 `sys_collect_tasks` 吗？ | **含**。但恢复时清空 `running` 状态（同 main.py `_migrate_sys_collect_tasks` 逻辑） |
| 恢复覆盖了正在跑的采集怎么办？ | 恢复成功后清 `sys_collect_tasks` 全部 `running` 记录；采集端用 polling 不会死锁 |
| 恢复是事务内吗？ | **是**。单事务内 `DROP+CREATE+COPY`，失败回滚；不部分成功 |
| 增量模式怎么定义"已存在"？ | 以**主键**判断。`INSERT ... ON CONFLICT (pk) DO NOTHING` |
| 增量模式会不会产生孤儿？ | **会**。删表不删记录的场景下会留孤儿（用户须知） |
| 备份要不要加密？ | **不加密**。本地运维工具，文件落在 `backups/` 目录；如需加密走 OS 层（EFS / BitLocker）|
| 备份要不要压缩？ | **不内建**。gzip 交给 OS 或用户；备份文件 50MB 量级不构成压力 |
| 前端传的路径要不要做安全校验？ | **必须**。禁止绝对路径遍历、禁止写入 `backend/src/`、禁止符号链接到系统目录 |
| 异步任务怎么持久化？ | 写入 `sys_backup_records.status`；进程重启后 `running` 视为"中断"标记为 `interrupted` |
| 多用户并发备份会冲突吗？ | **不会**。每个任务有唯一 `id`，文件名带 UUID；输出路径同但文件名不同 |
| 备份目录要不要自动清理？ | **不自动**。但提供"手动清理 > 30 天"按钮（v2） |

## 5. 路径策略（关键设计）

### 5.1 路径来源优先级

```
请求里的 output_dir / input_dir
        │
        │  若为空/未传
        ▼
后端 ENV 变量 BACKUP_DIR（默认 backend/backups/）
        │
        │  若也未配置
        ▼
代码兜底 default_backup_dir = backend/backups/
```

### 5.2 路径安全校验（白名单）

```python
ALLOWED_ROOTS = [
    Path("/data/backups"),                  # Linux 服务器
    Path("D:/codes/Attribution_Analysis/backend/backups"),  # Windows 本地
    # 前端可追加白名单路径（通过 /backups/config 修改）
]

def validate_path(p: str, mode: "read" | "write") -> Path:
    abs_p = Path(p).resolve()
    # 1. 必须在某个白名单根下
    if not any(_is_under(abs_p, root) for root in ALLOWED_ROOTS):
        raise PathSecurityError(...)
    # 2. 写模式：禁止写入 backend/src/, backend/migrations/
    if mode == "write":
        forbidden = ("/src/", "/migrations/", "/.git/", "/.keys/")
        if any(str(abs_p).replace("\\", "/").endswith(f.rstrip("/")) or f in str(abs_p) for f in forbidden):
            raise PathSecurityError(...)
    # 3. 禁止符号链接穿透
    if abs_p.is_symlink():
        raise PathSecurityError(...)
    return abs_p
```

### 5.3 前端路径配置持久化

```typescript
// stores/backup.ts
const pathConfig = ref({
  outputDir: "",   // 留空 = 用后端 ENV
  inputDir: "",
})
// 持久化到 localStorage（按用户独立）
watch(pathConfig, v => localStorage.setItem('backup.path', JSON.stringify(v)), {deep: true})
```

## 7. 一句话总结

**SQL 渲染 + COPY 写入 + 异步轮询 + 路径白名单 + 全量/增量两种恢复模式。**

后端做"引擎 + 异步任务 + 路径安全"，前端做"向导式 UI + 路径配置 + 进度轮询"，不依赖 Alembic、不调 `pg_dump`、不影响 `main.py` 启动流程。
