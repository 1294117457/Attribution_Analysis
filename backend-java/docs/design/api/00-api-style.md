# 00 · 接口风格总纲

> 本文档是 attribution-analysis 后端 API 设计的总纲。  
> 后续 `01-path-naming.md` / `02-page-vo.md` / `03-api-response.md` 是本总纲在三个维度上的展开。

---

## 1. 设计目标

后端 API 设计需要同时满足 **4 类诉求**：

| 诉求维度         | 面向场景                       | 本套规范的对策                  |
| ---------------- | ------------------------------ | ------------------------------- |
| **可读性**       | 前端联调、二次开发、自测联调   | 路径语义清晰、动词标准化        |
| **可缓存**       | 未来上 CDN / 反向代理 / 多级缓存 | 读操作用 GET，URL 自带 key      |
| **工具链兼容**   | Swagger / SpringDoc / 网关 / 监控 | 遵循 RESTful + HTTP 语义标准   |
| **业务可演进**   | 批量导入、异步任务、进度查询    | 动作型资源以独立路径暴露        |

---

## 2. 风格选型：纯 REST

本系统全部接口采用 **REST 风格 + HTTP 语义方法**，**不采用**以下风格：

| 风格                | 是否采用 | 不采用的原因                               |
| ------------------- | -------- | ------------------------------------------ |
| **纯 RPC（POST 全包）** | ❌       | POST 默认不可缓存，无法上 CDN/网关边缘缓存     |
| **REST + RPC 混合**  | ❌       | 团队认知成本高，OpenAPI 自动生成客户端代码易混乱 |
| **GraphQL / tRPC**   | ❌       | 当前业务无强定制字段需求，引入收益小于复杂度   |

## 3. 总体原则

### 3.1 路径三段式

```
/{module}/{resource}[/{id}][/{sub-resource}][?queryParams]
```

- **module**：业务模块前缀
- **resource**：资源名（复数优先，名词）
- **{id}**：资源主键（路径参数）
- **{sub-resource}**：子资源（仅在业务主键必须组合时使用）

详细规则见 `01-path-naming.md`。

### 3.2 动词统一交给 HTTP 方法

| HTTP 方法 | 语义       | 是否可缓存 | 本系统的使用场景                   |
| --------- | ---------- | ---------- | --------------------------------- |
| GET       | 查 / 列举  | ✅ 是       | 读操作（含统计、进度查询、导出触发以外的"读"） |
| POST      | 创建 / 动作 | ❌ 否       | 增、触发异步任务、批量操作         |
| PUT       | 全量更新   | ❌ 否       | 改（整资源替换）                   |
| PATCH     | 部分更新   | ❌ 否       | 改（局部字段）                     |
| DELETE    | 删除       | ❌ 否       | 删                                 |

> 🔑 **关键约定**  
> 查询类操作 **必须** 用 GET（包括"导入进度查询""同步状态查询"这些"读"语义）。  
> 一旦允许"查询用 POST"，CDN 缓存 key 就无法构造，未来上 CDN 必须重写大量接口。

### 3.3 路径扁平化

**默认**不使用两层及以上嵌套路径。  
"父子资源"通过业务字段直接定位，或下沉为独立的虚拟资源。

详见 `01-path-naming.md` 第 4 节"避免两层 id 的业务扁平化"。

### 3.4 响应统一封装

业务层接口 **必须** 返回统一封装结构：

```json
{
  "code": 0,
  "data": { ... },
  "msg": "ok"
}
```

详细字段约定、HTTP 状态码映射、业务错误码定义见 `03-api-response.md`。

### 3.5 列表分页统一

所有**列表查询接口**必须返回统一分页结构：

```json
{
  "code": 0,
  "data": {
    "total": 123,
    "page": 1,
    "pageSize": 20,
    "dataList": [ ... ]
  },
  "msg": "ok"
}
```

字段定义、Spring 接口写法、SQL 限制见 `02-page-vo.md`。

## 5. 评审 checklist

在评审本套规范时，按以下顺序检查：

- [ ] **风格选型**（第 2 节）：纯 REST 是符合预期
- [ ] **路径三段式**（第 3.1 节）：模块前缀、命名风格接受
- [ ] **HTTP 方法统一**（第 3.2 节）：查询全部用 GET 是符合预期
- [ ] **路径扁平化**（第 3.3 节）：避免两层 id 的规则接受
- [ ] **响应封装**（第 3.4 节）：`[code, data, msg]` 形式接受
- [ ] **分页统一**（第 3.5 节）：`PageVO` 字段（`total` / `page` / `pageSize` / `dataList`）接受
