### 3.4 索引

PostgreSQL `ALTER TABLE ... RENAME TO ...` **不**自动改索引名（索引与表一起搬过来，名字保留）。应用层不再依赖索引名，无须改。

### 3.5 字段名一致性（最大的风险）

**核心要求**：
- RENAME 之前的列名（如 `cap_moneyflow` 表里的 `ts_code` / `trade_date` / `buy_sm_vol`）必须与 Tushare 适配器返回的 dict 键名一致
- 读侧代码 `text('SELECT * FROM capital_moneyflow')` 返回的 dict 键名 = 列名 = 适配器输出

> **决策：列名不动**。RENAME 只改表名，不改列名。详见 [`10-分库与表结构.md §5`](10-分库与表结构.md)。

如果建表时列名用了 camelCase / 复数，必须在 D4 之前 `ALTER TABLE` 改成 snake_case 单数。

## 4. 读侧代码改写（D4 / D5）

`route/api/v1/data_board.py` 现在 14 个查询全部走 `select(XxxDB)`。改写原则：

| 旧 | 新 |
| :-- | :-- |
| `select(CapMoneyflowDB).where(...)` | `query_raw_table("capital_moneyflow", filters={...})` |
| ORM 模型属性访问 | 返回 `dict`（键名=列名） |
| 序列化到 BO | 直接 `dict` 返回（与之前 BO 序列化结果**字段名一致**） |

> ⚠️ **字段名一致性是这次改写最大的风险**。逐字段对比：ORM `CapMoneyflowDB.ts_code` → SQL 列 `ts_code` → dict key `ts_code` → JSON `ts_code`。只要建表时列名 = 适配器输出键名，**响应零变化**。

## 8. 风险与缓解

| 风险 | 缓解 |
| :-- | :-- |
| DDL `RENAME TABLE` 时阻塞读 | 选低峰；D2 阶段先把读侧切到新表，旧表查询不再被使用后 RENAME 几乎瞬时 |
| `pg_dump` 跨库数据丢失 | 显式 `-t 表名` 列表；`pg_dump --section=pre-data --section=data --section=post-data` 分段；导入后 `SELECT COUNT(*)` 对比 |
| 字段名漂移（ORM 列名 vs adapter 输出） | D4 之前 grep 一次 RENAME 前列名与适配器输出列名；不一致就 ALTER 改列名 |
| 14 套 `XxxItem` BO 被 `concept_reason` 等任务间接 import | D4 之前 grep 一次 `XxxItem` import；落单后再删 |
| `SqlRawDataStore` 删除后 `RawDataStorePort` 实现没人接 | D2 阶段已上线 `DynamicRawDataStore`；D3 已在 `CollectContext` 注入；D5 仅是删除旧实现，不影响接口 |
| 用户选错表（缺列） | 采集时 `resolve_table_schema` + `validate_row_fields` 校验失败，任务 fail 不写盘 |
| **跨库事务失败** | 采集 job 写 `attribution_db` 与 raw 写 `raw_data_db` 不在同事务，job 状态延迟几毫秒可接受；job fail 时 raw 试运行行仍在表里（接受） |
| **DROP TABLE attribution_db.X 后发现要回滚** | 30 天内保留 `pg_dump` 归档；恢复命令 `psql attribution_db < dumpfile.sql` |
