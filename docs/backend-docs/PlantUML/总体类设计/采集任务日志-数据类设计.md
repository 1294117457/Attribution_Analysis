# 采集任务日志 — 数据类设计

> 对应 UML 类图：`02_collect_task_log.puml`

## 一、设计目标

为所有数据采集操作提供统一的任务记录和日志追踪能力：
- 记录每次采集的参数、进度、结果
- 支持手动触发和后续定时任务两种来源
- 一张主表适配所有数据类型（日K、估值、基本信息、财报等）
- 配合 Redis 提供实时进度查询，避免频繁写库

## 二、表结构

### 2.1 主表：`sys_collect_tasks`

| 字段 | 类型 | 约束 | 说明 |
|:---|:---|:---|:---|
| `id` | BIGSERIAL | PK | 自增主键 |
| `task_type` | VARCHAR(32) | NOT NULL, INDEX | 采集类型 |
| `trigger_type` | VARCHAR(16) | NOT NULL, DEFAULT 'manual' | 触发方式 manual/schedule |
| `params` | JSONB | NULLABLE | 任务参数（不同类型格式不同） |
| `status` | VARCHAR(16) | NOT NULL, DEFAULT 'pending' | pending/running/success/failed/cancelled |
| `total_count` | INT | DEFAULT 0 | 总任务数 |
| `success_count` | INT | DEFAULT 0 | 成功数 |
| `fail_count` | INT | DEFAULT 0 | 失败数 |
| `skip_count` | INT | DEFAULT 0 | 跳过数 |
| `started_at` | TIMESTAMPTZ | NULLABLE | 开始时间 |
| `finished_at` | TIMESTAMPTZ | NULLABLE | 结束时间 |
| `duration_ms` | INT | NULLABLE | 总耗时（毫秒） |
| `message` | TEXT | NULLABLE | 完成摘要/错误概述 |
| `created_at` | TIMESTAMPTZ | DEFAULT NOW() | 创建时间 |
| `updated_at` | TIMESTAMPTZ | DEFAULT NOW() | 更新时间 |

**索引：**
- `ix_sys_collect_tasks_type_time` ON (task_type, started_at DESC) — 按类型查历史记录
- `ix_sys_collect_tasks_status` ON (status) WHERE status = 'running' — 快速判断是否有运行中任务

### 2.2 明细表：`sys_collect_task_details`（可选，全量采集时使用）

| 字段 | 类型 | 约束 | 说明 |
|:---|:---|:---|:---|
| `id` | BIGSERIAL | PK | 自增主键 |
| `task_id` | BIGINT | FK → sys_collect_tasks, INDEX | 所属任务 |
| `symbol` | VARCHAR(10) | NOT NULL | 股票代码 |
| `status` | VARCHAR(16) | NOT NULL | success/failed/skipped |
| `saved_count` | INT | DEFAULT 0 | 本次存入条数 |
| `error_message` | TEXT | NULLABLE | 失败原因 |
| `duration_ms` | INT | NULLABLE | 单只耗时 |
| `created_at` | TIMESTAMPTZ | DEFAULT NOW() | 记录时间 |

**索引：**
- `ix_sys_collect_task_details_task` ON (task_id) — 按任务查明细

## 三、task_type 枚举定义

| 值 | 说明 | params 示例 |
|:---|:---|:---|
| `daily_kline` | 日K线 | `{"days": 7}` 或 `{"start_date": "20260101", "end_date": "20260918"}` |
| `daily_basic` | 日频估值（PE/市值等） | `{"trade_date": "20260918", "days": 3}` |
| `stock_basic` | 股票基本信息同步 | `{"list_status": "L"}` |
| `fin_report` | 财务报表 | `{"period": "20260630"}` |
| `moneyflow` | 资金流向 | `{"trade_date": "20260918"}` |
| `margin` | 融资融券 | `{"exchange_id": "SSE", "trade_date": "20260918"}` |

## 四、Redis 实时进度方案

PostgreSQL 负责**持久化**，Redis 负责**实时进度**（前端高频轮询场景）。

### Key 设计

```
collect:progress:{task_id}  →  Hash
```

| Field | 说明 |
|:---|:---|
| `total` | 总数 |
| `done` | 已完成 |
| `success` | 成功数 |
| `fail` | 失败数 |
| `skip` | 跳过数 |
| `status` | 当前状态 |
| `current` | 正在处理的 symbol |
| `started_at` | 开始时间 (ISO) |

**TTL：24小时**，任务结束后自动过期。

### 数据流

```
1. 前端点击"采集日K"
2. 后端创建 sys_collect_tasks 记录 (status=running)
3. 后端在 Redis 写入 collect:progress:{task_id}
4. BackgroundTask 循环采集，每处理一只更新 Redis Hash
5. 前端每 3s GET /collect/tasks/{id}/progress → 后端读 Redis 返回
6. 采集完成 → 更新 PostgreSQL 主表 (status/counts/finished_at)
7. 如需明细 → 批量写入 sys_collect_task_details
8. Redis key 24h 后自动过期
```

## 五、与现有 collect/all 的对接

当前 `kline.py` 中的 `_collect_all_running` 全局变量和 `_collect_all_progress` dict 将被替换为：
- 创建 `sys_collect_tasks` 记录获得 `task_id`
- 进度写入 Redis `collect:progress:{task_id}`
- 完成后更新 PostgreSQL
- 前端通过 `task_id` 查询进度，支持多任务并存的历史记录

## 六、扩展性说明

1. **新增采集类型**：只需在 `task_type` 枚举新增值，无需新建表
2. **定时任务**：`trigger_type='schedule'`，后续接入 APScheduler 或 Celery Beat 时自动标记来源
3. **重试**：可根据 `status='failed'` 的任务重新发起，参数从 `params` 字段恢复
4. **清理策略**：按 `created_at` 保留最近 N 天/条记录，过老的自动清理
