阶段1，快速落地
    最早是利用ai快速落地mvp,架构杂乱，模型设计混乱，字段不清晰
    能快速调用底层sdk,查询数据，入库;进而实现基本业务功能
    问题有不方便长期使用，结构不清晰难以维护，设计散乱定时任务和后续比如监控数据不好设计
阶段2,复杂设计逻辑
    采用python的protocol契约语法来实现多源切换（tushare/adata）
    将所有fetcher在后端服务启动时注册到进程内存中，并且返回可用的数据fetcher
    gateway+指令的设计模式，统一Fetcher一个基类，派生多个fetcher，并通过指令模式指定调用哪个数据类型fetcehr和数据源source
    
    优点：多设计模式组合，使用灵活
    缺点：过度设计，内部fetcher,source,和service过度耦合，使用灵活但是，还是难以维护

阶段3，建模入库配置花
    将每个外部接口抽象建模data_port，设计核心字段：调用必须参数pamars，source数据源选择加上基本字段facet,name等，入库配置话
    设计一个fetcher引擎，调用时根据选定data_port对应的source、parmas和name参数调用对应sdk的对应方法

    优点：每个接口新增时都只需要在data_port中新增一条记录;并且无方案2注册到进程内存的糟糕设计;且接口层、业务层代码极其精简
    缺点：持久化存在明显问题，数据表得提前建立（这个还好），
        重点是如果持久化用repo层编写对应入库代码，每个data_port和对应repo代码关联又需额外字段
        曾尝试增加一个output_params字段，定义data_port采集数据返回参，然后用Sqlalchemy映射关系来创建ORM模型建表，但是这样不安全
阶段4,最终阶段
    核心是：底层sdk配置后，所有需要的数据类型（约28个），配置对应：
        28个fetcher--28个service--28个repo--28个interface
    service中增加metadata元数据，给前端采集管理页面生成当前已实现采集接口的ui
    按功能fetcher分三类：
        增量采集（日k，数据量多且有分析价值），全量覆盖（股票基本信息，变化不大），实时查询（分k，变化大）
    service底层有taskRunner:
        每个采集服务调用采集功能时，都是派发taskrunner去采集数据
        service层处理日志创建、数据处理、入库
        日志监控taskrunner进度，更新redis,采集结束入库

阶段5,去掉taskRunner
    collect 方法（HTTP 入口）：
        接收前端参数
        创建协程后台运行
        返回给前端"采集任务创建成功"
    run_collect 方法（后台采集）：
        自己构造 dbsession
        自己构造其他服务（log_service、stock_basic 等）
        创建日志
        采集数据
        监控进度并更新 Redis
        数据入库
        采集完成后更新日志的数据库状态
