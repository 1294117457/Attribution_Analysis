### 2.4 🟡 `stop_on_fail` 的判断条件不生效（吸收 groups 时要顺手修）

    """根据 summary 决定最终 status（兼容既有"部分失败也算成功"的语义）"""

### 2.5 🟡 时间点列表无法用 cron 表达（这是改造的核心原因之一）

**cron 的小时列表和分钟列表是笛卡尔积，不是配对关系。**

假设你想每天 `09:30` 和 `15:00` 采集，转成 cron：

| 步骤 | 结果 |
|------|------|
| 合并小时 + 分钟 | `30 9,15 * * *` |
| 该表达式实际触发 | 09:30、**09:00**、15:30、**15:00** |
| 多出来的 | 09:00、15:30 ← 错误 |

只要选的几个时间点里**分钟数不全相同**，转 cron 必然失真。
APScheduler 的 `CronTrigger(hour=..., minute=...)` 同理。

**所以必须单独存结构化的时间点列表，不能复用 cron 列。**

### 2.6 🟡 一个接口只能配一个方案

`task_type` 有 unique 约束。无法实现"同一接口早上采一次、收盘后再采一次，且用不同参数"。

**本次重构的 `collect_plan_items` 正好解决这个**（见 `01-四层职责边界.md` §6.3）。

## 5. 技术栈约束

| 约束 | 说明 | 影响 |
|------|------|------|
| **没有 alembic** | 建表/改表全靠 `main.py` 里手写 SQL | 新表靠 `create_all`；删表重建靠手写 `DROP TABLE` |
| **DB 是远程共享库** | `8.148.204.54`，不是本地 | 破坏性操作不可逆 —— **本次已确认接受**（无有效数据） |
| **APScheduler 单进程** | `AsyncIOScheduler`，job 存在内存 | 重启后从 DB 重建，符合预期 |
| **热重载会取消任务** | uvicorn reload → `cancel_background()` | 改后端文件会杀掉在跑的采集 |
| **Pydantic 数组字段无 DB 校验** | `times` 存 JSON list | 格式校验必须在 service 层做 |
| **`create_all` 不改已存在的表** | 遇到已存在的表直接跳过 | ⚠️ **删表必须在 `create_all` 之前**，否则表建了又被删 |

`DROP TABLE IF EXISTS` 和 `ADD COLUMN IF NOT EXISTS` 都是幂等的，迁移函数本身安全。
问题只在于破坏性操作会真删数据。

**唯一需要谨慎操作的是 `sys_collect_tasks`**：这张表有真实任务历史，
`group_run_id` → `plan_run_id` 用 `RENAME COLUMN` 而非删表（**数据保留**）。见 `03` §7.6。

## 7. 结构探测：`information_schema`

删表重建的幂等性靠探测表结构，不靠"是否执行过"的标记：

```python
probe = await conn.execute(text("""
    SELECT column_name FROM information_schema.columns
    WHERE table_name = 'collect_plans'
"""))
cols = {r[0] for r in probe.fetchall()}
if {"name", "schedule_type"} <= cols and "task_type" not in cols:
    return   # 已是新结构
```

**为什么不建一张 `schema_version` 表**：
项目现在没有迁移框架（无 alembic），单独为这一处建版本表属于过度设计。
而且探测式判断更健壮——即使 `schema_version` 表本身被误删，
探测逻辑仍然正确；反之如果探测逻辑有 bug，版本表会误判成"已迁移"而永不执行。
