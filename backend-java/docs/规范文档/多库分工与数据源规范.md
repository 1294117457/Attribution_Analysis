---

## 0. 一句话结论

> **Java 端用「双数据源 + `@DS("raw")` 路由」，Collector 端用「双 engine + 双 session_factory + 双 ORM Base」。**
> **两侧的判据完全一致：这张表属于哪个库，就用哪个库的连接。**
> **任何一条 SQL 语句只允许涉及一个库；跨库关联一律拆成多次查询 + Service 层内存 join。**

## 1. 方案选型（已定）

### 1.1 三个候选与最终结论

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. postgres_fdw 外表** | attribution 库建 FDW server + `IMPORT FOREIGN SCHEMA`，Java 单数据源读 `raw.*` | ⚠️ **备选，不用** |
| **B. 双数据源 + `@DS`** | Spring `dynamic-datasource`，采集表 Mapper 标 `@DS("raw")` | ✅ **采用** |
| **C. 应用层 join** | 先查业务库，再查 raw 库，内存拼 | ✅ **是 B 的配套模式，不是独立方案** |

### 1.2 为什么选 B 而不是 A

**硬证据：现有 4 个 XML Mapper 中，没有任何一条 SQL 语句同时涉及两个库的表。**

|---|---|---|
| `StockInfoMapper.xml` | `stock_pool_members` + `stock_pools` | **attribution** |
| | `fundamental_concept_member` + `fundamental_concept` | **raw_data** |
| | `fundamental_daily_basic` / `fundamental_report` / `tech_kline_daily` | **raw_data** |
| `PoolMemberMapper.xml` | `stock_pool_members` | attribution |
| `ConceptMapper.xml` | `fundamental_concept_member` + `fundamental_concept` + `fundamental_stock_info` + `fundamental_daily_basic` | **全 raw_data** |
| `ConceptMemberMapper.xml` | `stock_pool_members` + `stock_pools` | **attribution** |

### 1.3 不用 A（FDW）的三个理由

| 理由 | 说明 |
|---|---|
| **FDW 会诱导跨库 JOIN** | 一旦外表就位，开发者很自然会写 `JOIN raw.tech_kline_daily`。FDW 的 JOIN 下推能力有限（PG 12+ 有部分下推，但 CTE / 聚合 / 标量子查询仍会拉全量回本地）。`selectStockStats` 那种带 CTE + `MAX(trade_date)` 标量子查询的 SQL 走 FDW 会非常慢 —— **性能是静默劣化，不是报错** |
| **两个库在同一个 PG 实例、同一个 owner** | 实测 `attribution` / `raw_data` 均 owned by `zhouch`，同 host `8.148.204.54:5432`。FDW 是「跨服务器」场景的方案，这里属于过度设计 —— 直接两个数据源连同一个实例的两个库更直接 |
| **引入额外运维面** | 要建 extension / server / user mapping（**含明文密码**）/ schema，还要处理 `IMPORT FOREIGN SCHEMA` 的静态快照问题（raw 库加表必须重新 IMPORT） |

### 1.4 A 方案何时才适用

> **当且仅当：两个库在不同的 PG 服务器上，且确实需要频繁的跨库 JOIN。**

本项目不满足。若未来满足，届时按 A 方案实施，并**同步废止** B 方案（不可并存）。


> ⚠️ **原 `spring.datasource.url` 配置必须删除或改造**。`dynamic-datasource` 会接管 `spring.datasource`，若同时存在单数据源配置会冲突。

### 3.3 `strict: true` —— 最关键的一条

> **`strict: true` 是本方案的安全底线。**

开启后，若某个 Mapper **没有标 `@DS`** 却访问了 raw_data 的表，会**明确报错**（类似 `can not find a datasource for [raw_data]`），而不是静默连到业务库然后报「表不存在」。

这正好挡住了 Collector 那边同一个坑：

| | 现状（无 strict） | 加 strict 后 |
|---|---|---|
| 忘标 `@DS` | 连到 attribution 库 → `relation "tech_kline_daily" does not exist` | `can not find datasource` → **启动/首次调用即失败，错误信息直接指向根因** |

**必须开启。** 任何「靠报错发现配错」的方案都不合格。

### 3.4 `@DS` 标注规则

#### 规则 1：标在 **Mapper 接口**上，不是 Service 上

```java
// ✅ 正确：标在 Mapper
@Mapper
@DS("raw")
public interface TechKlineMapper extends BaseMapper<TechKlinePO> {
}
```

```java
// ❌ 错误：标在 Service
@DS("raw")
@Service
public class KlineServiceImpl { ... }
```

原因：`dynamic-datasource` 通过 AOP 代理在**方法调用时**切换 ThreadLocal 中的数据源上下文。

| 标错位置 | 后果 |
|---|---|
| 标 Service 上，同一 Service 内先调 raw Mapper 再调 biz Mapper | 切换时机取决于代理织入顺序，可能连错库 |
| 标 Service 上，但 Mapper 被别的 Service 复用 | 复用方拿不到该上下文 |
| **标 Mapper 上** | ✅ 每次调用该 Mapper 的方法，切换都精确发生 |

#### 规则 2：一个 Mapper 只能对应一个库

> **一个 Mapper 接口 = 一张表 = 一个库。**

**违反这条会导致 `@DS` 无效或报错**（`@DS` 是接口级注解，一个接口无法同时指定两个数据源）。

#### 规则 3：跨库查询必须**拆 Mapper**

**当前有 2 个 Mapper 违反规则 1/2，必须拆分**：

| Mapper | Base 表（库） | 违规方法 | 涉及库 |
|---|---|---|---|
| `StockInfoMapper`（market 模块） | `fundamental_stock_info`（raw） | `selectPoolMemberships` / `selectPoolMembershipsBySymbol` | **attribution**（`stock_pool_members` + `stock_pools`） |
| `ConceptMemberMapper`（concept 模块） | `fundamental_concept_member`（raw） | `selectPoolMemberships` | **attribution**（`stock_pool_members` + `stock_pools`） |

**拆分方案（受模块依赖方向约束）**：

当前 Maven 依赖方向是：

```
attribution-common  ←  attribution-market  ←  attribution-user
                      ←  attribution-concept
```

即 **`attribution-user` 依赖 `attribution-market`**（`PoolServiceImpl` import 了 `com.attribution.market.service.StockInfoService`），**不是**反过来。而 `attribution-concept` **不依赖** `market`，也不依赖 `user`。

因此「把归属查询放到 `attribution-user`」会让 `attribution-concept` 需要新增对 `user` 的依赖 —— **可行但不必要**（会扩大依赖面）。

**推荐拆分方案**：

| 新增位置 | Mapper | 承载 | 理由 |
|---|---|---|---|
| `attribution-user/mapper/` | `PoolMembershipQueryMapper` | `stock_pool_members` + `stock_pools` 联查 | 语义归属最准（自选池是 user 领域） |
| `attribution-common` ❌ | — | 不放 | `common` 不该有 Mapper（它是 DTO/VO/异常/工具层） |

配套依赖调整：

```
attribution-concept  →  新增 dependency: attribution-user
attribution-market   →  新增 dependency: attribution-user
```

> ⚠️ **注意循环依赖风险**：`attribution-user` 已依赖 `attribution-market`。若让 `attribution-market` 再依赖 `attribution-user` → **直接循环，Maven 构建失败**。
>
> **必须先解耦**：`attribution-user` 对 `attribution-market` 的依赖，来源是 `PoolServiceImpl` 用 `StockInfoService` 查股票名 + `PoolConverter` 用 `StockBriefVO`。解耦方式二选一：
> - **选项 A（推荐）**：`StockInfoService` 的这处调用改为**直接注入 `StockInfoMapper`**（user 模块本来就该能查股票基础信息表），消除对 market 的 Service 依赖；`StockBriefVO` 移到 `attribution-common` 或在 user 侧定义等价 VO。
> - **选项 B**：`PoolMembershipQueryMapper` 放在 `attribution-market` 模块内（虽然语义上属于 user 领域），避免任何依赖调整。**改动最小，零依赖风险。**
>
> **落地建议：先做选项 B（把新 Mapper 放 `attribution-market`），把选项 A 的解耦作为独立重构任务。** 采集相关的双库改造不应该被模块依赖重构阻塞。

拆分后：

```
StockInfoMapper       删除 selectPoolMemberships / selectPoolMembershipsBySymbol 及其 XML 语句
ConceptMemberMapper   删除 selectPoolMemberships 及其 XML 语句
```

替换为调用新的 `PoolMembershipQueryMapper`（在 business 库，不标 `@DS`）。

#### 规则 4：默认数据源 = 业务库，`@DS("raw")` 是「例外」

好处：新增业务表时**不需要**任何标注，忘标注的后果最轻（而 `strict` + 表不存在会立刻暴露）。

### 3.5 XML Mapper 的数据源归属

XML 里的 SQL 由**所属 Mapper 接口**决定数据源，与 XML 文件所在目录无关。

```xml
<!-- attribution-market/src/main/resources/mapper/StockInfoMapper.xml -->
<mapper namespace="com.attribution.market.mapper.StockInfoMapper">
    <!-- 该 Mapper 标了 @DS("raw")，所以这里的 SQL 走 raw_data -->
    <select id="selectStockStats" ...>
        FROM tech_kline_daily ...
    </select>
</mapper>
```

**规范**：

| 规则 | 说明 |
|---|---|
| XML 的 namespace **必须**等于一个 Mapper 接口 | 由 MyBatis 绑定，间接决定数据源 |
| XML 所在模块 ≠ 数据源 | `StockInfoMapper.xml` 在 market 模块，但查的是 raw_data |
| **XML 内禁止跨库 JOIN** | 与 §2.1 铁律 5 一致 |

### 3.6 跨库关联的规范写法

**禁止**：

```xml
<!-- ❌ 禁止：一条 SQL 跨两个库 -->
<select id="selectStockWithPools">
    SELECT s.symbol, p.name
    FROM fundamental_stock_info s
    JOIN stock_pool_members m ON m.symbol = s.symbol   <!-- ← attribution 库 -->
    JOIN stock_pools p ON p.id = m.pool_id              <!-- ← attribution 库 -->
</select>
```

**正确：拆成两个 Mapper，Service 层内存 join**（现状已是此模式）：

```java
// attribution-user：查业务库
List<PoolMembershipRow> poolRows = poolMembershipQueryMapper.selectPoolMemberships(symbols);

// attribution-market：查 raw_data
List<StockInfoPO> stocks = stockInfoMapper.selectList(wrapper);

// Service 层按 symbol 拼装
Map<String, List<PoolMembershipVO>> poolsBySymbol = groupBy(poolRows);
```

### 3.7 事务与 `@DS` 的关系

| 场景 | 规则 |
|---|---|
| **单个 `@Transactional` 方法内只碰一个库** | ✅ 正常 |
| **单个 `@Transactional` 方法内要碰两个库** | ❌ **不允许**。`@DS` 是**方法级**切换，事务开始时数据源已锁定，方法内的 `@DS` 切换不生效 |
| 跨库写操作 | 拆成**两个独立事务**，业务库事务在外层、raw 库事务在内层（或反之，按失败补偿需求定） |
| **Java 不写 raw_data** | ✅ 所以 Java 侧实际**不存在**跨库事务需求 —— 只读场景，天然安全 |

> **重要简化**：因为 **Java 只读 raw_data、只写 attribution**，所以 Java 侧**永远不会有跨库事务**。`@DS` + `@Transactional` 的经典冲突在本项目不存在。

### 3.8 `@DS` 与 `@Transactional` 的注解顺序

当一个方法**同时**需要 `@DS` 和 `@Transactional`（只读业务库但要事务一致性时）：

```java
@Transactional(rollbackFor = Exception.class)
@DS("raw")            // ← @DS 在外层，优先级更高
public void doSomething() { ... }
```

`dynamic-datasource` 通过 `DatasourceAspect` 的 `Ordered.HIGHEST_PRECEDENCE` 切数据源，必须**在事务开启之前**切好。

> 但按 §3.7，本项目 Java 不写 raw_data，**实际不会出现 `@DS("raw")` + `@Transactional` 组合**。此条仅作规范备案。

```20:31:backend-java/attribution-app/src/main/java/com/attribution/app/config/MybatisPlusConfig.java
        PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.POSTGRE_SQL);
```

**与数据源无关** —— 拦截器在 SQL 执行前工作，数据源切换在更外层。**跨库分页天然不可用**（分页必须落在单个库的单个 Mapper 内），这正好强化了「拆 Mapper」的必要性。

## 4. Collector 端：双库处理规范

### 4.1 双 engine + 双 factory + 双 Base

```python
# collector-python/src/core/db.py
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase

# ── 业务库 → attribution ────────────────────────────────
db_async_engine = create_async_engine(
    settings.DATABASE_URL,
    echo=settings.DEBUG,
    poolclass=NullPool,
    pool_pre_ping=True,
)
db_session_factory = async_sessionmaker(
    bind=db_async_engine, class_=AsyncSession,
    expire_on_commit=False, autocommit=False, autoflush=False,
)

# ── 采集库 → raw_data ───────────────────────────────────
raw_async_engine = create_async_engine(
    settings.RAW_DATABASE_URL,
    echo=settings.DEBUG,
    poolclass=NullPool,
    pool_pre_ping=True,
)
raw_session_factory = async_sessionmaker(
    bind=raw_async_engine, class_=AsyncSession,
    expire_on_commit=False, autocommit=False, autoflush=False,
)


class AttribBase(DeclarativeBase):
    """业务库 ORM 基类（attribution 库）"""


class RawBase(DeclarativeBase):
    """采集库 ORM 基类（raw_data 库）"""
```

### 4.2 ORM Base 与库的绑定

> **基类必须与实际写入的库严格对应。SQLAlchemy 不校验 base ↔ engine 匹配，写错库不报错，只是静默写错地方。**

| 模型 | 必须继承 | 写往 | session |
|---|---|---|---|
| `models/raw/**`（29 张采集表） | `RawBase` | raw_data | `raw_session_factory()` |
| `models/business/collect_logs.py` | `AttribBase` | attribution | `db_session_factory()` |
| `tech_calendar`（交易日历） | `RawBase` | raw_data | `raw_session_factory()` |
| `stock_pools` / `stock_pool_members` | `AttribBase` | attribution | `db_session_factory()` |

### 4.3 🔴 当前 P0 缺陷

> **`raw_session_factory` 全工程零调用。**

实测统计：

```
raw_session_factory   →  仅 core/db.py（定义 + __all__ 导出），0 处业务调用
db_session_factory    →  18 个文件
```

而 29 个采集模型**全部**是 `RawBase`，配套写入代码却用业务库 session：

```python
# collectors/fundamental/daily_basic_service.py
async with db_session_factory() as session:
    await session.execute(delete(FinDailyBasicDB).where(...))
    stmt = pg_insert(FinDailyBasicDB).values(rows)
```

**后果**：采集数据**静默写向 attribution 库**。而该库实测**根本没有这些表**：

```
tech_kline_daily       → MISSING in attribution
fundamental_stock_info → MISSING in attribution
capital_moneyflow      → MISSING in attribution
fundamental_concept    → MISSING in attribution
news_article           → MISSING in attribution
```

→ **当前所有采集任务都会因「表不存在」而失败。**

另外两处：

**`collect_logs` 保持 `db_session_factory()`** —— 它在 attribution 库。

### 4.5 「表不存在」不能靠 try/except 吞掉

**现状反模式**：

```python
try:
    from models.adj_factor import AdjFactorDB
except ImportError:
    logger.debug("adj_factor 表未建，跳过入库")
    return 0
```

问题：**`ImportError` 只在模块不存在时抛出**。ORM 模块存在但**物理表不存在**时，`session.execute()` 抛的是 `ProgrammingError`（`relation does not exist`），**不会被捕获**。

规范：

| 规则 | 说明 |
|---|---|
| ORM 模块导入**不需要** try/except | 模块必然存在；不存在是代码问题，应直接崩 |
| 「表不存在」**必须 fail-fast** | 采集写入失败要让任务标记 `failed` 并留日志，不能静默返回 0 |
| 建表**不在运行时做** | 由迁移脚本一次性创建 |

### 4.6 Collector 端不需要跨库 join

Collector 的职责是「把数据从数据源搬进 raw_data」。它**不需要**把 raw_data 的表和 attribution 的表关联查询。

唯一的跨库场景是 `collect_logs`（写 attribution）与采集数据（写 raw_data）**同时发生**，但这是**两次独立事务**：

```
① INSERT collect_logs (attribution)   ← db_session_factory
② INSERT tech_kline_daily (raw_data) ← raw_session_factory
```

**不跨库事务**。日志状态允许延迟几毫秒。

### 4.7 配置

**当前 `.env`（已实测可用，两库指向正确）**：

```bash

```

**🔴 `.env.example` 是错的（compose 部署会踩坑）**：

```bash

```

| 规则 | 说明 |
|---|---|
| 两个 URL **必须指向不同库** | 🔴 现状 `.env.example` 两个都指 `attribution`（`.env` 本地是对的） |

### 4.8 部署：raw_data 库必须被创建

**现状**：`postgres/initdb/01-init.sql` 只建扩展，**没有 `CREATE DATABASE raw_data`**。

| `attribution.collect_logs` 同理 | 迁移脚本创建 |

## 6. 规范速查

### 6.1 Java 端

| 问题 | 答案 |
|---|---|
| 有几个数据源 | 2 个（`biz` = attribution，`raw` = raw_data） |
| 默认是哪个 | `biz`（业务库） |
| `@DS` 标在哪 | **Mapper 接口上**，不标 Service |
| `@DS("raw")` 标多少个 | 29 个采集表 Mapper（§2.2 逐表清单） |
| 混合库 Mapper 怎么办 | **拆分**（`StockInfoMapper` / `ConceptMemberMapper`） |
| `strict` 要不要开 | **必须开 `true`** |
| 跨库 JOIN 能写吗 | **不能**。拆成两个 Mapper，Service 层内存 join |
| 跨库事务 | **不存在**（Java 只读 raw_data、只写 attribution） |
| 要加 Redis 依赖吗 | 不要 |
| 要建 FDW 吗 | 不要 |
| XML 所在模块决定数据源吗 | 不决定，由 namespace 绑定的 Mapper 决定 |

### 6.2 Collector 端

| 问题 | 答案 |
|---|---|
| 有几个 engine | 2 个（`db_async_engine` / `raw_async_engine`） |
| 有几个 session factory | 2 个 |
| 有几个 ORM Base | 2 个（`AttribBase` / `RawBase`） |
| 采集表用哪个 | `RawBase` + `raw_session_factory()` |
| `collect_logs` 用哪个 | `AttribBase` + `db_session_factory()` |
| 采集表写哪个库 | raw_data |
| `collect_logs` 写哪个库 | attribution |
| 跨库事务 | 无。两次独立 commit |
| 建表在哪做 | 迁移脚本，不在运行时 |
| `import` 要 try/except 吗 | 不要 |

### 6.3 两端共同铁律

| # | 铁律 |
|---|---|
| 1 | 一条 SQL 只涉及一个库 |
| 2 | 跨库关联在应用层内存 join |
| 3 | 表属于哪个库，由表名前缀（`tech_` / `capital_` / `fundamental_` / `news_`）决定；`collect_logs` / `collect_*` / `stock_*` / `pool_*` / `sys_*` 属于业务库 |
| 4 | 表 → 库 的映射在两端必须一致 |
| 5 | 库名全局统一：`raw_data` / `attribution` |
