## 5. 测试用例（8 个核心）

### TC1: 全表全量备份 + 全量恢复（端到端）

**前置**：dev 库有数据

**步骤**：
1. 调 `POST /backups/ {backup_type: "full", scope: "all", output_dir: null}`
2. 轮询 `GET /backups/{id}` 直到 `status=success`
3. 记录 `file_path` 和 `row_count`
4. 手动 `DROP DATABASE attribution_test; CREATE DATABASE attribution_test;`（或新建一个测试库）
5. 改 settings 指向测试库
6. 调 `POST /backups/restore {source_path: <原 file_path>, restore_mode: "cover", confirm: true}`
7. 轮询直到 `status=success`
8. 跑 SQL 比对每张表的 `count(*)` 与原库一致

**预期**：所有 38 张表行数完全一致；耗时 < 1 分钟（100 万行）

### TC2: 选表备份 + 增量恢复

**前置**：dev 库有数据

**步骤**：
1. 选 `stock_infos` + `tech_kline_dailys` 2 张表
2. 调 `POST /backups/ {backup_type: "full", scope: "partial", tables: [...]}` → full 备份
3. 改 dev 库中 `stock_infos` 第 100 行的 `name`
4. 调 `POST /backups/restore {..., restore_mode: "upsert"}`
5. 验证：`stock_infos` 第 100 行 `name` **未变**（主键 skip）
6. 验证：备份时不存在但当前存在的行**未删**

**预期**：upsert 模式按主键 skip；不影响其他表

### TC3: 路径安全校验

**步骤**：
1. 调 `POST /backups/ {output_dir: "C:/Windows/System32"}` → 期望 403
2. 调 `POST /backups/ {output_dir: "D:/codes/Attribution_Analysis/backend/src"}` → 期望 403
3. 调 `POST /backups/ {output_dir: "D:/extra_backups"}`（不在白名单）→ 期望 403
4. 调 `POST /backups/ {output_dir: "D:/codes/Attribution_Analysis/backend/backups"}` → 期望 202

**预期**：白名单生效，敏感路径全拒

### TC4: 头部校验（恢复时强校验）

**步骤**：
1. 手工编辑一个 .sql，删掉头部 `generator:` 行
2. 调 `/backups/restore` → 期望 400 `InvalidBackupFileError`
3. 手工编辑一个 .sql，改 `generator: other-system`
4. 调 `/backups/restore` → 期望 400

**预期**：头部 5 行任一缺失/不匹配 → 拒

### TC5: 大表性能（COPY vs INSERT 对比）

**步骤**：
1. 备份 `tech_kline_dailys`（100 万行）
2. 记录 `duration_sec`
3. 期望：< 30 秒（COPY 协议）

**预期**：COPY 协议下 100 万行导出 < 30 秒

### TC6: 进程崩溃恢复

**步骤**：
1. 启动备份任务
2. 任务 `status=running` 时，**强制 kill -9 进程**
3. 重启服务
4. 调 `GET /backups/{id}` → 期望 `status=interrupted`

**预期**：启动期 `recover_interrupted_tasks` 把 `running` 标 `interrupted`

### TC7: 恢复失败回滚

**步骤**：
1. 备份 → 拿到 .sql
2. 手工编辑 .sql，在某行 INSERT 加一个语法错误
3. 调 `/backups/restore` → 期望 `status=failed`
4. 验证：原表数据**未受影响**（事务回滚）

**预期**：单事务失败 → 整体回滚，无副作用

### TC8: 鉴权粒度

**步骤**：
1. 用 viewer 角色登录
2. 调 `GET /backups/tables` → 期望 403
3. 调 `POST /backups/` → 期望 403
4. 用 admin 角色登录
5. 同样的接口 → 期望 200 / 202

**预期**：非管理员用户无备份权限

## 7. 风险与回退

| 风险 | 应对 |
|---|---|
| 恢复失败导致数据丢失 | **强制 pre-restore 备份**（cover 模式）+ 单事务回滚 |
| 备份文件太大占满磁盘 | v1 限制 2GB；提供"清理 > 30 天"按钮（v2）|
| SQLAlchemy `CreateTable` 渲染 bug | 测过 38 张表；遇到不完美行 → 人工补丁并降级 |
| 备份期间采集任务写入新数据 | 备份用 `REPEATABLE READ` 事务快照；恢复前建议先停采集 |
| 用户误恢复 cover 模式 | 二次确认弹窗 + 强警告 UI + 服务端 `confirm=True` 强校验 |
| `pg_dump` 兼容性问题 | **不依赖 pg_dump**（这是设计选择本身）|
| 备份目录在项目内被提交到 git | `backend/.gitignore` 加 `backups/` |
| Windows 路径分隔符 | 后端用 `pathlib.Path`，统一 `/` 校验 |

|---|---|---|

| 不做差异/增量备份 | 全量备份 | v2 |
