## 〇、决策与方向（评审前先看）

### 0.1 本次优化目标

本次优化解决两个问题：

1. **元数据碎片化**：当前 28 个 service 各自声明了 `name`、`facet`、`sub_facet`、`label`、`RATE_LIMIT`、`CONCURRENCY`、`UI_SCHEMA` 等字段，散落在每个 service class 里，缺乏统一抽象。新增 service 时容易漏填字段，且 catalog 生成逻辑（`CatalogService._to_item()`）和 service 自身逻辑耦合。
2. **采集进度黑盒**：前端触发采集后，后端 `asyncio.gather` 跑完后才返回结果，用户面对长时间 loading 看不到任何进度，不知道是卡住了还是在采、预计还要多久。中间发生错误也只有最终报错，没有过程日志。

### 0.2 解决思路

| 问题 | 方案 |
|---|---|
| 元数据碎片化 | 引入统一的 `ServiceMeta` 数据类（dataclass），所有 service 只声明 meta + UI_SCHEMA，其余字段从 meta 派生 |
| 采集进度黑盒 | 新建 `collect_logs` 表 + Redis 实时进度 key，用 AOP 装饰器 `@collect_logger` 统一注入日志逻辑，service 层几乎不改 |
| 前端无感知 | POST 触发后立即返回 `log_id`，前端轮询 `GET /collect/logs/{service_name}` 拿到实时进度 |

### 0.3 重要决策（评审通过项）

- **不引入 MQ**：当前阶段日志创建、进度更新、终态落库全部走 AOP 装饰器 + DB/Redis，**不引入 RabbitMQ**。后续独立日志服务再考虑 MQ。
- **删除 `mode` 字段**：前端参数直接透传给 `service.collect()`，不再区分"全量/条件"——增量类型在 `params` 里留空表示全量、填了表示指定采集。
- **不使用 AOP 框架（如装饰器/字节码）做日志创建**：AOP 装饰器只做"采集进度监控 + Redis 更新 + 终态落库"，**日志记录在 HTTP handler 同步创建**。理由见 4.5。
- **log_id 使用 `uuid4`**，handler 同步生成并返回前端，不依赖 DB 或 MQ。
- **删除旧表** `collect_run_log` 和 `collect_schedule`（残留），新建 `collect_logs` 表。

## 一、ServiceMeta 字段评审

### 1.1 现状字段调研

以 `concept_members_service.py` 为例（其他 27 个 service 结构类似）：

```python
class ConceptMembersService:
    name = "concept_members"        # 类属性
    facet = "fundamental"           # 类属性
    sub_facet = "concept"           # 类属性
    label = "概念成分股"             # 类属性
    DEFAULT_PARAMS = {"index_codes": []}    # 类属性
    UI_SCHEMA = [...]               # 类属性
    RATE_LIMIT = ("adata", 100, 60)  # 类属性
    CONCURRENCY = 3                 # 类属性
```

### 1.2 字段必要性分析

| 字段 | 必要性 | 说明 |
|---|---|---|
| `name` | ✅ **必填** | 全局唯一标识，catalog、URL、日志表 `service_name` 都用它 |
| `facet` | ✅ **必填** | 大类（tech/fundamental），URL 第一段，分类用 |
| `sub_facet` | ⚠️ **可推导/可选** | 实际几乎所有 service 都填了，但前端 catalog 不展示。可保留 |
| `label` | ✅ **必填** | 前端展示名（按钮文案、表格列名） |
| `description` | ⚠️ **可选** | 前端 catalog 可展示，**目前 28 个 service 都没填**，先不做强制 |
| `DEFAULT_PARAMS` | ❌ **可以去掉** | 字段名语义不清（"默认值"还是"初始值"？），前端从 `UI_SCHEMA` 自动生成空表单即可 |
| `UI_SCHEMA` | ✅ **必填（但要重命名）** | 前端表单配置，不可缺。改名为 `param_schema` 更清晰 |
| `RATE_LIMIT` | ✅ **必填** | 限速配置，缺失会导致采集打爆第三方 API |
| `CONCURRENCY` | ✅ **必填** | 并发数，缺失会导致采集过慢 |

### 1.3 决策

| 旧字段 | 处置 | 新字段（ServiceMeta） |
|---|---|---|
| `name` | 保留 | `name` |
| `facet` | 保留 | `facet` |
| `sub_facet` | 保留（仍为可选） | `sub_facet` |
| `label` | 保留 | `label` |
| `description` | 保留（可选） | `description` |
| `DEFAULT_PARAMS` | **删除** | 由前端从 `ui_schema` 推导默认空值 |
| `UI_SCHEMA` | **重命名** | `param_schema` |
| `RATE_LIMIT` | 保留 | `rate_limit` |
| `CONCURRENCY` | 保留 | `concurrency` |
| — | **新增** | `kind: ServiceKind`（增量/全量/实时） |

**注意**：`UI_SCHEMA` 中 key 命名要保持和后端 `params` 完全一致（前端表单字段名 = 后端入参名），不再依赖 `DEFAULT_PARAMS` 提供初值。

### 1.4 ServiceMeta dataclass 完整定义

```python
# contexts/collect/application/service/base.py

from dataclasses import dataclass, field
from enum import Enum


class ServiceKind(Enum):
    """采集服务类型，决定 UI 展示和触发方式"""
    INCREMENTAL = "incremental"     # 增量入库，需要时间范围（如日K）
    FULL_REFRESH = "full_refresh"  # 全量覆盖，无时间范围（如股票基本信息）
    REALTIME = "realtime"           # 实时查询，不入库（如分K）


@dataclass
class ServiceMeta:
    """采集 service 的统一元数据"""
    # ── 标识 ──────────────────────────────────────
    name: str                                       # 全局唯一标识
    facet: str                                      # 大类
    sub_facet: str = ""                            # 子类
    label: str = ""                                # 前端展示名
    description: str = ""                          # 描述（可选）
    
    # ── 采集行为 ──────────────────────────────────
    kind: ServiceKind = ServiceKind.INCREMENTAL
    
    # ── 前端 UI_SCHEMA ────────────────────────────
    param_schema: list[dict] = field(default_factory=list)
    
    # ── 限速与并发 ────────────────────────────────
    rate_limit: tuple[str, int, int] | None = None  # ("tushare", 200, 60)
    concurrency: int = 1
    
    # ── 自动派生 ──────────────────────────────────
    @property
    def path(self) -> str:
        return f"/collect/{self.facet}/{self.name}"
    
    @property
    def query_path(self) -> str | None:
        return f"/collect/query/{self.name}"
    
    @property
    def supports_query(self) -> bool:
        return self.kind == ServiceKind.REALTIME
```

-- ============================================================
-- collect_logs：采集日志（每次触发采集产生一条记录）
-- ============================================================
CREATE TABLE public.collect_logs (
    -- 主键
    id              UUID PRIMARY KEY,                -- log_id，handler 同步生成（uuid4）
    
    -- 采集服务标识
    service_name    VARCHAR(128) NOT NULL,           -- e.g. "daily_kline"（不带 facet 前缀，单独存）
    facet           VARCHAR(64)  NOT NULL,           -- e.g. "tech"
    kind            VARCHAR(32)  NOT NULL,           -- "incremental" / "full_refresh" / "realtime"
    
    -- 触发信息
    trigger_source  VARCHAR(32)  NOT NULL DEFAULT 'manual',  -- "manual" / "script" / "schedule"(预留)
    trigger_user    VARCHAR(64),                    -- 触发用户（前端为 null 或 username，未来对接 auth）
    
    -- 采集参数（前端原始入参）
    params          JSONB NOT NULL DEFAULT '{}'::jsonb,
    
    -- 状态机
    status          VARCHAR(32) NOT NULL DEFAULT 'pending',
    -- pending → running → success / partial_fail / failed / skipped
    
    -- 数量统计
    total_count     INTEGER     DEFAULT 0,          -- 预估总量（symbol 总数等，0 表示未知）
    saved_count     INTEGER     DEFAULT 0,          -- 已入库记录数（不是 symbol 数）
    fail_count      INTEGER     DEFAULT 0,          -- 失败记录数
    progress        SMALLINT    DEFAULT 0,          -- 0-100 进度百分比
    
    -- 错误
    error_message   TEXT,                           -- failed 时记录
    
    -- 时间
    started_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    finished_at     TIMESTAMPTZ,                    -- 终态时填
    
    -- 元信息
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    
    -- 约束
    CONSTRAINT ck_collect_logs_status 
        CHECK (status IN ('pending', 'running', 'success', 'partial_fail', 'failed', 'skipped')),
    CONSTRAINT ck_collect_logs_progress 
        CHECK (progress >= 0 AND progress <= 100),
    CONSTRAINT ck_collect_logs_kind 
        CHECK (kind IN ('incremental', 'full_refresh', 'realtime'))
);

-- 索引
CREATE INDEX idx_collect_logs_service_name  ON public.collect_logs(service_name);
CREATE INDEX idx_collect_logs_status        ON public.collect_logs(status);
CREATE INDEX idx_collect_logs_started_at    ON public.collect_logs(started_at DESC);
CREATE INDEX idx_collect_logs_service_time  ON public.collect_logs(service_name, started_at DESC);

-- updated_at 自动维护触发器
CREATE OR REPLACE FUNCTION public.set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_collect_logs_updated_at
BEFORE UPDATE ON public.collect_logs
FOR EACH ROW

| `progress` | SMALLINT | 0-100 进度 |
| `error_message` | TEXT | 失败时填 |
| `started_at` | TIMESTAMPTZ | 任务实际开始时间 |
| `finished_at` | TIMESTAMPTZ | 终态时间 |

### 2.4 状态机

```
pending ──→ running ──→ success
                  ├─→ partial_fail  (部分失败但可接受)
                  └─→ failed        (全部失败或异常)
```

| 状态 | 含义 |
|---|---|
| `pending` | 日志已创建，等待采集任务启动 |
| `running` | 采集中，progress 实时更新 |
| `success` | 采集完成，全部成功 |
| `partial_fail` | 采集完成，部分失败（fail_count > 0 但 saved_count > 0） |
| `failed` | 采集失败（异常或全部失败） |
| `skipped` | 跳过（realtime 类型调 collect() 时） |

## 三、Redis 实时进度

### 3.1 Key 设计

```
Key:   collect:log:{service_name}:{log_id}
Type:  Hash
TTL:   3600 秒（1小时）
```

**Field 设计**：

| Field | 类型 | 说明 |
|---|---|---|
| `status` | string | pending/running/success/partial_fail/failed |
| `progress` | int | 0-100 |
| `saved_count` | int | |
| `fail_count` | int | |
| `total_count` | int | |
| `started_at` | string (ISO) | |
| `updated_at` | string (ISO) | AOP 每次更新都写 |
| `error` | string | 失败信息 |

### 3.2 写入时机

| 时机 | 操作 | 执行位置 |
|---|---|---|
| Handler 收到 POST | `HSET` 初始化 `status=pending, progress=0` | **HTTP handler（同步）** |
| 后台任务启动 | `HSET status=running, started_at=now` | **AOP 装饰器** |
| 每批 yield | `HSET progress=X, saved_count=Y, updated_at=now` | **AOP 装饰器（同步）** |
| 终态 | `HSET status=success/failed/partial_fail` | **AOP 装饰器** |
| 终态后 | 保留 1h 自动过期 | Redis TTL |

### 3.3 不写 DB 的优化

AOP 装饰器**只把进度同步写 Redis**，DB 进度在终态时**一次性**落库。理由：
- Redis 写一次 < 1ms，不阻塞 generator
- DB 每批写 IO 太重，且 DB 进度不需要实时性（前端轮询读 Redis）
- 终态时再写 DB，保证 final 状态必落库

## 四、AOP 日志装饰器

### 4.1 职责拆分

| 阶段 | 谁做 | 做什么 |
|---|---|---|
| **1. 触发采集** | HTTP handler | 生成 log_id、**同步创建 collect_logs 记录（status=pending）**、**同步写 Redis pending hash**、返回 log_id、启动 `asyncio.create_task` |
| **2. 采集开始** | AOP 装饰器 | 更新 DB 和 Redis 为 `status='running'`、记录 started_at |
| **3. 采集中** | AOP 装饰器 | 拦截 yield，**只更新 Redis**（progress/saved_count/fail_count） |
| **4. 采集结束** | AOP 装饰器 | 写 DB 终态（status/final counts）、更新 Redis 终态 |
| **5. 异常** | AOP 装饰器 | 写 DB failed、记录 error_message、更新 Redis failed |

**关于 `status='running'`**：这只是一个状态字段，不是独立进程或服务。它在 AOP 装饰器进入 `wrapper()` 时写入，告诉前端"这个采集任务正在执行中"。fetcher（TushareFetcher / AdataFetcher 等）就在同一个协程里被调用，没有额外的 infra 进程。

### 4.2 为什么日志创建放在 handler，不放 AOP

- **AOP 装饰器只能拦截方法调用**，不能在调用前"知道"这次是 HTTP 触发还是脚本调用
- handler 同步创建 DB + Redis 后，**采集后台协程可以直接用 log_id**（不依赖 AOP 内部逻辑）
- 即使 AOP 装饰器未来有问题，handler 也能保证日志存在
- 详见 4.5

### 4.3 装饰器实现

```python
# shared/infrastructure/aop/collect_logger.py

import functools
import logging
from datetime import datetime
from typing import AsyncGenerator, Any

from sqlalchemy.ext.asyncio import AsyncSession
from contexts.collect.infrastructure.persistence.repositories import CollectLogRepository

logger = logging.getLogger(__name__)


def collect_logger(service_meta: "ServiceMeta"):
    """
    AOP 日志装饰器：拦截 collect() 的 yield，更新进度和终态。
    
    前置条件：调用方必须在调用前创建 collect_logs 记录（pending）并传入 log_id。
    
    装饰器只负责：
    1. 标记 running
    2. 拦截 yield → 实时更新 Redis（不写 DB）
    3. 终态（success/partial_fail/failed）→ 写 DB + Redis
    """
    service_name = service_meta.name
    facet = service_meta.facet
    kind = service_meta.kind.value
    
    def decorator(func):
        @functools.wraps(func)
        async def wrapper(self, params: dict, session: AsyncSession, log_id: str, **kwargs):
            repo = CollectLogRepository(session)
            redis_key = f"collect:log:{service_name}:{log_id}"
            _r = get_redis()
            
            try:
                # ── 1. 标记 running ───────────────────────
                started_at = datetime.now()
                await repo.update_status(log_id, "running", started_at=started_at)
                await _r.hset(redis_key, mapping={
                    "status": "running",
                    "started_at": started_at.isoformat(),
                    "updated_at": started_at.isoformat(),
                })
                
                # ── 2. 执行 generator，拦截 yield ──────────
                saved_total = 0
                fail_total = 0
                total = 0
                async for batch in func(self, params=params, session=session, log_id=log_id, **kwargs):
                    saved = batch.get("saved", 0)
                    fail  = batch.get("fail", 0)
                    total = batch.get("total", total)
                    saved_total += saved
                    fail_total += fail
                    
                    progress = int((saved_total + fail_total) / total * 100) if total else 0
                    
                    # 实时更新 Redis（< 1ms，不阻塞 generator）
                    await _r.hset(redis_key, mapping={
                        "progress": min(progress, 100),
                        "saved_count": saved_total,
                        "fail_count": fail_total,
                        "total_count": total,
                        "updated_at": datetime.now().isoformat(),
                    })
                
                # ── 3. 终态：写 DB + Redis ─────────────────
                if fail_total == 0:
                    status = "success"
                elif saved_total == 0:
                    status = "failed"
                else:
                    status = "partial_fail"
                
                finished_at = datetime.now()
                await repo.finish(log_id, status, saved_total, fail_total, progress=100, finished_at=finished_at)
                await _r.hset(redis_key, mapping={
                    "status": status,
                    "progress": 100,
                    "saved_count": saved_total,
                    "fail_count": fail_total,
                    "updated_at": finished_at.isoformat(),
                })
                
            except Exception as e:
                # ── 4. 异常：写 DB + Redis ─────────────────
                logger.exception(f"[{service_name}] 采集失败: {e}")
                finished_at = datetime.now()
                await repo.finish(
                    log_id, "failed", saved_total, fail_total,
                    error=str(e)[:500], finished_at=finished_at,
                )
                await _r.hset(redis_key, mapping={
                    "status": "failed",
                    "error": str(e)[:500],
                    "updated_at": finished_at.isoformat(),
                })
                raise
        
        return wrapper
    return decorator
```

### 4.4 装饰器调用方式

```python
class DailyKlineService:
    META = ServiceMeta(...)  # 必须有 META
    
    @collect_logger(META)  # 传入 META 引用，装饰器读 service_name/facet/kind
    async def collect(self, params: dict, session: AsyncSession, log_id: str):
        """
        :param params: 前端采集参数
        :param session: DB session
        :param log_id: 日志 ID（由 handler 同步生成）
        :yield: 每批进度 dict
        """
        symbols = params.get("symbols") or await self._list_all_symbols()
        start = params["start_date"]
        end = params["end_date"]
        total = len(symbols)
        sem = asyncio.Semaphore(self.META.concurrency)
        
        async def one(symbol: str) -> dict:
            async with sem:
                try:
                    klines = await self._fetch(symbol, start, end)
                    saved = await self._save(symbol, klines, session)
                    return {"saved": saved, "fail": 0, "total": total}
                except Exception as e:
                    logger.exception(f"采集 {symbol} 失败: {e}")
                    return {"saved": 0, "fail": 1, "total": total}
        
        # 边采集边 yield 进度
        for coro in asyncio.as_completed([asyncio.create_task(one(s)) for s in symbols]):
            result = await coro
            yield result
```

**业务逻辑（`_fetch`、`_save`）完全不变**，只是把"gather 完返回"改成"边跑边 yield"。

### 4.5 为什么日志创建在 handler，不在 AOP

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. AOP 装饰器创建日志** | 装饰器统一管理，service 不需要关心 log_id | 1. AOP 拦截的是 `collect()`，调用前需要预先生成 log_id 并传入 → **仍然要 handler 生成**；2. AOP 装饰器依赖外部状态（log_id），增加复杂度；3. 脚本/测试调用 `collect()` 也要传 log_id，否则不记录日志 |
| **B. Handler 同步创建（推荐）** | 1. log_id 在 handler 内闭环生成并立即返回；2. AOP 只接收 log_id，不需要关心"怎么来的"；3. 脚本调用 `collect()` 时传 `log_id=None`，AOP 自然跳过日志逻辑 | 1. handler 多了一点样板代码（约 10 行） |

**结论**：handler 同步创建更清晰，AOP 只做"已存在日志的进度维护"。

### 4.6 统一所有 service 加 AOP 切面 ✅

- 所有 28 个 service 都加 `@collect_logger(META)` 装饰器
- 装饰器对 `log_id` 为 None 兼容（脚本场景）：

```python
async def wrapper(self, params, session, log_id, **kwargs):
    if log_id is None:
        # 脚本/测试场景：直接执行，不写日志
        async for batch in func(self, params=params, session=session, log_id=None, **kwargs):
            yield batch
        return
    # ... 正常日志逻辑
```

- service 业务逻辑（fetch/save）不变
- 采集 API 协议从 `asyncio.gather(...)` 改成 generator + yield

    asyncio.create_task(

        "status": "pending",
        "service_name": service_name,
        "facet": facet,
        "message": "采集任务已创建，请通过 /collect/logs/{service_name} 轮询进度",
    })

    svc = svc_class()
    try:
        async for _ in svc.collect(params=params, session=session, log_id=log_id):

async def list_logs(
    service_name: str,
    limit: int = 10,
    session: AsyncSession = Depends(get_db),
) -> dict[str, Any]:
    """
    返回最近 limit 条日志。
    如果状态是 pending/running，从 Redis 读实时进度覆盖 DB 数据。

    repo = CollectLogRepository(session)
    logs = await repo.list_recent(service_name, limit=limit)

            redis_data = await _r.hgetall(key)
            if redis_data:

                if "fail_count" in redis_data:
                    log["fail_count"] = int(redis_data["fail_count"])

## 六、前端轮询实现

### 6.1 进入采集页面的逻辑

```ts
// views/collect-manage/daily-kline.vue

import { onMounted, ref } from 'vue'
import { triggerCollect, listCollectLogs, type CollectLog } from '../api'

const logs = ref<CollectLog[]>([])
const activeLogId = ref<string | null>(null)  // 当前轮询的日志 ID
const polling = ref(false)

onMounted(async () => {
  await loadLogs()
  await resumePollingIfNeeded()  // 有 pending/running 就接着轮询
})

async function loadLogs() {
  const res = await listCollectLogs('daily_kline', 20)
  logs.value = res.items
}

/** 有 pending/running 状态的日志就接着轮询 */
async function resumePollingIfNeeded() {
  const active = logs.value.find(
    l => l.status === 'pending' || l.status === 'running'
  )
  if (active) {
    activeLogId.value = active.id
    await pollProgress(active.id)
  }
}

/** 触发采集 */
async function startCollect() {
  const res = await triggerCollect('tech', 'daily_kline', {
    params: {
      symbols: symbolsInput.value,
      start_date: startDate.value,
      end_date: endDate.value,
    }
  })
  activeLogId.value = res.log_id
  await loadLogs()  // 重新拉一次列表
  await pollProgress(res.log_id)
}

/** 轮询单条日志进度 */
async function pollProgress(logId: string) {
  polling.value = true
  while (polling.value) {
    const res = await listCollectLogs('daily_kline', 50)
    const log = res.items.find(l => l.id === logId)
    
    if (!log) {
      // 日志不在最近 50 条里（极旧），停止轮询
      break
    }
    
    // 更新本地 logs 列表
    const idx = logs.value.findIndex(l => l.id === logId)
    if (idx >= 0) logs.value[idx] = log
    
    // 终态停止
    if (['success', 'partial_fail', 'failed', 'skipped'].includes(log.status)) {
      break
    }
    
    await sleep(2000)  // 2 秒一次
  }
  polling.value = false
}
```

### 6.2 关键点

| 场景 | 行为 |
|---|---|
| **进入页面有 pending 日志** | 自动接着轮询（断网恢复、刷新页面都能继续看进度） |
| **进入页面有 running 日志** | 自动接着轮询 |
| **进入页面只有终态日志** | 不轮询，直接展示历史 |
| **触发新采集** | 立即拿到 log_id → 加入轮询 |
| **同一时间多个采集** | 各自独立轮询（按 `logId` 区分） |

### 6.3 轮询频率

- **2 秒一次**（适中，平衡实时性和后端压力）
- 后续可优化为 SSE 或 WebSocket（Phase 3 考虑）

## 八、CollectLogRepository 设计

```python
# contexts/collect/infrastructure/persistence/repositories/collect_log_repository.py

class CollectLogRepository:
    def __init__(self, session: AsyncSession):
        self._session = session
    
    async def create(
        self,
        id: str,
        service_name: str,
        facet: str,
        kind: str,
        trigger_source: str,
        params: dict,
        trigger_user: str | None = None,
    ) -> None:
        """创建日志（pending 状态）"""
        stmt = insert(CollectLog).values(
            id=id,
            service_name=service_name,
            facet=facet,
            kind=kind,
            trigger_source=trigger_source,
            trigger_user=trigger_user,
            params=params,
            status="pending",
            started_at=datetime.now(),
        )
        await self._session.execute(stmt)
        await self._session.commit()
    
    async def update_status(
        self,
        log_id: str,
        status: str,
        started_at: datetime | None = None,
    ) -> None:
        """更新状态（pending → running）"""
        values = {"status": status}
        if started_at:
            values["started_at"] = started_at
        stmt = (
            update(CollectLog)
            .where(CollectLog.id == log_id)
            .values(**values)
        )
        await self._session.execute(stmt)
        await self._session.commit()
    
    async def finish(
        self,
        log_id: str,
        status: str,
        saved_count: int,
        fail_count: int,
        progress: int = 100,
        error: str | None = None,
        finished_at: datetime | None = None,
    ) -> None:
        """终态写入"""
        stmt = (
            update(CollectLog)
            .where(CollectLog.id == log_id)
            .values(
                status=status,
                saved_count=saved_count,
                fail_count=fail_count,
                progress=progress,
                error_message=error,
                finished_at=finished_at or datetime.now(),
            )
        )
        await self._session.execute(stmt)
        await self._session.commit()
    
    async def list_recent(self, service_name: str, limit: int = 10) -> list[dict]:
        """最近 N 条日志"""
        stmt = (
            select(CollectLog)
            .where(CollectLog.service_name == service_name)
            .order_by(CollectLog.started_at.desc())
            .limit(limit)
        )
        result = await self._session.execute(stmt)
        rows = result.scalars().all()
        return [_to_dict(r) for r in rows]
    
    async def get_by_id(self, log_id: str) -> dict | None:
        """按 ID 查单条"""
        stmt = select(CollectLog).where(CollectLog.id == log_id)
        result = await self._session.execute(stmt)
        row = result.scalar_one_or_none()
        return _to_dict(row) if row else None
```

| 4 | 并发约束 | **不做**，同一 service 可多次触发，日志表自然有多条记录 |
| 5 | Redis 高可用 | **暂不考虑**，先跑通 |
| 6 | `running` 是什么 | **仅是状态字段**（DB/Redis），由 AOP 装饰器在协程进入/退出时切换；fetcher 在同一协程里被调用，无需额外 infra 进程或服务 |

### `running` 状态详解

`running` 不是进程/服务，而是 `collect_logs.status` 字段的一个枚举值：

```
pending ──→ running ──→ success
                  ├─→ partial_fail
                  └─→ failed
```

| 状态 | 含义 | 谁写入 |
|---|---|---|
| `pending` | handler 已返回前端，后台协程尚未真正开始 fetch | **Handler 同步写** |
| `running` | 协程正在执行 fetch/save（调用 TushareFetcher 等） | **AOP 装饰器** |
| `success` / `partial_fail` / `failed` | 协程正常结束或异常退出 | **AOP 装饰器** |

**底层调用链**（协程内部）：

```
_run_collect() 协程（FastAPI 进程内）
  └─ svc.collect(params, session, log_id)  ← @collect_logger 装饰
        └─ async for batch in _do_fetch_and_save():
              ├─ await check(RATE_LIMIT)
              ├─ await self._fetcher.fetch(...)     ← TushareFetcher / AdataFetcher
              ├─ await self._repo.save(...)        ← Repository 写 DB
              └─ yield { saved: N, fail: 0, total: M }
```

**fetcher 就在协程里被调用**，不是独立进程。`running` 状态只是告诉前端"这个采集任务正在执行中"。
