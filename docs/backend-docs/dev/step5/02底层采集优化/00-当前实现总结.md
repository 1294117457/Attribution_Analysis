# 00 当前实现总结

> 截至 2026-10-13，P1–P6 已全部完成。本文描述**代码现在的样子**；01–07 是当时的设计方案，细节以本文和代码为准。
> 后续把采集任务上移到应用层的方案见 [03collect优化](../03collect优化/README.md)。

## 1. 一句话

所有外部数据（Tushare / adata / pytdx）都通过一个入口 `DataGateway` 获取。一份数据只定义一次（`XxxPort`），可以有多个实现，按优先级选源、失败换源。限流、重试、统计、缓存都在 Gateway 里做，调用方不用管。

采集入库、实时查询、HTTP / Agent 按名调用，都只是 Gateway 的不同使用方式。

## 3. 数据层

### 3.1 三层结构

| 层 | 位置 | 内容 |
| :-- | :-- | :-- |
| 根约束 `DataPort[Params, Item]` | `application/port/data/base.py` | 元数据字段（`name` / `label` / `facet` / `unit` / `cache` / `sample_params` …）+ 抽象 `fetch(params) -> list[Item]` |
| 接口约束 `XxxPort` | `application/port/data/<面>.py` | 只描述"取什么"：名称、参数模型、返回 BO，不含数据源信息 |
| 底层实现 `<工具>XxxAdapter(XxxPort, AdapterBase)` | `infrastructure/adapter/data/<工具>/` | `tool` / `origin` / `priority` / `throttle_group`；入参转换 → 调 Client → 转 BO |
| SDK 连接 `<工具>Client` | 同上 `client.py` | 鉴权、同步转异步、把 SDK 异常翻译成 `RateLimited` / `SourceUnavailable` |

注册表（`DataPortRegistry`）在 `register` 时沿 MRO 自动找到 Adapter 所属的 Port，并做以下校验：

- 必须填写 `tool` / `origin`。
- `throttle_group` 必须已定义。
- Adapter 不能覆盖 Port 的元数据。
- 同一 Port 下 `tool` 不能重复。

- 分 K 用 `interval: MinuteInterval` + `days: 1..5`。1min 只支持当天，由模型校验。

### 3.3 一次调用经过什么

```
gateway.fetch(XxxPort, params, source=None, policy=COLLECT|QUERY)
  ① 参数校验：dict → XxxPort.Params（失败抛 InvalidParams）
  ② 设置 call_policy（contextvar）
  ③ policy=QUERY 且 Port 声明了 cache → CacheDecorator（缓存命中直接返回；未命中加单飞锁）
  ④ 选源：指定 source 只用它；否则按 priority 逐个试
        supports()=False 跳过；RateLimited / SourceUnavailable 换下一个；InvalidParams 直接抛
  ⑤ 每个实现外面套：MetricsDecorator → RetryDecorator → ThrottleDecorator → Adapter
  ⑥ 返回 DataResult{items, source, cached, fetched_at, latency_ms, attempts}
```

两种调用策略的区别：

| | COLLECT（采集，默认） | QUERY（查询） |
| :-- | :-- | :-- |
| 缓存 | 不走 | Port 声明了 `cache` 才走 |
| 限频 `RateLimited` | 等 `retry_after`（tushare 60s）后重试，最多 3 次 | 直接抛 |
| 不可用 `SourceUnavailable` | 退避 1s、3s 重试 | 退避 0.5s 重试 1 次 |
| 限流 | 占并发名额 + 最小调用间隔 | 只占并发名额；单次取数 10s 超时 |

限流分组（进程内，单进程假设）：

| 分组 | 并发上限 | 最小间隔 |
| :-- | :-- | :-- |
| `tushare` | `COLLECT_MAX_CONCURRENCY`（默认 8） | 0.15s |
| `adata:ths` | 5 | 0.5s |
| `tdx` | 1 | 0 |

所有等待都用 `sleep_cancellable`：每秒检查一次 `cancel_check`，所以采集任务被取消时，正在限频等待的调用也能及时退出。

### 3.4 错误类型

| 错误 | 含义 | Gateway 行为 |
| :-- | :-- | :-- |
| `InvalidParams` | 参数不合法 | 不重试、不换源，直接抛 |
| `NotSupported` | 没有实现支持这组参数 | 抛（HTTP 400） |
| `RateLimited` | 限频 | 按策略重试，仍失败则换源 |
| `SourceUnavailable` | 网络 / 超时 / SDK 异常 | 退避重试，仍失败则换源；全部失败时抛出，并在 `attempts` 里带上各实现的错误 |

## 4. 谁在用 Gateway

| 使用方 | 方式 | 说明 |
| :-- | :-- | :-- |
| 采集任务（`adapter/collect/`） | `get_data_gateway().fetch(XxxPort, ...)`，COLLECT | 取数后自行入库，见 §6 |
| `StockInfoService` | 注入 gateway | `sync_stocks`（`stock_basic`）、`collect`（`daily_kline`）、`get_minute_klines`（`stock_minute_kline`，QUERY） |
| `ConceptService` | 注入 gateway | `stock_concepts`（QUERY）；概念实时行情经 `ConceptRealtimeReader` |
| `ConceptRealtimeReader` | `fetch_many(ConceptMinutePort, ..., QUERY)` | 失败或无数据时降级为库里最近一条日 K 收盘，标 `stale=true`（降级是业务决策，放在应用层） |
| `ConceptBoardService` | 经 `ConceptRealtimeReader` | 概念看板（后续会去掉） |
| `DataQueryService` | `invoke(DataCommand)`，固定 QUERY | 按名调用：`/data/*`、`/collect/realtime/*` 试查、Agent 工具；返回超过 5000 条报错 |
| `CollectManageService` | `is_realtime(name)` | 区分实时接口和采集任务 |

Agent 工具目录：`build_agent_tools(svc)` 由数据目录生成 23 个工具定义（`data_<port>`，参数即 Port 的 JSON Schema）。

## 5. Redis 键

| 键 | 内容 | 写入方 |
| :-- | :-- | :-- |
| `ds:cache:{port}:{sha1(params)}` | 实时数据缓存 `{items, source, fetched_at}`，TTL 由 `market_session.ttl_for` 决定（交易时段 15s） | `CacheDecorator` |
| `ds:lock:{port}:{sha1(params)}` | 单飞锁，`SET NX EX 5`；其他请求最多等 2s 读缓存 | `CacheDecorator` |
| `ds:stats:{port}:{tool}:{yyyymmdd}` | 调用统计：calls / latency_sum / errors / rate_limited / last_error，保留 7 天 | `MetricsDecorator` |
| `ds:stats:{port}:cache:{yyyymmdd}` | 缓存命中：hits / misses | `CacheDecorator` |
| `collect:progress:{task_id}` | 采集进度：total / done / success / fail / skip / status / current（与改造前一致） | 采集框架 `base.py`、`CollectManageService.prepare` |

Redis 不可用时：缓存和统计静默跳过，直接取数。

### 6.3 CollectManageService

- 提交：校验类型 → 防重（同类型有 `running` 则 `TaskConflict`）→ 建任务行 → 初始化 Redis 进度 → 后台 `execute_task`。
- 失败任务重跑、方案增删改查、方案执行（按顺序跑方案项，`stop_on_fail` 时遇到失败停止）。
- 定时：方案增删改时调用 `SchedulerPort.upsert/remove`；到点 `handle_job` → `run_plan(trigger="schedule")`；启动时 `restore_schedules`。

## 9. 启动顺序与配置

`main.py` lifespan：

1. `ensure_schema`，清理上次遗留的 `running` 任务，初始化默认池和管理员。
2. `setup_default_registry()` → `setup_data()`：按 `SOURCES` 创建 tushare / adata / pytdx 的 Client，注册 Adapter，并套上装饰器。某个数据源初始化失败只告警跳过，不影响启动。
3. `setup_collect_task_registry([...])`：逐个实例化 23 个任务。
4. `_sync_fetcher_catalog()`：用代码里的任务 + 实时 Port 对账 `collect_fetchers` 表（缺的补录，多的标 `orphan`）。
5. `COLLECT_SCHEDULER_ENABLED` 为真时：创建 `ApschedulerAdapter` → `set_scheduler` → `on_fire(handle_job)` → `restore_schedules` → `start`。
6. 关闭时 `scheduler.shutdown()`，再 `cancel_background()`。

配置（`settings.py`）：

| 配置 | 默认 | 位置 | 作用 |
| :-- | :-- | :-- | :-- |
| `TUSHARE_TOKEN` | — | `k8s/public/public.env` | 敏感 |
| `DATA_SOURCE_DISABLED` | 空 | `backend/.env` | 逗号分隔的 tool，临时禁用某个数据源 |
| `COLLECT_CONCURRENCY` / `COLLECT_MAX_CONCURRENCY` | 3 / 8 | `backend/.env` | 日 K 采集并发；后者同时是 tushare 限流组并发上限 |
| `COLLECT_SCHEDULER_ENABLED` / `COLLECT_SCHEDULER_TIMEZONE` | true / Asia/Shanghai | `backend/.env` | 定时调度 |

我的看法是：现在不建议拆成独立服务再加 MQ。更划算的做法是先完成 03collect优化，把采集的边界理清；以后真有需要，先在同一套代码里拆成"API 进程 + 采集 Worker 进程"，用已有的 Redis 做任务队列。 真正拆成独立服务 + MQ，等出现下面第 4 部分列的信号再做。

1. 你想要的好处，大部分已经有了，或者不需要拆服务也能拿到
想要的效果	现状
业务只负责触发，成功、重试都由采集侧处理
已经是这样。同源重试在 RetryDecorator，换源在 Gateway，失败单元补采在 run_units，状态判定在 execute_task。业务方只调用 submit / run_one，看不到这些细节
异步执行
已经是异步。submit 建好任务行后在后台执行，接口立即返回 task_id
进度回传
已经有了。Redis 的 collect:progress:{id} 加 sys_collect_tasks 表，前端轮询
采集不拖慢业务接口
这一条现在确实没做到：采集和接口在同一个进程里。但要解决它，拆进程就够了，不需要拆服务
所以拆服务加 MQ 带来的真正新增收益，主要是"进程隔离"和"以后能独立扩容"。前一个靠拆进程就能拿到，后一个以你目前的规模用不上：k8s 清单里也没看到后端多副本部署。

2. 真要拆成独立服务，会碰到的几个硬问题
数据库是共享的。 采集写入的表，正是业务直接读的表：

data_board.py 直接用 14 个 XxxRepoImpl 读原始数据。
StockInfoService 读日 K 和技术指标。
概念服务读成分股和概念指数日 K。
只拆服务、不拆数据库，就成了"分布式单体"：部署变复杂了，耦合一点没少。要拆数据库，业务读数据就得改成调采集服务的查询接口，改动面非常大。

有些调用必须同步，不能走 MQ。

实时查询：分 K、概念分时、stock_concepts、试查。这些请求要立刻拿到结果，只能留在业务侧，或者改成同步 RPC 调采集服务。

run_one 的同步语义：

/stocks/sync 和 /stocks/sync-daily-basic（stock.py:74、stock.py:114）。
/klines/collect 和批量采集（kline.py:84、kline.py:108）。
这些接口现在直接返回采集结果。改成 MQ 后要么变成异步、要求前端跟着改，这违反你定的"对外接口不变"约束；要么做成请求-响应式的 MQ，比直接调用复杂得多。

日 K 采集里混着业务逻辑。 daily_kline 走的是 StockInfoService.collect，取数之后还要算 17 个技术指标再入库。拆服务前要先想清楚：指标计算归采集服务还是业务服务？

采进度不适合走 MQ。 日 K 一次要处理 5000 多个单元，每个单元都发一条 MQ 消息给业务方，纯属浪费。进度这种高频、只需要"最新值"的状态，继续用 Redis 哈希加轮询是对的。MQ 只适合传"任务完成 / 失败"这种低频事件。

运维成本：

MQ 本身的部署和监控（RabbitMQ 或 Kafka 要进 k8s）。
投递是"至少一次"，所以任务要能安全重复执行。
死信处理、跨服务的链路追踪和排错。
一个人维护的项目，这些成本很实在。

还有一点要注意："至少一次"投递下，大多数原始表是按唯一约束 upsert 的，重复执行没问题；但 concept_snapshot 是追加写入，重复执行会多出数据。

3. 推荐分三步走
第一步（现在）：完成 03collect优化。

它产出的就是将来拆分要用的那几个接口：

CollectTaskStorePort（任务行）、CollectProgressPort（进度）。
CollectRunner（执行任务）。
CollectContext（注入依赖）。
做完之后，"提交任务"和"执行任务"之间只隔着端口。以后无论换成队列、换成独立进程还是独立服务，都只需要换端口的实现，业务代码不用动。

第二步（出现性能或稳定性问题时）：同一份代码，拆成两个进程。

同一个镜像，两个启动入口
├─ api      FastAPI：业务接口、实时查询、提交采集
│           CollectManageService.submit：建任务行 → 放进队列（Redis Stream 或 arq）
└─ worker   消费队列 → CollectRunner 执行 → 写 Redis 进度（key 不变）和任务行
            APScheduler 只在 worker 里跑（单副本）
这一步能拿到的好处：

长时间运行的采集和接口进程隔离：worker 卡住或崩溃不影响 API，可以单独重启。
tushare 的限流配额集中在 worker 一个进程里，不会因为 API 加副本而被打穿。
定时调度只有一个实例，不会因为多副本而重复触发。
另外：

实时查询留在 API 进程，因为它们用的是 pytdx 和 adata，不占 tushare 配额。
run_one 这类短的同步调用，可以继续在 API 进程里直接执行。
不需要新加 MQ：Redis 已经有了，Redis Stream 足够用。
第三步（真的需要时）：拆成独立服务，配专门的 MQ。

前提是先把数据库所有权理清：哪些表归采集服务，业务方通过什么方式读这些数据。

4. 什么时候才值得做第三步
出现下面任意一条，再考虑：

后端要多副本或水平扩展，而采集负载和接口负载需要分开扩容。
有其他系统也要用采集能力或原始数据，比如一个独立的 Agent 服务、另一个产品。
采集侧的发布节奏或技术栈要和业务侧分开，或者由不同的人维护。
数据源越来越多（akshare、东财等），采集逻辑大到需要一个独立团队或独立的代码库。
目前这几条一条都还没出现。

总结一下：你说的"业务只负责触发、采集自己管成败和重试"这个方向是对的，而且现在已经基本做到了。真正缺的是代码层面的边界（也就是 03collect优化要做的事）和进程隔离。这两样都不需要引入 MQ。要不要我把第二步"API + Worker"的方案也写成一份文档，放到 03collect优化后面作为后续阶段？
