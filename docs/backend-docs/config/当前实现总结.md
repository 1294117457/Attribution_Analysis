## 1. 整体架构：DDD 四层 + 共享层

代码按 `interface → application → domain ← infrastructure` 的依赖方向严格分层，**`domain` 零外部依赖**（不 import 任何 framework/SDK）。各业务上下文（bounded context）按 `interface / application / domain / infrastructure` 四列同构地组织在 `contexts/<ctx>/` 下。

### 1.1 物理目录布局

```
src/
├── shared/                        # 跨 context 的纯通用能力（无业务）
│   ├── interface/                 # _response 统一响应包装、validators、Page
│   ├── domain/                    # 跨 context 通用领域基类（base / repository）
│   └── infrastructure/
│       ├── config/settings.py     # pydantic-settings 单例
│       ├── connection/            # 资源连接实例（不带 Depends）
│       │   ├── db_factory.py      # db_session_factory / raw_session_factory
│       │   └── redis_client.py    # _build_client
│       ├── di/                    # 基础设施级 Depends 工厂
│       │   ├── db_session.py      # get_db / get_raw_db / *_context
│       │   └── redis_session.py   # get_redis
│       └── persistence/           # ORM 基类
│           ├── orm_base.py        # AttribBase / RawBase / Base
│           └── mixins.py          # TimestampMixin
│
├── contexts/
│   ├── auth/                      # 用户认证 + 角色/权限管理（attribution_db）
│   ├── user/                      # 自选股池 + 池级后台操作（attribution_db）
│   ├── collect/                   # 28 个采集 service + 元数据（attribution_db + raw_data_db）
│   ├── scheduler/                 # 调度契约 + 计划/运行日志（attribution_db）
│   ├── market/                    # 技术/资金/基本面查询（raw_data_db 读 + 实时计算）
│   └── concept/                   # 概念（concept_quote / concept_board / concept_query）— raw_data_db
│
├── main.py / application.py       # 入口（uvicorn 启动点）
└── shared/interface/router_compat.py   # 聚合所有 context 的 router
```

每个 context 的标准四列：

```
contexts/<ctx>/
├── application/
│   ├── service/                   # AppService，按需分子目录（collect/{tech,capital,fundamental,...}）
│   ├── bo/                        # 外部数据进入系统时的载体（按 facet 分子目录）
│   ├── port/                      # port 契约（接口 + 参数 + 契约级错误）
│   └── ...                        # dto 不在此（见下）
├── domain/
│   ├── entitys/<aggregate>/       # entity.py / repository.py / vo.py
│   ├── service/                   # 跨聚合根的领域服务（纯算法）
│   └── exceptions.py              # 业务级异常
├── infrastructure/
│   ├── adapter/                   # 外部 SDK / 调度器适配
│   ├── fetcher/                   # collect 专用：BaseFetcher + 各数据源实现
│   ├── cache/                     # Redis 机制（rate_limit / refresh_token / email_code ...）
│   ├── connect/                   # 客户端单例（tushare / adata / pytdx）
│   ├── persistence/
│   │   ├── models/                # ORM 模型
│   │   └── repositories/          # domain/repository 的 SQL/ORM 实现
│   ├── di/                        # 业务 DI 工厂（按资源类型分文件）
│   ├── security/                  # auth 用：jwt / password / key_manager / captcha / email
│   └── lifespan.py                # lifespan 启动初始化（仅 collect 有）
└── interface/
    ├── route/                     # 一个业务子模块一个文件
    ├── deps.py                    # route 层横切依赖
    └── dto/                       # request / response 分目录
```

### 1.2 强约束摘要（与 DDD.md 对齐）

| 规则 | 当前落地 |
|---|---|
| `domain` 零外部依赖 | ✅ `contexts/<x>/domain/` 内部不 import sqlalchemy / fastapi / tushare |
| 业务异常归 `domain`，port 错误归 `application/port` | ✅ `contexts.collect.domain.exceptions.InvalidParams/NotSupported` + `contexts.collect.application.port.errors.RateLimited/SourceUnavailable` |
| 业务 DI 放 `contexts/<x>/infrastructure/di/`，不放 `shared/` | ✅ shared 仅放 `db_session.py / redis_session.py`（基础设施级） |
| `config/` 只放配置 | ✅ `shared/infrastructure/config/settings.py` 仅 pydantic-settings |
| `connection/` 资源实例 + `di/` Depends 工厂分离 | ✅ 见 `db_factory.py` vs `db_session.py` |
| `interface/route/` 按业务子模块分文件 | ✅ `auth_login.py / auth_password.py / auth_register.py / route_user.py / route_role.py / route_permission.py` |
| 单文件大路由 | ❌ 不存在；collect 用了「按 facet 子目录」进一步拆分 |
| collect 的 service 按 5 个 facet 分子目录 | ✅ `application/service/{tech,capital,fundamental,news,sentiment}/` |
| collect 的 route 按 5 个 facet 分子目录 | ✅ `interface/route/{tech,capital,fundamental,news,sentiment}/__init__.py` |

## 2. 两个数据库（物理隔离）

参见 `docs/backend-docs/config/五个基本面.md`。当前实现已按 D4 阶段完成物理分库。

| 库 | SQLAlchemy Base | Session 工厂 | 内容 | 用途 |
|---|---|---|---|---|
| `attribution_db`（业务库） | `AttribBase`（=`Base`） | `db_session_factory`（via `db_async_engine`） | 11 张业务表：用户/角色/权限/采集元数据/采集 job/采集方案/股票池/池操作 | 业务对象、用户数据、调度元数据 |
| `raw_data_db`（采集库） | `RawBase` | `raw_session_factory`（via `raw_async_engine`） | 27 张采集表（5 个面） | 全部 Tushare / 第三方数据 |

- 配置在 `Settings`：`DATABASE_URL` + `RAW_DATABASE_URL`（允许同 URL 走 dev 模式）。
- `shared.infrastructure.persistence.orm_base` 同时声明 `AttribBase / RawBase / Base(=AttribBase)`，建模时按归属选基类。

### 2.1 attribution_db（11 张）

```
sys_users / sys_roles / sys_permissions
sys_user_roles / sys_role_permissions
sys_data_ports           -- 端口元数据
sys_collect_jobs         -- 采集执行实例
sys_collect_plans        -- 采集方案
sys_collect_plan_items   -- 采集方案项
stock_pools              -- 自选股池
stock_pool_members       -- 池-股票关联
pool_operations          -- 池操作后台任务
```

### 2.2 raw_data_db（27 张，5 个面）

| 面 | 表数 | 表前缀 | 备注 |
|---|---:|---|---|
| 技术面 | 5 | `tech_` | `tech_kline_daily / tech_adj_factor / tech_name_change / tech_suspend / tech_calendar`；MA/EMA/MACD 等指标**不入库**，按需实时算 |
| 资金面 | 7 | `capital_` | `capital_moneyflow / capital_margin / capital_margin_detail / capital_top_list / capital_top_inst / capital_block_trade / capital_holder_num` |
| 基本面 | 13 | `fundamental_` | `fundamental_daily_basic / fundamental_report / fundamental_top10 / fundamental_top10_float / fundamental_dividend / fundamental_index_member / fundamental_sector_daily / fundamental_market_daily / fundamental_stock_info` + 概念 4 张 `fundamental_concept*` |
| 新闻面 | 0 | `news_` | 尚未实现 |
| 情绪面 | 0 | `sentiment_` | 尚未实现 |

> `daily_basic` 同源同时含 PE 和换手率，**都进 `fundamental_daily_basic`**，应用层按字段归类（换手率算资金语义、PE 算基本语义）。

### 2.3 跨库 join 处理

两个 session 互不干扰：
- route 层可同时 `Depends(get_db)` + `Depends(get_raw_db)`，两个 session 两个事务。
- 应用层在**内存合并**（不在 SQL 层做跨库 join）。

## 3. 6 个 bounded context

### 3.1 `auth`（用户与认证）

- **库**：`attribution_db`
- **domain**：`User / Role / Permission` 实体 + 仓储接口 + 业务异常（`InvalidCredentialsError / UserAlreadyExistsError / TokenInvalidError ...`）
- **port（application/port 内）**：`PasswordHasherPort / CaptchaPort / EmailVerificationPort / JwtPort` —— 由 `infrastructure/security/` 实现
- **infrastructure/security/**：`password.py / key_manager.py / jwt_service.py / captcha.py / email.py`
- **infrastructure/cache/**：`refresh_token.py`（Redis refresh token）+ `email_code.py`（邮箱验证码）
- **infrastructure/adapter/**：`email_verification.py`（SMTP 适配）+ `auth_port_adapters.py`（port 适配）
- **interface/route/**：`auth_login.py / auth_register.py / auth_password.py` + `route_user.py / route_role.py / route_permission.py`（用户/角色/权限管理）
- **入口**：`POST /api/auth/login`、`/api/auth/register`、`/api/auth/password/...` + `/api/users`、`/api/roles`、`/api/permissions`

### 3.2 `user`（自选股池 + 池级后台操作）

- **库**：`attribution_db`
- **domain**：`stock_pool/entity.py`、`stock_pool/vo.py`、`stock_pool/repository.py`
- **application**：`stock_pool_service.py` + `port/operation_dispatcher_port.py`
- **infrastructure/adapter/background/**：`operation_dispatcher.py`（后台池级操作的执行器）
- **interface/route/pool.py**：完整的池 CRUD + 成员管理 + 反向查询（by-symbol）+ 池级操作（`POST /pools/{id}/operations` 发起后台采集）+ 操作进度查询
- **DTO**：`pool_operation.py / pool.py`（request/response 分目录）

### 3.3 `collect`（采集元数据 + 28 个采集 service）

这是**最大、最核心**的 context，负责把外部数据落进 `raw_data_db`，并把元数据写进 `attribution_db`。

#### 3.3.1 三层抽象：`Fetcher → Service → Route`

| 层 | 职责 | 位置 |
|---|---|---|
| **Fetcher** | 只调 SDK 拿数据，返回 `list[BO]`（Pydantic）。**不**限流、不并发、不缓存、不入库 | `infrastructure/fetcher/{tech,capital,fundamental,news}/<业务><源>Fetcher.py` |
| **Service** | 编排采集用例：限流 + 并发 + 调 fetcher + 解析 BO + 写库 + 返回 `CollectResult` | `application/service/{tech,capital,fundamental,news,sentiment}/<业务>_service.py` |
| **Route** | HTTP 入口，`Depends(get_xxx_service)` 注入 service，统一 `_run()` 把 `mode` 注入 params | `interface/route/{tech,capital,fundamental,news,sentiment}/__init__.py` |

- `BaseFetcher`（`infrastructure/fetcher/base.py`）是唯一抽象类；fetcher 直接 `fetch(**params) -> list[BaseModel]`，签名简洁。
- `CollectService` 是 `Protocol`（`application/service/base.py`），通过 class attribute 声明 `name / facet / sub_facet / DEFAULT_PARAMS / RATE_LIMIT / CONCURRENCY`。
- `CollectResult`（`@dataclass(frozen=True)`）一次采集返回：`total / success / fail / skip / saved / message`。
- `application/port/` 只保留契约级错误与参数类型；**不再持有 SchedulerPort**（已迁到 `contexts.scheduler.application.port`，参考 DDD.md step7）。

#### 3.3.2 28 个 service 的 facet 分布

| Facet | Service 数 | Service 名（按 `name`） |
|---|---:|---|
| tech | 5 | `daily_kline / minute_kline / adj_factor / suspend / name_change` |
| capital | 9 | `moneyflow / moneyflow_hsgt / top_list / top_inst / block_trade / margin / hsgt_top10 / limit_list_d / holder_number` |
| fundamental | 12 | `daily_basic / fin_income / top10_holders / top10_floatholders / dividend / stock_basic / stock_concepts / concept_list / concept_members / concept_index_daily / concept_minute / concept_snapshot` |
| news | 1 | `news`（占位） |
| sentiment | 1 | `sentiment`（占位，catalog 中隐藏） |

URL 风格：

```
POST /api/collect/{facet}/{service_name}            采集入口（写库 or 实时）
GET  /api/collect/services                          28 service 元数据 catalog
GET  /api/collect/query/{service_name}              实时查询（仅 supports_query=true）
```

#### 3.3.3 Service 的统一范式（典型代表：`DailyKlineService`）

```python
class DailyKlineService:
    name = "daily_kline"
    facet = "tech"
    sub_facet = "kline_daily"
    DEFAULT_PARAMS = {"symbols": [], "start_date": None, "end_date": None}
    RATE_LIMIT = ("tushare", 200, 60)   # 数据源名 / max / window
    CONCURRENCY = 5

    def __init__(self, fetcher=None): ...  # DefaultConstruct，无外部依赖
    async def collect(self, params) -> CollectResult: ...
    async def get(self, ...) -> list[dict]: ...   # 实时查询（可选）
```

要点：
1. `symbols` 留空 → 自动 `list_all_a_symbols()`（拉全 A 股票代码）。
2. `index_codes` 留空 → 自动 `list_all_concept_codes()`（从 `concept` 表读，依赖 `concept_list` 先入库）。
3. `CONCURRENCY` 用 `asyncio.Semaphore` 控制并发。
4. `RATE_LIMIT` 通过 Redis 滑动窗口（`collect:rl:tushare` / `collect:rl:adata`）共享配额。
5. 命中 `RateLimited` → 退避 `retry_after` 后重试（最多 3 次）。
6. 入库用 `pg_insert(...).on_conflict_do_update(...)` upsert，唯一键见五个基本面.md §2.2。

#### 3.3.4 数据源客户端单例

| 数据源 | 位置 | 备注 |
|---|---|---|
| Tushare | `infrastructure/connect/tushare_client.py` | 模块级单例 `get_tushare_client()`；限频异常翻译为 `RateLimited`，其它翻译为 `SourceUnavailable` |
| Adata | `infrastructure/connect/adata_client.py` | 同花顺概念数据 |
| Pytdx | `infrastructure/connect/pytdx_client.py` | 实时行情（`jstdx.gtjas.com:7709`），用于 `minute_kline` / `concept_minute` |

#### 3.3.5 限流与并发机制

- **限流**（`infrastructure/cache/rate_limit.py`）：
  - 原子原语 `check_rate_limit(key, max, window)`（Redis INCR+EXPIRE pipeline）。
  - 业务策略 `check(rate_limit_tuple)`：命中即 `await asyncio.sleep(window)` 等待。
  - 全局共享键：`collect:rl:tushare`（200/60s）+ `collect:rl:adata`（100/60s）。
- **并发**：service 内部 `asyncio.Semaphore(CONCURRENCY)` + `asyncio.gather(...)`。

#### 3.3.6 lifespan 初始化

`contexts/collect/infrastructure/lifespan.py` 负责：
- 初始化 `ServiceRegistry`（内存中按 `name → ServiceClass` 注册，供前端 catalog 与 query endpoint 反射）。
- 启动调度器（条件性，受 `COLLECT_SCHEDULER_ENABLED` 控制）。
- 关闭连接池（`close_db`）。

## 4. 依赖注入与生命周期（参考 `depend管理.md`）

### 4.1 三层 DI 分工

| 层 | 职责 | 文件 |
|---|---|---|
| `shared/infrastructure/connection/` | 资源连接实例（engine / sessionmaker / redis client），**不带** FastAPI Depends | `db_factory.py` / `redis_client.py` |
| `shared/infrastructure/di/` | 基础设施级 FastAPI Depends 工厂（所有 context 都会用） | `db_session.py` / `redis_session.py` |
| `contexts/<x>/infrastructure/di/` | **业务** DI 工厂（本 context 业务 service 的 Depends 工厂，按资源类型分文件） | 例如 `auth/infrastructure/di/auth_service.py`、`collect/infrastructure/di/collect_service.py`、`market/infrastructure/di/stock_info.py` |

### 4.2 DB session 的两种用法

| 入口 | 场景 | 函数 | 事务边界 |
|---|---|---|---|
| FastAPI Depends | route 层 | `get_db / get_raw_db` | 跟随请求；yield/try/except/finally（commit/rollback/close） |
| `async with` 上下文 | service 层后台任务 / 调度任务 | `get_db_context / get_raw_db_context` | 跟随 `async with` 块 |

- 两个 session 互不干扰；一个 route 可以同时注入 `get_db` + `get_raw_db`，互不串事务。
- 池用 `NullPool`（避免事件循环绑定问题）+ `pool_pre_ping=True`。

### 4.3 Redis 客户端

- 单例（无状态），所有需要缓存的地方共用一个 client。
- `get_redis()` 在 `shared/infrastructure/di/redis_session.py`，**直接 import 直接调用**也是允许的（无事务）。
- 当前 Redis 用法：限流（`collect:rl:tushare / adata`）+ 邮箱验证码 + refresh token 存储。

### 4.4 业务 service 的注入路径

标准范式（route → service → session 全部走 Depends）：

```
route 函数 Depends(get_xxx_service)  ←  contexts/<x>/infrastructure/di/<resource>.py
         ↓
service 内部需要 DB 时：
    ① 走 Depends 链（route 注入 service 时一并注入 session）
    ② 走 get_db_context() 独立事务（后台/调度/collect.service 内部自己起任务）
```

collect 的 service **无外部依赖**（fetcher 自己 `get_tushare_client()`），所以 DI 工厂只 `return XxxService()` —— **无状态、线程安全**。

### 4.5 启动流程

```
进程启动
  ├─ Settings() 加载 .env（pydantic-settings 单例 + lru_cache + 线程锁）
  ├─ db_factory.py：构造 db_async_engine / raw_async_engine + sessionmaker
  ├─ redis_client.py：构造 aioreids client 单例
  ├─ FastAPI lifespan：
  │     ├─ collect.infrastructure.lifespan.init_service_registry()
  │     ├─ collect.infrastructure.lifespan.init_schedule_runner()（受 COLLECT_SCHEDULER_ENABLED 控制）
  │     └─ 其它 context 的初始化（按需）
  └─ router_compat.py 聚合所有 context 的 router → main.app.include_router
```

请求到来 → FastAPI `dependency_cache` 维护请求级 Depends 树 → route 函数 → 返回 `_response.ok({...})` 包装。

## 6. 端到端时序：一次「按 symbol 批量采集日 K 线」

1. **HTTP**：前端 `POST /api/collect/tech/daily_kline`，body `{"mode": "full", "params": {"symbols": [], "start_date": null, "end_date": null}}`
2. **route**（`interface/route/tech/__init__.py`）：`_run(svc, body)` → 把 `mode` 合并进 `params` → `svc.collect(merged)`
3. **DI 工厂**（`infrastructure/di/collect_service.py:get_daily_kline_service`）：`return DailyKlineService()`（DefaultConstruct）
4. **Service.collect**（`application/service/tech/daily_kline_service.py`）：
   - `symbols` 为空 → 调 `list_all_a_symbols()` 拉全 A 股票代码（用 tushare `stock_basic list_status=L`）
   - 用 `asyncio.Semaphore(CONCURRENCY=5)` + `asyncio.gather` 并发跑
   - 每个 symbol：调 `check(RATE_LIMIT)` → 调 `fetcher.fetch(symbol=..., start_date=..., end_date=...)` → 拿到 `list[KlineBO]`
5. **Fetcher**（`infrastructure/fetcher/tech/DailyKlineTushareFetcher.py`）：
   - `ts_code = symbol_to_ts_code(symbol)`（6 位 → 带后缀的转换在 fetcher 里做）
   - `await tushare_client.query("daily", ts_code=..., start_date=..., end_date=...)`
   - tushare 限频 → 翻译为 `RateLimited(retry_after=60)`
   - 解析为 `list[KlineBO]`（Pydantic）
6. **入库**（service 内部）：
   - `pg_insert(TechKlineDailyDB).values([...]).on_conflict_do_update(index_elements=["symbol","date"], set_={...})`
   - `async with raw_session_factory() as session: ... await session.commit()`
7. **返回**：`CollectResult(total, success, fail, saved, message).to_dict()` → `R.ok(...)` 包装 → JSON
8. **调度场景**：scheduler 调 `ServiceRegistry.get(name).collect(params)`（与 HTTP 走**同一个** service.collect，保证行为一致）

## 7. 关键设计决策与权衡

| 决策 | 落地点 | 收益 |
|---|---|---|
| 28 个 service 统一抽象 | `CollectService` Protocol + class attribute 元数据 | HTTP / 调度 / catalog 三处共用一份代码；前端元数据可反射生成 UI |
| `fetcher` 只负责调 SDK | `BaseFetcher` 极简抽象 | 限流/并发/入库策略由 service 决定，可按 service 差异化 |
| `tushare_client` 模块级单例 | `get_tushare_client()` lazy init | 复用 HTTP 连接池；service DefaultConstruct |
| 物理分库（业务 / 采集） | `AttribBase / RawBase` 双 Base + 双 engine | 备份/迁移/扩展独立；ORM 模型不串 |
| 共享 Redis 限流配额 | `collect:rl:{source}` 全局键 | 22 个 service 不会因并发打爆数据源 |
| Scheduler 抽到独立 context | `contexts/scheduler` | collect 不再耦合调度元数据，契约清晰 |
| 技术指标放 `domain/service/` | `IndicatorCalculator` | 纯函数式、零外部依赖、可单测；不入库按需实时算 |
| 业务异常 vs port 错误分层 | `domain/exceptions.py` + `application/port/errors.py` | 调用方依据异常类型决定「重试/换源/降级」 |
| 业务 DI 按 context 自管理 | `contexts/<x>/infrastructure/di/<resource>.py` | 改业务不动 `shared/`；shared 只装基础设施级 DI |
| 路由按业务子模块分文件 | `auth_login.py / auth_password.py ...` | 单文件不膨胀，跨文件搜索清晰 |
