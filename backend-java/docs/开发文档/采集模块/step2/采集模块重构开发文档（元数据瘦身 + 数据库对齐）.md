## 0. 一句话结论

> **元数据层面**：前端既然只按 `strategy` 出形态，那 service 就不该再暴露「用户可填的参数」和「二级分组」——`DEFAULT_PARAMS` 和 `sub_facet` 是**已被前端形态取代的历史包袱**，删掉；**`facet` 保持不变**（最终决策：service 属性 / `collect_logs` 列名 / 前端目录树三处同名同义，不引入 `category`）。
>
> **数据库层面**：🔴 **远端库和代码已经完全对不上**——10 张表名不一致、1 张表本地有远端没有、26 张表时间列类型是 `timestamp without time zone`（代码按 `timestamptz` 写）、`collect_logs` 表结构完全不同（远端是**旧版**，本地代码是**新版**）。**当前所有采集任务都会失败**。本轮出可执行的 SQL 对齐脚本。

## 4. 数据库对齐方案（远端 `8.148.204.54`）

### 4.0 决策：改代码 vs 改库

| 方案 | 说明 | 判断 |
|---|---|---|
| A. 改远端表名 → 规范名 | 库表名改成代码期望的 `tech_kline_daily` 等 | ❌ `tech_kline_daily` 比远端的 `tech_daily` 更啰嗦；`capital_holder_num` 比 `capital_stk_holdernumber` 更贴近领域词 |
| **B. 改代码表名 → 库现状** | 代码 ORM 改成远端实际表名 | ✅ **采纳** —— 远端表名符合「五分类前缀 + 领域词」规范；改代码不动数据、零风险、可回滚 |
| C. 双向都改 | 改成第三套名字 | ❌ 无收益，多一次迁移 |

> **结论：采纳 B —— 以远端 dump 为权威，改本地代码（ORM `__tablename__`）去对齐远端表名。**
> **数据一行不动**，无需 RENAME，无需备份。

**唯一的例外**：`market_limit_list` → 远端是 `capital_limit_list_d`。
`market_` **不是**五分类前缀之一（违反《多库分工与数据源规范》§7.2），但 `capital_limit_list_d` 带 `_d` 后缀（daily）也是事实。
→ **采纳远端 `capital_limit_list_d`**，并在规范文档里把该例外登记为「已知例外」（`limit_list` 接口本身也叫 `limit_list_d`）。

### 4.2 时间列类型对齐（26 张表 / 53 列）

**问题**：本地 ORM 用 `DateTime(timezone=True)`（= `timestamptz`），远端全是 `timestamp without time zone`。
`core/db.py` 的注释已明确警告：*「asyncpg 写 aware datetime 到 naive 列会直接报错」*。

**但实际会怎样？** asyncpg 对 `timestamp without time zone` 传 aware datetime → 抛
`asyncpg.exceptions.DataError: invalid input for query argument ... (can't subtract offset-naive and offset-aware datetimes)`。
→ **所有带 `TimestampMixin` 的 INSERT 全部失败**。

**SQL（对 26 张表批量执行）**：

```sql
-- 对远端 raw_data 库所有 raw_data 库的 timestamp without time zone 列改 timestamptz
DO $$
DECLARE r RECORD;
BEGIN
  FOR r IN
    SELECT c.table_name, c.column_name
    FROM information_schema.columns c
    WHERE c.table_schema = 'public'
      AND c.data_type = 'timestamp without time zone'
      AND c.column_name IN ('created_at','updated_at','started_at','finished_at',
                            'synced_at','ann_date','added_at','granted_at')
  LOOP
    EXECUTE format('ALTER TABLE public.%I ALTER COLUMN %I TYPE timestamptz USING %I AT TIME ZONE ''Asia/Shanghai''',
                   r.table_name, r.column_name, r.column_name);
  END LOOP;
END $$;
```

> ⚠️ **`USING ... AT TIME ZONE 'Asia/Shanghai'`**：远端库 `SET timezone = 'Asia/Shanghai'`（见 `postgres/initdb/01-init.sql`），
> 且 dump 里 `created_at` 默认值是 `now()`。naive 值本身就是**上海本地时间**，
> 直接 `AT TIME ZONE 'Asia/Shanghai'` 才是正确的语义（把本地时间解释为上海时区，转成 UTC 存储）。
> 若用 `AT TIME ZONE 'UTC'` 会整体偏移 8 小时 —— **数据全错**。

**影响行数极小**：只有 `tech_daily`(188,933)、`fundamental_stock_basic`(5,576)、`tech_adj_factor`(3,879) 有数据，
其中 `created_at`/`updated_at` 是 `now()` 默认值，偏移 8 小时对这两列影响可忽略（仅审计用途）。

### 4.3 `collect_logs` 表统一（attribution 库）

**决策**：远端 `collect_logs` 是**旧结构**（50 行），远端 `collect_log`（单数）是**接近新版的结构**（1 行，缺 9 列）。
本地代码（Python ORM / Java PO / `postgres/initdb/02-collect-logs.sql`）用的是**新版完整结构**。

→ **方案**：在远端**重建** `collect_logs` 为新版完整结构，把 `collect_log`（单数）的 1 行数据迁移过去，然后**删除** `collect_log`（单数）。

```sql
-- ① 归档旧表（留 1 个月）
ALTER TABLE collect_logs RENAME TO collect_logs_legacy_20261029;
```

#### 4.4.1 三张「语义不同」的表 —— 需要业务决策

`capital_hsgt_top10` / `capital_moneyflow_hsgt` / `capital_limit_list_d` 这三张表，
**远端存的是「每日排行榜」数据**（带 `rank`/`close`/`p_change`/`buy`/`sell`），
而**本地 ORM 声明的是「持仓/资金流汇总」结构**。

| service | 上游 API | 远端表实际存的内容 | 本地 ORM 期望 |
|---|---|---|---|
| `hsgt_top10` | tushare `hsgt_top10` | 每日十大成交股排行 | 持仓天数/占比/市值 |
| `moneyflow_hsgt` | tushare `moneyflow_hsgt` | 每日十大成交股排行 | 交易所维度的买/卖/净额 |
| `limit_list` | tushare `limit_list_d` | 涨跌停明细（含封单额） | 涨停板（连板数/封板强度/原因） |

**三个选项**：

| 选项 | 说明 | 工作量 | 风险 |
|---|---|---|---|
| **① 远端 ADD 缺失列 + 保留远端列**（**推荐**） | 远端表**加**本地 ORM 缺的列（都设 nullable），本地 ORM 声明**两个库的列并集** | 小 | 低 —— 不动已有数据 |
| ② 远端表重建为本地 ORM 结构 | 远端表是空的（0 行）→ 直接 DROP + CREATE | 中 | 低（0 行数据） |
| ③ 改本地 ORM 对齐远端 | 改 ORM 列名以匹配远端 | 中 | 中 —— 要改 service 的字段映射 |

> **推荐 ①**，理由：三张表**远端都是 0 行**，无论①还是②都不丢数据；
> 但①（ADD COLUMN）**可逆、不删列、保留远端已有的完整 Tushare 原始字段**（`rank`/`close`/`buy`/`sell` 等对后续业务分析有用），
> 而②会丢掉这些字段。①的代价只是本地 ORM 多声明几个 nullable 列。

> ##### ⚠️ Step 3 结论（本节方案已被**方案 A** 取代）
>
> 上面的选项①最终**被 Step 3 推翻** —— 原因是**实调上游后发现的前提是错的**：

## 6. 风险与红线

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **时间列 `AT TIME ZONE` 用错时区** | 必须用 `'Asia/Shanghai'`；用 `'UTC'` 会整体偏移 8 小时 |
| R2 | **`collect_logs` 重建丢历史** | 迁移前 `pg_dump` 备份；旧表 RENAME 保留 1 个月不删 |
| R3 | **RENAME 后旧代码仍在跑** | 迁移必须与代码发布**同时**；建议先停 collector |
| R4 | **远端表 `id` 序列随 RENAME 改名** | PG 中序列名独立于表名（`OWNED BY` 跟随），RENAME 表不影响序列；**但**我们不改库表名，只改代码 → 无此风险 |
| R5 | ~~`capital_hsgt_top10` 语义错配~~ | ✅ **Step 3 已按方案 A 彻底对齐** —— 实调上游核对后重建远端表 + 改 ORM/PO/fetcher/service；详见 §4.4.1 的 Step 3 结论 |
| R6 | **DDL 锁表** | 26 张表共 53 列，`ALTER TYPE` 是重写表的操作 → **在低峰期执行**；`tech_daily`(18.9 万行) 耗时最长 |
| R7 | ~~前端 `path` 拼接依赖 category~~ | ✅ **已消解** —— 最终决策统一用 `facet`，`api.ts` 的 `createCollectTask` 里 `svc?.facet` 无需改动 |
| R8 | ★ **迁移脚本内的 DDL 顺序影响守卫条件** | ⚠️ **实际踩到**：`03-rebuild-collect-logs.sql` 的「迁旧 50 行」守卫写成 `EXISTS(legacy) AND NOT EXISTS(collect_log)`，但 `collect_log`（单数）在**后面**才 DROP → 条件恒 false → 50 行被**静默跳过**。<br>**教训**：DO 块守卫必须逐段校验影响行数；已由 `03b-migrate-legacy-rows.sql` 补迁 |
