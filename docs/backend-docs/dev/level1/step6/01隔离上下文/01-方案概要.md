## 0. 一句话总结

把现在"以层为骨"（`domain/` / `application/` / `infrastructure/` / `route/`）的目录
改成"**以 8 个有界上下文为骨、每个 context 内部再分 4 层**"的目录。**单进程、单数据库
仍然保留**，但 `import` 方向、文件归属、测试边界都按 context 收紧。

> **本阶段不修改代码**，仅产出方案与目录骨架。

## 1. 背景与动机

### 1.1 现状

| 维度 | 现状 |
| :-- | :-- |
| **目录** | 按"层"切：`domain/entitys/{kline,concept,stock_pool,...}/`、`application/service/`、`application/port/`、`infrastructure/persistence/`、`route/api/v1/` |
| **业务模块** | 同一聚合根的所有物散落在多个层目录：domain 实现在 `entitys/<mod>/`，应用服务在 `application/service/<mod>_service.py`，Port 在 `application/port/<mod>_port.py` 或 `application/port/data/`，仓储实现在 `infrastructure/persistence/repositories/<mod>_repository.py`，路由在 `route/api/v1/<mod>.py` |
| **context 边界** | **没有显式边界**。`ConceptService` 被 `stock_info` / `market` / `concept_board` 三个模块共用，DI 在 `infrastructure/config/di.py` 单点编排 |
| **跨模块复用** | 走共享层（`ConceptBriefService`、`IndicatorCalculator`、`DataQueryService`）和共享端口（`DataGatewayPort`） |
| **典型问题** | ① 改一个聚合根要动 5 个目录；② 不知道"加一个新模块"该放哪；③ 业务边界靠口口相传；④ 跨 context 调用无审计 |

### 1.2 动机

业务增长（概念 v2 已上线、`stock_pool` 复杂化、归因分析在筹备）暴露了 3 类问题：

1. **改一个聚合根要扫多个目录**。`stock_pool` 的改动通常横跨 `domain/entitys/stock_pool/`、`application/service/stock_pool_service.py`、`application/port/operation_dispatcher_port.py`、`infrastructure/persistence/repositories/{pool,pool_operation}_repository.py`、`route/api/v1/pool.py`、`route/dto/{request,response}/pool*.py`。
2. **没有"业务边界"的概念**。`ConceptService` 既被 `concept_board` 用，又被 `stock_info` 用，又被 `market` 用——但这三处对概念的"视角"其实并不一样。
3. **未来要加 news / sentiment / 归因时不知道放哪**。news 的 BOs/适配器会撑爆 `application/port/data/`（已经 8 个文件了）。

**结论**：层优先（layer-first）的目录在 1~2 个聚合根时好用，5+ 个聚合根 + 跨模块复用时开始失控。
切到**上下文优先（context-first）**，每个 context 自带 4 层。

## 2. 目标

### 2.1 核心目标

- **每个业务模块（=有界上下文）独立可读**——打开一个目录就能看到这个 context 的全部物（domain、service、port、repo、route、dto）。
- **跨 context 调用走"应用服务层 + Port"**——禁止 context 之间直接 `import` 对方的 domain。
- **占位 context 有明确契约**——`news` / `sentiment` / `user` 三个占位从第一天起就定义好"将来要有什么"。

### 2.2 非目标（本期不做）

- **不改业务逻辑**。所有 service、repo、entity 的代码正文保持不变。
- **不改数据库 schema、不改 API 路径、不改前端调用方式**。
- **不引入新的依赖**（不引入 fastapi-utils / dependency-injector / litestar / anyio queue 等）。
- **不拆进程**。保持模块化单体（modular monolith）。
- **不重写端口**。`DataGatewayPort` / `CollectPort` 等仍然单点编排，只是物理位置变化。
- **不强制"应用层不依赖基础设施"**——DI 工厂仍由 `infrastructure/config/di.py` 负责（DDD 严格派会在后续步骤里做）。

### 2.3 验收标准

| 编号 | 标准 |
| :-- | :-- |
| AC-1 | `src/contexts/{name}/{domain,application,infrastructure,interface,bootstrap.py}` 5 部分都存在（占位 context 至少 README） |
| AC-2 | `application/grep_infra.txt`（脚本扫描）输出空——`application/` 任何文件都不再 `import infrastructure.*` |
| AC-3 | `domain/grep_external.txt` 输出空——`domain/` 任何文件都不再 import FastAPI / SQLAlchemy / Pydantic（但 `domain/base.py` 是个例外，它本来就纯标准库） |
| AC-4 | `contexts/` 之外**不再有** `entitys/<module>/`、`application/service/<module>_service.py`（仅 shared 例外） |
| AC-5 | 启动、采集端到端、采集 23 任务、HTTP 接口路径全部不变 |
| AC-6 | 前端无需改动（API 路径一致） |
| AC-7 | 旧 import 路径在 `application/legacy_compat.py` 里仍可被外部代码 import（向后兼容） |

## 4. 每个 context 的内部结构

### 4.1 四层 + 一启动文件

```
src/contexts/{name}/
├── domain/                    领域层（核心；不依赖 SQLAlchemy / FastAPI / Pydantic）
│   ├── entity.py              聚合根实体（多文件可拆 entity/ 子包）
│   ├── vo.py                  值对象
│   ├── repository.py          仓储接口（Protocol）
│   ├── service.py             领域服务（无 IO 纯规则；多文件可拆 service/ 子包）
│   ├── event.py               领域事件
│   └── exception.py           领域异常
│
├── application/               应用层（用例编排；只依赖 domain + port）
│   ├── service/               应用服务
│   ├── port/                  端口定义（对内 / 对外）—— context 对外暴露什么接口
│   │   ├── query.py           读 Port（如 KlineQueryPort）
│   │   ├── command.py         写 Port
│   │   └── event.py           事件 Port（订阅其他 context 的事件）
│   └── dto/                   应用层 DTO（可选；不强求）
│
├── infrastructure/            基础设施层（Port 的具体实现）
│   ├── persistence/           SQLAlchemy 模型 + 仓储实现
│   │   ├── models/            ORM 模型（按归属聚合；不再散在 14+ 文件里）
│   │   └── repository.py      仓储实现（继承 domain 的 Repository Protocol）
│   ├── adapter/               外部适配器（SDK、第三方 API、缓存、调度器、消息）
│   ├── security/              鉴权相关（仅 auth context 有）
│   └── mapping/               ORM ↔ domain 转换器（若复杂）
│
├── interface/                 接口层（HTTP 路由 / DTO / 中间件）
│   ├── route.py               FastAPI 路由（与本 context 业务对齐）
│   ├── schema.py              Pydantic schema（请求 / 响应）
│   ├── event_handler.py       事件处理（若订阅了其他 context 的事件）
│   └── middleware.py          中间件（按需）
│
└── bootstrap.py               本 context 的 DI 装配（声明本 context 对外暴露什么、依赖什么）
```

### 4.2 4 层职责的精炼

| 层 | 可依赖 | 不可依赖 | 主要产出 |
| :-- | :-- | :-- | :-- |
| **domain** | stdlib、同一 context 的其他 domain 文件 | SQLAlchemy、FastAPI、Pydantic、redis、其他 context | 实体、值对象、领域服务、仓储协议、领域事件、领域异常 |
| **application** | domain、本 context 的 port、其他 context 的 **port** | 其他 context 的 domain、SQLAlchemy、FastAPI、redis | 应用服务、port 定义、DTO |
| **infrastructure** | domain、application、SQLAlchemy、Redis、第三方 SDK | FastAPI | ORM、仓储实现、适配器、配置读取 |
| **interface** | domain、application、FastAPI | — | 路由、schema、handler |

### 4.3 context 的"对外接口"约定

每个 context 通过 `bootstrap.py` 声明：

```python
# contexts/concept/bootstrap.py（草案，**本期不实现**）
from dataclasses import dataclass

@dataclass(frozen=True)
class ConceptPort:
    """对外暴露的概念服务（其他 context 仅看这一个 facade）"""
    query_port: object   # type: ConceptQueryPort（domain 层定义）
    command_port: object # type: ConceptCommandPort
    event_subscriber: object  # type: ConceptEventSubscriber（订阅市场事件）

@dataclass(frozen=True)
class ConceptContext:
    """本 context 的 DI 容器（app 层组合）"""
    port: ConceptPort
    internal: object  # type: ConceptInternalDI（本 context 内部使用）
```

> 本期**不强制**使用 `bootstrap.py` 的容器结构——只要求文件存在 + 注释说明未来形态。

### 4.4 占位 context 的最小内容

`news` / `sentiment` / `user`（部分字段）虽然是占位，但**第一周就要写好契约**：

```
contexts/news/

├── domain/
│   └── .gitkeep
├── application/
│   └── port/
│       └── news_port.py    # 阶段 1 不实现，只写 Protocol 和 BO 定义

```

> `user` 阶段 1 要实现 `stock_pool` 子模块（迁移现有），所以 `user` 不完全是占位。

## 5. 应用装配层与共享设施

### 5.1 app/ 应用装配

```
src/app/
├── main.py             旧 main.py 上提；调各 context 的 register(app) / wire()
├── config.py           旧 settings.py + DI 重组
├── lifespan.py         旧 lifespan 逻辑
├── middleware.py       跨 context 中间件（CORS / trace / 全局异常）
└── container.py        顶层 DI 容器（组合各 context 的 bootstrap）
```

> 本期**不强行**抽出 `container.py`——只在 `main.py` 顶部按顺序 `setup_collect()` /
> `setup_market()` / `setup_concept()` / `setup_user()` / `setup_auth()`，让"启动序列"可见。
> 容器是更进一步的工程化（步骤 4 再说）。

### 5.2 shared/ 跨 context 共享

```
src/shared/
├── domain/
│   ├── base.py             旧 domain/base.py
│   └── types.py            公共类型（TradeDate / Symbol / IndexCode）
├── application/
│   └── port/
│       └── page.py         旧 application/port/page.py（Page[T]）
├── interface/
│   └── response.py         旧 route/api/_response.py（统一响应壳）
└── infrastructure/
    ├── persistence/
    │   ├── connection.py   AsyncSessionLocal / async_engine / close_db
    │   └── schema_init.py  init.sql 校验
    ├── cache/
    │   └── redis_client.py
    └── config/
        └── settings.py     Pydantic Settings
```

> `shared/` 只放**真的有跨 context 复用价值**的东西。谨慎使用，宁可先复制后提取。

### 5.3 不放进 shared 的（反例）

- `ConceptBriefService` → 进 `contexts/concept/domain/service/`，被 market 跨用通过 `ConceptPort`。
- `IndicatorCalculator` → 进 `contexts/market/domain/service/`，concept 反查"涨幅"通过 `MarketPort`。
- `DataQueryService` → 进 `contexts/data/application/service/`。
- `DataGatewayPort` → 进 `contexts/data/application/port/`。
- `CollectRunner` / `CollectContext` → 进 `contexts/collect/application/collect/`。

## 7. 与本节相关的对话备忘（步骤 5 后）

> 这是上一节对话里沉淀出的"为什么"，供后续步骤 4 / 5 / 6 翻查。

- **Q：为什么概念独立 context？** 概念有自己的聚合根（`Concept` + `ConceptMember` + `ConceptSnapshot` + `ConceptIndexTH`）、独立的"成分股动态性"、独立的算法（brief/policy/realtime）；不像 market 是"事实记录"，概念是"分类/归因"。严格说 market 内"前 4 类面"归 market 也合理（数值时序），但"事件型"（新闻/事件）严格说也独立。
- **Q：news / sentiment / user 是不是也要单独 context？** 满足"独立聚合根 + 独立业务行为 + 独立数据源/算法"任一即考虑独立；news 满足全部、sentiment 满足算法 + 数据源、user 满足业务行为 + 隐私。
- **Q：每个 context 的分层？** `domain / application / infrastructure / interface` 四层 + `bootstrap.py` 一个 DI 入口。
- **Q：单体 vs 微服务？** 优先**模块化单体**——`shared` infra + 单进程 + 单数据库。理由：团队 1~2 人、业务探索期、跨 context 事务多。未来如要拆：先拆 DB schema → 再拆进程 → 最后全微服务。
