## 1. 当前架构总览

### 1.1 依赖方向

```
route  →  application  →  domain  ←  infrastructure
   │           │                       │
   └──── DTO/Response 模型定义 ─────────┘
```

实际代码验证结论：**依赖方向没有反向违反**。具体扫描结果：

- `domain/` 不 import `route/`、`application/`、`infrastructure/`、SQLAlchemy、FastAPI、Pydantic——**符合 DDD §1**。
- `application/` 不直接 import SQLAlchemy 或 ORM 模型——**符合 DDD §2.2**（个别 `KlineAppService` 例外，见 02 章）。
- `infrastructure/` 实现 `domain/repository` 接口和 `application/port` 接口——**符合 DDD §2.4**。

### 1.2 各层规模

| 层 | 文件数 | 代码行（估） | 主要目录 |
|---|---|---|---|
| `route/` | 18 | ~1.5k | `api/v1/`、`dto/{request,response}/` |
| `application/` | 11 | ~2.2k | `service/`、`port/` |
| `domain/` | 78 | ~3.5k | `entitys/`（22 个聚合根）、`service/`、`market/`、`concept/` |

## 2. 架构稳定度评估

### 2.1 优势

1. **依赖方向严格**——domain 完全 Python-only（`dataclasses` + `enum` + `zoneinfo` + `re`），零外部依赖。可独立单测。
2. **协议层（port）抽得干净**——`application/port/collector_port.py` 定义 6 类采集器协议（`KlineFetcher`、`MinuteKlineFetcher` 等），`setup_default_registry()` 在 lifespan 注册实现，新增数据源 = 新增一个 fetcher 类 + 一行注册。
3. **跨聚合根服务定位准确**——`domain/market`（交易时段）、`domain/concept/collection_policy`（采集保护）、`domain/service/`（指标/信号/概念摘要）都满足 DDD §3.2「不依赖外部 IO / 可独立单测」。
4. **DI 边界清晰**——`infrastructure/config/di.py` 集中构造 AppService；`infrastructure/config/settings.py` 用 pydantic-settings 统一环境变量。
5. **面板的 4 表快照**——`StockPanelComposeRepository`（domain 层 Protocol）+ `StockPanelComposeRepoImpl`（infrastructure 实现）单独抽出来，没有污染 StockPoolRepo，是正确的"跨表 JOIN"的领域抽象做法。

### 2.2 风险与瓶颈

1. **entity 子目录数量爆炸（22 个）**——`domain/entitys/{stock_info,stock_pool,kline,panel,concept,fin_report,fin_daily_basic,base_adj_factor,base_dividend,base_name_change,base_suspend,cap_*,fin_top10_*,mkt_*}/`。其中 13 个 `cap_*`/`fin_top10_*`/`mkt_*`/`base_*` 实体**只有 model 和 repository，没有任何 service 调用**（详见 02 章）。
2. **application/service/ 中存在旧路径 import**——`realtime_app_service.py` 在 git status 里被标记，但在 IDE 看不到，需要回滚。
3. **infrastructure/adapter/akshare/ 等"占位目录"**——`akshare/`、`pytdx/`、`tushare/`、`adata/` 是上一轮声明式 Pipeline 路线的遗留空目录，从未被引用。
4. **scripts/ 目录堆积 26 个 `_test_*`/`_verify*`/`_check_*`/`_kill_*` 脚本**——多数为一次性探针脚本，仅 2 个（`fix_tech_kline_table.py`、`trigger_collect.py`）值得保留。
5. **KLineAppService 仍然自己 `new KlineRepoImpl`**（`daily_kline.py:98`）——破坏了 DDD "构造注入"约定；DI 应贯穿到框架层（见 02 章建议）。

## 3. 重构建议清单（按 ROI 排序）

| 编号 | 内容 | 风险 | 收益 |
|---|---|---|---|
| L1 | 将 13 个 `cap_*`/`fin_top10_*`/`mkt_*`/`base_*` 实体统一抽到 `domain/entitys/datalink/` 子模块 | 中（边界划定难） | 减少 entity 文件数 |

## 5. 一句话总结

**架构稳定，方向正确；剩 60% 是死代码 / 空壳 / 过期文档清理，30% 是构造注入一致性补完，10% 是 entity 子目录命名建议。** 不建议在这个时间点做大规模的"按 bounded context 重划"——会让现有清晰的 22 个 entity 文件混乱。
