## 3. 按数据类型分别设置采集节奏：思路对，但概念要拆开看

"每个采集任务类带默认调度配置，采集管理页可以改"这个设计合理。但"概念按分钟采"要细分，5 个概念任务的变化频率差别很大：

| 任务                 | 实际变化频率       | 建议节奏                             |
| :------------------- | :----------------- | :----------------------------------- |
| 概念清单、概念成分股 | 几天到几周才变一次 | 每天盘后或每周一次                   |
| 概念入选理由         | 很少变             | 每周一次，只补缺失（`only_missing`） |
| 概念指数日 K         | 每天一根           | 每天收盘后（比如 15:30）增量跑       |
| 概念行情快照         | 盘中实时变化       | 见下文                               |
| 日 K 线、日频估值    | 每天               | 每天收盘后固定时间                   |
| 股票基本信息         | 很少变             | 每天或每周一次                       |

行情快照不适合按分钟跑全量。实测跑一轮 390 个概念要约 12 分钟（每次请求间隔 0.5 秒，还会被同花顺限流），根本跟不上一分钟一轮。如果每分钟入库一次，一天也会多出约 390 × 240 ≈ 9 万行。比较现实的做法：

- 盘中每 15–30 分钟跑一轮，用来更新涨跌染色和排名；
- 需要真正实时的场合（比如打开某个概念的详情），当场调接口实时查，现在的 `live-by-symbol` 就是这种模式。

实现要点：

- 任务类层面： 在 `BaseCollectTask` 上加一个类变量 `default_schedule`，声明默认是否启用、cron 表达式或间隔、是否只在交易时段跑、默认参数（比如 `{"only_missing": true}`）。
- 数据库层面： 新建一张 `sys_collect_schedules` 表（`task_type`、`enabled`、`cron`、`params`、`last_run_at`、`next_run_at`）存用户修改后的配置。表里没有记录时，就用类上的默认值。
- 调度器： 目前项目里没有任何定时调度，只有手动触发。可以在 `lifespan` 里启动 APScheduler 的 `AsyncIOScheduler`，触发时走现有的"创建采集任务"流程，这样进度、取消、历史记录都能复用。
- 需要提前考虑的几个问题：
  - 交易日历： "只在交易日跑"要用交易日历，但 `mkt_calendars` 目前也是空表，得先补一个 tushare `trade_cal` 采集任务。
  - 防重叠： 上一轮还没跑完时，新一轮要跳过。
  - 热重载： 开发时 WatchFiles 一重载，调度器就跟着重启，错过的触发点要能处理。
  - 单实例： 以后如果部署多个 worker 进程，要保证只有一个进程在跑调度。
- 前端： 采集管理的任务卡片上加开关、频率选择、下次运行时间，再加一个"调度总览"视图。
