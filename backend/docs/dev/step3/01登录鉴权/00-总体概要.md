## 0. TL;DR（一分钟看完）

| 项 | 选型 | Why |
|---|---|---|
| 鉴权方案 | 自实现 JWT，单体内置 | 单体后端单前端，自实现足够解眼前需求 |
| Token 算法 | **RS256**（非对称） | 私钥签 / 公钥验 |
| Token 体系 | **access_token（15 min）+ refresh_token（7 d，rotation）** | access 短期保 API 安全，refresh 长期保 UX，rotation 防 token 盗用 |
| 密码 | **bcrypt**（cost=12） | 业界标准；SHA256 不可逆但无盐 |
| RBAC | **4 张核心表 + 2 张关联表**（user / role / permission / 关联） | 简单够用，可扩展 |
| 数据库 | **复用现有 PostgreSQL** | 已有 `attribution` 库，加 6 张 `sys_*` 表，不动旧表 |
| 邮箱注册 | ✅ 任意邮箱（**不限制学生邮箱**） | 用户需求 |
| 前端存储 | `localStorage` 存双 token + Pinia store | 简单 |
| API 自动刷新 | axios 拦截器 | 401 → 自动用 refresh_token 换新 → 重放原请求 |
| 路由守卫 | Vue Router `beforeEach` | 未登录跳 `/login` |
| 现有代码改动 | **2 个后端 + 4 个前端** 文件 | 最小侵入，DDD 分层完全兼容 |

## 1. 设计原则

1. **贴合现有 DDD 分层**：`route → application → domain ← infrastructure`，与 `stock / pool / kline` 模块一致。
2. **复用现有基础设施**：PostgreSQL、AsyncSession、NullPool、TimestampMixin、_response 统一响应、register_exception_handlers。
3. **复用前端基础设施**：Pinia、Element Plus、PageWrapper、LeftBar、TopBar、Vue Router。
4. **单一职责**：auth 模块只管身份与权限；不耦合业务。

## 3. 双 Token 流程

```
用户登录                              后端
  │                                   │
  ├── POST /auth/login ─────────────► │
  │   { email, password }              │
  │                                   ├── 查 sys_users
  │                                   ├── bcrypt 验证密码
  │                                   ├── 签 access_token (RS256, 15min)
  │                                   │   claims: {sub, email, roles, perms, ...}
  │                                   ├── 签 refresh_token (RS256, 7d, jti)
  │                                   ├── 存 sys_refresh_tokens
  │                                   │
  │ ◄──── { access_token, refresh_token, user_info } ───
  │
  ├── 存 localStorage
  │
  ├── GET /stocks/600519 ───────────► │
  │   Header: Authorization: Bearer <access_token>
  │                                   ├── 验 RS256 签名（用公钥）
  │                                   ├── 验过期 / 类型
  │                                   ├── 解析 sub → user_id
  │                                   ├── 调 StockAppService
  │ ◄──── 200 OK ───
  │
  │ ... 15 分钟后 ...
  │
  ├── GET /users/ ────────────────► │
  │   Header: Bearer <expired_token>  │
  │ ◄──── 401 TOKEN_EXPIRED ───
  │
  ├── axios 拦截器拦截 401
  ├── POST /auth/refresh ──────────► │
  │   { refresh_token: <jti_X> }      │
  │                                   ├── 验签名 / 过期
  │                                   ├── 查 sys_refresh_tokens (jti_X)
  │                                   ├── 检查未撤销、未被重复用
  │                                   ├── 撤销 jti_X（旧 token rotation）
  │                                   ├── 签新 access_token + refresh_token
  │                                   ├── 存新 refresh_token (jti_Y)
  │ ◄──── { new_access, new_refresh } ───
  │
  ├── 替换 localStorage
  ├── 重放原 GET /users/ 请求（新 token）
  │ ◄──── 200 OK ───
```

## 4. RBAC 设计

### 4.1 角色（3 个内置，is_system=true 不可删）

| code | name | 说明 |
|---|---|---|
| `admin` | 系统管理员 | 拥有所有权限；唯一可访问 `/users/`、`/roles/`、`/permissions/` |
| `member` | 普通用户 | 注册即默认绑定；可读股票、读 K 线、读采集、读/写操作池、触发 K 线采集 |
| `viewer` | 只读用户 | 仅可读：股票、K 线、采集、操作池 |

### 4.2 权限（14 个内置，按 `资源:操作` 命名）

| code | resource | action | name | admin | member | viewer |
|---|---|---|---|---|---|---|
| `stock:read` | stock | read | 查看股票 | ✅ | ✅ | ✅ |
| `stock:write` | stock | write | 编辑股票 | ✅ | ❌ | ❌ |
| `stock:delete` | stock | delete | 删除股票 | ✅ | ❌ | ❌ |
| `kline:read` | kline | read | 查看 K 线 | ✅ | ✅ | ✅ |
| `kline:write` | kline | write | 采集 K 线 | ✅ | ✅ | ❌ |
| `pool:read` | pool | read | 查看操作池 | ✅ | ✅ | ✅ |
| `pool:write` | pool | write | 编辑操作池 | ✅ | ✅ | ❌ |
| `pool:delete` | pool | delete | 删除操作池 | ✅ | ❌ | ❌ |
| `collect:read` | collect | read | 查看采集 | ✅ | ✅ | ✅ |
| `collect:write` | collect | write | 操作采集 | ✅ | ❌ | ❌ |
| `user:read` | user | read | 查看用户 | ✅ | ❌ | ❌ |
| `user:write` | user | write | 编辑用户 | ✅ | ❌ | ❌ |
| `user:delete` | user | delete | 删除用户 | ✅ | ❌ | ❌ |
| `role:read` | role | read | 查看角色 | ✅ | ❌ | ❌ |
| `role:write` | role | write | 编辑角色 | ✅ | ❌ | ❌ |
| `role:delete` | role | delete | 删除角色 | ✅ | ❌ | ❌ |

> 注：上表实际 16 行（含 `user:delete`、`role:delete`），但初版只放 14 个核心权限；可在 001 建表 SQL 中扩展。

### 4.3 鉴权使用方式（3 种粒度）

```python
# 方式 1：仅需登录
@router.get("/me", dependencies=[Depends(get_current_user_id)])

# 方式 2：需要特定角色
@router.delete("/admin/cache", dependencies=[Depends(require_role("admin"))])

# 方式 3：需要特定权限（推荐）
@router.post("/users", dependencies=[Depends(require_permission("user:write"))])
```

### 5.5 现有路由加鉴权（**只加 `dependencies=`，不动业务**）

按权限粒度给现有路由加 `Depends(require_permission(...))`：

| 路由模块 | 操作的 Depends |
|---|---|
| `stock.py` | `GET /` → 无（公开接口，但建议加 login）；`PATCH /{symbol}` → `stock:write`；`DELETE /{symbol}` → `stock:delete`；`POST /sync`、`POST /sync-daily-basic` → `collect:write` |
| `pool.py` | `POST /`、`PATCH /{id}` → `pool:write`；`DELETE /{id}` → `pool:delete`；其余读 → `pool:read` |
| `kline.py` | `POST /collect`、`/collect/batch` → `kline:write`；`DELETE` → `kline:write`（限 member/管理员） |
| `collect_task.py` | `POST /tasks` → `collect:write`；`POST /tasks/{id}/cancel` → `collect:write` |
| `concept.py` | 仅读，无需鉴权或加 `stock:read` |

> **保守做法**：先只给 `/auth/*` 和 `/users/*` 加鉴权；其他业务接口暂保持公开。鉴权灰度上线后再逐步收紧。

## 7. 安全要点

| 要点 | 措施 |
|---|---|
| 密码 | bcrypt cost=12，存哈希不存明文 |
| access_token | 15 分钟，RS256，payload 含 sub/email/roles/permissions |
| refresh_token | 7 天，RS256，**每次用都 rotation**（旧的撤销），reused 检测 → 全撤销 |
| 密钥 | RSA 2048，私钥 `backend/.keys/jwt_private.pem`（600 权限，`.gitignore`）|
| 异常 | `AuthError` 继承 `DomainError`；全局 `register_exception_handlers` 统一 `{code, message, data}` |
| CORS | 现有 `ALLOWED_ORIGINS` 兼容（开发时 `http://localhost:5173`）|
| 防爆破 | 登录失败不区分"用户不存在"vs"密码错"（统一 `INVALID_CREDENTIALS`）|
| 防 CSRF | 当前是 SPA + Bearer token，无 CSRF 问题 |

---

## 8. 关键决策 FAQ

| 问 | 答 |
|---|---|
| 为什么用 RS256？ | 非对称签名，私钥签 / 公钥验；密钥轮换直接重生成 `.keys/` |
| 为什么 bcrypt 不是 SHA256？ | bcrypt 自动加盐 + 可调成本；SHA256 太慢但无盐 |
| 为什么 refresh token 要 rotation？ | 防 token 泄漏后被滥用；reused 检测 = 主动告警 |
| 为什么不分离 auth 服务？ | 当前单体单前端，无需多跳；多跳会增加部署和延迟 |
| 为什么不分离 auth-service？ | 一次请求多跳 → 性能差 + 部署复杂；先解眼前问题 |
| 为什么不用 httpOnly cookie？ | 当前 SPA + 第三方 API 调用方少，localStorage 简单 |
