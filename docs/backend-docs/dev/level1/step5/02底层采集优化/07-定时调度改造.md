# 07 定时调度改造：应用层决定"何时跑什么"，基础设施只负责"到点叫醒"

> 对应 README 的使用方式"定时编排"。阶段 P5，与其他阶段无依赖。

## 1. 现在 scheduler 做什么

`infrastructure/adapter/scheduler/` 下其实是两件不相关的事：

| 文件 | 职责 |
| :-- | :-- |
| `collect_scheduler.py` | 采集方案定时：APScheduler 封装 + 启动时读方案表注册 job + `sync_plan` / `next_run` + 到点调 `run_plan` + 定时规则校验（`validate_schedule` / `normalize_times` / `MIN_INTERVAL_SECONDS`） |
| `operation_dispatcher.py` / `task_registry.py` | 股票池操作的后台 asyncio 任务派发与取消，与定时无关 |
| `collect/` | 采集任务（见 04，P6 上移到 `adapter/collect/`） |

## 2. 现在的问题

依赖方向双向缠绕：

```
CollectManageService ──import──▶ collect_scheduler.get_collect_scheduler / validate_schedule / normalize_times
        ▲                                   │
        └────── 到点 import di + Service ◀──┘  （_fire_plan 里 lazy import）
collect_scheduler.start() ──import──▶ CollectConfigRepoImpl（自己读方案表）
```

具体表现：

- `collect_manage_service.py` 顶部直接 import 调度器实现（第 29–33 行），`plan_to_dict` 里还直接调用 `get_collect_scheduler()` 计算下次触发时间。Service 虽然定义了 `CollectSchedulerPort`，但没有完全通过它。
- 调度器启动时自己读仓储、自己决定注册哪些 job，相当于基础设施在做应用层编排。
- 到点时调度器反向 import `di` 和 `CollectManageService`，靠 lazy import 规避循环依赖。
- "间隔不能小于 30 秒""每天最多 24 个时间点"是业务规则，却放在基础设施里。

## 3. 改造后的分工

| 位置 | 放什么 | 不放什么 |
| :-- | :-- | :-- |
| `domain/entitys/collect_plan/vo.py` | `Schedule` 值对象：定时配置 + 校验规则（原 `validate_schedule` / `normalize_times` / `MIN_INTERVAL_SECONDS` / `MAX_TIMES_PER_DAY`） | 任何 IO、任何框架依赖 |
| `application/port/scheduler_port.py` | `SchedulerPort` 抽象（参数直接用 domain 的 `Schedule`） | APScheduler 细节 |
| `application/service/collect_manage_service.py` | 方案增删改时注册 / 删除定时；启动时恢复定时；到点执行 `run_plan` | import 调度器实现 |
| `infrastructure/adapter/scheduler/apscheduler_adapter.py` | 纯 APScheduler 封装：注册 / 删除 job、计算下次触发、到点回调 | 读仓储、认识"方案"、import Service |
| `infrastructure/adapter/background/` | `operation_dispatcher.py`、`task_registry.py`（原样搬迁） | — |

## 4. Schedule 值对象（domain）

"间隔不小于 30 秒""每天最多 24 个时间点"是采集方案自己的规则，按 DDD.md §3.2 归到采集方案这个聚合根下，而不是 `domain/service/`（那里只放跨聚合根的算法）。

```python
# domain/entitys/collect_plan/vo.py
MIN_INTERVAL_SECONDS = 30
MAX_TIMES_PER_DAY = 24

@dataclass(frozen=True)
class Schedule(ValueObject):
    type: Literal["time", "interval"]
    times: tuple[str, ...] = ()          # HH:MM，type=time 时；构造时去重 + 升序
    interval_seconds: int | None = None  # type=interval 时

    def __post_init__(self): ...         # 原 validate_schedule 的规则，非法抛 InvalidSchedule（领域异常）

    @classmethod
    def from_form(cls, schedule_type, times, interval_seconds) -> "Schedule | None":
        """表单 → VO；schedule_type 为空返回 None（不定时）。原 normalize_times 的去重排序在这里做"""
```

- 纯 `dataclass`，继承项目已有的 `domain.base.ValueObject`，和 `kline/vo.py` 等现有 VO 写法一致，零外部依赖。
- `InvalidSchedule` 继承 `ValueError`，Service 和路由现有的 `except ValueError` 不用改，报错文案原样保留。
- 本次只建 VO。方案的实体和仓储接口仍用现有 `CollectPlanDB` + `CollectConfigRepoImpl`，补齐 `collect_plan` 聚合根不在本次范围（§9）。

## 5. SchedulerPort

```python
# application/port/scheduler_port.py
from domain.entitys.collect_plan.vo import Schedule

JobHandler = Callable[[dict], Awaitable[None]]

class SchedulerPort(Protocol):
    def on_fire(self, handler: JobHandler) -> None: ...                  # 注册到点回调（启动期一次）
    def upsert(self, key: str, schedule: Schedule, payload: dict) -> None: ...  # 覆盖该 key 下所有 job
    def remove(self, key: str) -> None: ...
    def next_run(self, key: str) -> datetime | None: ...
```

- `key` 由应用层决定，方案定时用 `plan:{plan_id}`。Adapter 内部仍按现有约定展开为 `plan:{id}@{HH:MM}`（定时模式）或 `plan:{id}`（定频模式），并保留"精确匹配 `prefix + '@'`，避免 `plan:1` 误删 `plan:11@09:30`"的处理。
- `payload` 就是命令，到点原样传回给 `handler`：`{"plan_id": 1}`。
- `max_instances=1`、`coalesce=True`、`misfire_grace_time`（定时 300s / 定频 60s）这些 APScheduler 参数保留在 Adapter 内部，行为不变。

## 6. CollectManageService 的改动

```python
class CollectManageService:
    def __init__(self, ..., scheduler: SchedulerPort | None, ...): ...

    # 启动时调用一次：读方案表，恢复所有启用方案的定时（原 CollectScheduler.start 里的逻辑）
    async def restore_schedules(self) -> int: ...

    # 到点回调：payload 来自 upsert 时传入的命令
    async def handle_job(self, payload: dict) -> None:
        await self.run_plan(payload["plan_id"], trigger="schedule")

    # 原 _sync_scheduler：方案增删改后调用
    def _sync_schedule(self, plan_id, enabled, schedule: Schedule | None) -> None:
        if self._scheduler is None:
            return
        key = f"plan:{plan_id}"
        if enabled and schedule:
            self._scheduler.upsert(key, schedule, {"plan_id": plan_id})
        else:
            self._scheduler.remove(key)
```

- 删除 Service 文件内自定义的 `CollectSchedulerPort`（`sync_plan` / `next_run` 两个方法），统一用 `application/port/scheduler_port.py` 的 `SchedulerPort`。
- `_check_plan` 里原来的 `normalize_times(...)` + `validate_schedule(...)` 两步，改为 `schedule = Schedule.from_form(schedule_type, times, interval_seconds)`；落库时从 `schedule` 取 `times` / `interval_seconds`，表结构不变。
- `plan_to_dict` 不再调用 `get_collect_scheduler()`，改为由 Service 传入 `next_run_at`（`self._scheduler.next_run(key)`）。
- **仍然只允许"方案"被定时**。要单独定时某一个采集接口，就建一个只有一项的方案。这样定时、手动触发、采集历史都走同一条 `run_plan` 流水线，防重和进度逻辑不重复。

## 7. 启动接线

```python
# main.py lifespan
if settings.COLLECT_SCHEDULER_ENABLED:
    scheduler = ApschedulerAdapter(settings.COLLECT_SCHEDULER_TIMEZONE)
    set_scheduler(scheduler)                                         # di 持有，供 get_collect_manage_service 注入
    scheduler.on_fire(lambda payload: get_collect_manage_service().handle_job(payload))
    count = await get_collect_manage_service().restore_schedules()
    scheduler.start()
    logging.info("采集调度器已启动: %d 个方案", count)
...
scheduler.shutdown()
```

- `get_collect_manage_service()` 现在每次调用都新建 Service 实例（由 `di.py` 构造），回调里每次到点构造一次，与现在 `_fire_plan` 的行为一致。
- 调度器实例由 `di.py` 持有（替代 `collect_scheduler.py` 里的模块级 `_scheduler` 和 `get_collect_scheduler()`）。
- `COLLECT_SCHEDULER_ENABLED=false` 时 Service 拿到的 `scheduler` 为 `None`，方案照常可手动执行，与现在一致。

## 8. 目录变化

```
修改前                                              修改后
infrastructure/adapter/scheduler/                   domain/entitys/collect_plan/vo.py         Schedule 值对象 + 定时规则
  collect_scheduler.py                              application/port/scheduler_port.py        SchedulerPort
  operation_dispatcher.py                           infrastructure/adapter/scheduler/
  task_registry.py                                    apscheduler_adapter.py                  纯 APScheduler 封装
  collect/                                          infrastructure/adapter/background/
                                                      operation_dispatcher.py  task_registry.py
                                                    infrastructure/adapter/collect/           （04 §8，P6）
```

`operation_dispatcher.py` 搬迁后需要同步修改 import 的位置：`application/port/operation_dispatcher_port.py` 的注释、`di.py`（`get_stock_pool_service` 里的 lazy import）、`operation_dispatcher.py` 自身对 `task_registry` 的 import。

`OperationDispatcher._run` 里同样 lazy import 了 `di.get_collect_manage_service` 来调 `run_one("daily_kline", ...)`，和调度器 `_fire_plan` 是同一类反向依赖。顺手改为构造注入：

```python
# infrastructure/adapter/background/operation_dispatcher.py
class OperationDispatcher:
    def __init__(self, run_one: Callable[[str, str, dict], Awaitable[UnitResult]]) -> None: ...

# di.py get_stock_pool_service
dispatcher=OperationDispatcher(run_one=lambda t, u, p: get_collect_manage_service().run_one(t, u, p))
```

`OperationDispatcherPort` 的签名不变，`StockPoolService` 不用改。

## 9. 不在本次范围

- 补齐 `collect_plan` 聚合根（实体 + 仓储接口）。现在 `CollectManageService` 直接使用 ORM 模型 `CollectPlanDB` / `CollectPlanItemDB`，违反 DDD.md §4；本次只先把定时规则收进 `Schedule` VO，实体化另开文档。
- 多副本部署时的调度互斥（只能有一个副本触发）。当前按单进程设计，与现在一致；以后要多副本时，再给 Adapter 加 Redis 锁或 leader 选举。
- 采集任务执行器（`execute_task` / `BaseCollectTask`）仍被 Service 直接 import。可以再加一个 `CollectRunnerPort` 隔开，但改动面较大、收益有限，暂不做。

## 10. 验收

- 方案页新增 / 修改 / 停用 / 删除方案后，下次触发时间显示正确。
- 设置一个 1 分钟后的定时，到点触发，`sys_collect_tasks` 中 `trigger_type=schedule`。
- 定频方案 `interval_seconds < 30` 时保存报错，提示文案不变。
- `domain/entitys/collect_plan/vo.py` 不 import 任何第三方库；`Schedule` 可脱离数据库和调度器单测。
- `collect_manage_service.py` 中 grep 不到 `infrastructure.adapter.scheduler`。
- `adapter/scheduler/`、`adapter/background/` 中 grep 不到 `infrastructure.config.di` 和 `application.service`。
- 股票池"批量采集 K 线"操作的派发、进度、取消正常。
