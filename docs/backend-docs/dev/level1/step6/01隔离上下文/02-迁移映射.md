## 0. 总览

| 类别 | 数量 | 处置 |
| :-- | :--: | :-- |
| 需要移动的文件 | ~150 | 物理迁移到 `contexts/<name>/...` 对应层 |
| 需要新增的文件 | ~50 | 上下文骨架、context 自己的 `__init__.py`/`bootstrap.py`、新 port |
| 需要新建的"空"骨架（占位） | ~20 | news / sentiment / user 非 pool 部分 |
| 需要保留但路径不改的文件 | 0 | — |
| 需要删除的文件 | 0 | **本期不删任何代码** |

> 关键决定：**本期 0 删除**。物理移动走"复制 + 改 import + 验证 + 留 shim"三步走。所有旧路径仍可被外部代码 import。

## 1. 总体原则

### 1.1 文件去向判定（速查）

```
问自己：这个文件属于 8 个 context 里的哪一个？
├─ 答得出 → 移动到 contexts/<name>/<层>/...
├─ 答"不知道"但被 ≥ 2 个 context 用到 → 放到 shared/
└─ 答"shared/ 也不对" → 暂停，留个 issue，先到 _staging/
```

### 1.2 文件改 import 的判定（速查）

```
移动文件后，要改 import 吗？
├─ 同 context 内 import → 改相对路径（from .x import y）
├─ 跨 context import → 必须改为 port 调用（不直接 import 对方 domain）
├─ import shared/ 里的东西 → 改 from contexts.shared.xxx import ...
└─ import 旧路径（domain.entitys / application.service / route.api.v1 / infrastructure.*） →
   评估：还有谁在用？
   ├─ 只有旧文件用 → 改掉
   └─ 还有第三方 / 测试 / 前端生成代码用 → 在 contexts/_legacy_compat.py 留转发
```

### 1.3 兼容 shim 的契约

```python
# contexts/_legacy_compat.py
"""旧 import 路径 → 新位置的转发表（过渡期保留，~1 个月后删除）

保留原则：仅当外部代码（测试 / 脚本 / IDE 索引）需要旧路径时才转发。
内部代码一旦迁移完，统一走新路径。
"""
from __future__ import annotations
```

## 5. bootstrap.py 契约（每个 context 都有）

```python
# contexts/auth/bootstrap.py（草稿）

from typing import TYPE_CHECKING
from fastapi import FastAPI
from sqlalchemy.ext.asyncio import AsyncSession

if TYPE_CHECKING:
    from application.service import AuthService

def setup_auth(app: FastAPI) -> None:
    """auth context 的 DI 装配（app 启动时调用）
    
    1. 注册路由：app.include_router(auth_router, prefix="/api/v1", tags=["auth"])
    2. 注册依赖：get_auth_service 等
    3. 初始化外部资源：JWT 密钥对预热（key_manager.warmup）
    4. （阶段 2+）订阅其他 context 的事件
    """
    from .interface.route import router as auth_router
    from .interface.route_user import router as user_router
    from .interface.route_role import router as role_router
    from .interface.route_permission import router as permission_router
    from .infrastructure.security import key_manager
    
    # 1. 注册路由
    app.include_router(auth_router, prefix="/api/v1", tags=["auth"])
    app.include_router(user_router, prefix="/api/v1", tags=["user"])
    app.include_router(role_router, prefix="/api/v1", tags=["role"])
    app.include_router(permission_router, prefix="/api/v1", tags=["permission"])
    
    # 3. 初始化资源（lifespan 前）
    # key_manager 在 lifespan 里 warmup，bootstrap 不做
```

> 各个 context 的 `bootstrap.py` **不重复实现 DI 工厂**——DI 工厂仍集中在 `app/container.py`（或 `infrastructure/config/di.py`）。
> `bootstrap.py` 只做 **"我这个 context 要挂哪些路由 / 监听哪些事件 / 初始化哪些资源"**。

## 7. 一次性 vs 渐进式

### 7.1 一次性迁移（推荐）

```
E1 准备  1 天  备份当前代码到 D:\codes\_backup\attribution_step6_YYYYMMDD\
E2 建骨架 1 天  创建 contexts/ 下 8 个 context 的目录结构（含空 __init__.py）
E3 移动  4-5 天 按 §4 顺序逐个 context 移动文件
E4 改 import 2-3 天 全局替换为新路径（grep + sed/IDE 重构）
E5 加 shim  0.5 天  contexts/_legacy_compat.py
E6 验证    1 天  启动 + 23 任务 + 主要 HTTP 路径
───────────────────
E 总计   10-12 天（约 2 周）
```

### 7.2 渐进式迁移（不推荐但可备选）

每个 context **单独**做一次"小迁移"：
- D1：仅 auth
- D2：仅 collect
- ...
- D8：news 占位

**风险**：DI 在 `infrastructure/config/di.py` 单点编排，渐进期间反复改 di.py 易出错。
**收益**：每步可独立回滚。

> 本期采用**一次性迁移**。原因：所有 context 共享同一份 di.py，分批会让 di.py 反复改，引入风险。
