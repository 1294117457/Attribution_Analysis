## 1. 这是什么

智能金融数据归因分析平台的后端。Java 侧负责**查询与编排**，Python 侧（`collector-python`）负责**数据采集**。

```
frontend(:80) ──▶ java-app(:8080) ──Feign──▶ collector-python(:8001)
                      │                          │
                      └────▶ postgres:5432 ◀─────┘
                      └────▶ redis:6379 ◀────────┘（验证码/会话/采集限频）
```

* **Java 是「单体多模块」**：1 个 parent pom + 6 个 jar 模块，打 1 个 fat jar（`attribution-app`）。
* **Java 不做采集实现**，只透传：前端 → Java `/api/collect/**` → collector `/api/collect/**`。
* **Java 不做调度**（`@EnableScheduling` 未启用），采集只能手动触发。
* **Java 不直连 Redis**（规范要求），只有 `attribution-auth` 因为验证码/会话需要而引入 Redis 依赖。

> 详细拆分论证见 `规范文档/拆分方案.md`。

## 3. 模块地图

```
backend-java/
├─ pom.xml                      # parent，packaging=pom，只管版本 + 模块列表
├─ attribution-common/          # 无业务依赖：ApiResponse/PageResult/异常/WebConfig/TopN
├─ attribution-collector-client/# Feign 调 collector：Client + Fallback + 目录缓存
├─ attribution-market/          # 行情/K线/数据看板/面板/归因 + 采集代理（最重）
├─ attribution-concept/         # 概念板块/成分/快照
├─ attribution-user/             # 自选池 / 池级操作（依赖 market 的 Service）
├─ attribution-auth/            # 登录/用户/角色/权限（Redis + Mail + JWT）
├─ attribution-app/              # 唯一可执行模块：启动类 + application.yml + MyBatis-Plus 配置
└─ docs/                        # 本文档所在目录
```

### 依赖方向（**单向，不可循环**）

```
app → market → collector-client → common
app → concept → collector-client → common
app → user → market → collector-client → common
app → auth → common
```

铁律：
1. **跨模块只调 Service 接口**（构造器注入），**禁止跨模块调 Mapper**。
2. **禁止 `market ↔ user` 双向依赖**。当前是 `user → market`（`PoolServiceImpl` 注入 `StockInfoService`）。
3. **禁止 concept 反向依赖 market**（concept 当前不依赖 market，只依赖 common + collector-client）。
4. 新增模块 → 必须手工在 `AttributionApp` 的 `@MapperScan` 里加包名。

## 5. 分层约定（四层）

```
Controller  HTTP 协议、参数绑定、@Valid 校验、组装 ApiResponse
   ↕ DTO(Query) / VO
Service     ★ 业务编排 ★  规则校验 / 调 Mapper / PO→VO / 事务边界
   ↕ PO / Row
Mapper      ★ 持久化唯一入口 ★  单表 CRUD / 联表聚合 / 批量
   ↕
DB          表
```

外加两个纯函数层：
* **Converter** —— 只做 `po.getXxx() → vo.setXxx()`（无业务判断）。
* **Util** —— 无状态计算（`IndicatorUtil` 指标算法）。

### 包结构约定（每个业务模块内）

```
com.attribution.<模块>/
  controller/   ← @RestController
  service/      ← 接口
  service/impl/ ← @Service 实现
  mapper/       ← @Mapper extends BaseMapper
  entity/       ← *PO（@TableName）
  dto/          ← 入参（*Request / *Query）
  vo/           ← 出参（*VO / *ResponseVO）
  converter/    ← PO↔VO
```

### 数据形状约定

| 类型 | 用途 | 位置 |
|---|---|---|
| `*PO` | 与表一一对应，带 `@TableName` / `@TableField` | `entity/` |
| `*DTO` | Controller 入参，带 `@NotBlank` 等校验 | `dto/` |
| `*VO` | Controller 出参 | `vo/` |
| `*Row` | Mapper 内部行对象（如 `PoolMemberCountRow`） | Mapper 接口内嵌 |

> 命名细节：`@TableName("xxx")` 显式写全表名；列名用 `@TableField("xxx")`；PO 属性用 camelCase。

### 统一响应体

```java
ApiResponse.ok(data)     // code=200, message="success"
ApiResponse.created(data)// code=201, message="创建成功"
ApiResponse.fail(code,msg)
```

分页统一 `PageResult{total, list, page, pageSize}`（`PageResult.of(...)`）。

异常统一由 `GlobalExceptionHandler` 处理：
* `BusinessException` → HTTP 状态码 = 业务 code，message 直接透出（只记 warn，不打堆栈）。
* `MethodArgumentNotValidException` → 422，聚合全部字段错误。
* 兜底 `Exception` → 500，**只返回「服务器内部错误，请稍后重试」**，原始 message 只进日志（防信息泄漏）。

## 8. 关键实现要点（易踩坑）

### 8.1 分页 / 取前 N 条

**禁止**在 Service 层写 `.last("LIMIT " + n)`。统一用 `TopN.query(mapper, wrapper, limit)` / `TopN.latest(mapper, wrapper)`（`attribution-common`），底层走 MyBatis-Plus `Page` + 分页插件。

分页插件注册在 `MybatisPlusConfig`：`maxLimit=10000`，另有 `BlockAttackInnerInterceptor` 阻断全表 update/delete。**依赖此插件**，否则 `selectPage` 不会截断。

### 8.2 技术指标 warmup

MA/EMA/MACD/RSI/KDJ/BOLL 是**递推**的，计算窗口起点前必须额外取 **120 根** warmup 数据（`IndicatorUtil.WARMUP = 120`），算完再丢弃 warmup 部分。

调用模式见 `KlineServiceImpl.list` / `DataBoardServiceImpl.techKline`。

### 8.3 Collector 调用三铁律

1. **只经 `collector-client`**：`CollectorService` → `CollectorClient`（Feign）→ collector。业务 Service 不得直连 HttpClient。
2. **实时查询不拆信封**：`CollectorService.queryRaw` 返回整个 `{code,message,data}`。历史 bug：拆 `data` 后 collector 宕机的 `code=503` 会被包成 `code=200,data=null`，前端误判「成功但无数据」。
3. **`ObjectMapper` 必须 Spring 注入**，禁止 `new ObjectMapper()`（裸实例不带 `SNAKE_CASE` 全局配置）。

`CollectorFallback` 在 collector 不可用时返回 `{code:503, message:"collector unavailable", data:null}`。

### 8.4 采集目录动态校验

`CollectorCatalogCache` 从 collector 拉 `/api/collect/services` 并缓存（TTL 60s，**懒加载 + 访问触发**，因为项目不启用 `@EnableScheduling`）。

* 目录**从未成功加载**（collector 挂了）→ **降级为「不校验」**，让请求透传给 collector 给出权威错误。
* 旧硬编码 facet 集合已废弃，Python 新增 facet 不会卡死 Java 入口。

`CollectProxyController.TaskValidator` 做两层校验：① 纯语法（永远生效）② 目录校验（目录可用时）。

### 8.5 时间类型

* `collect_logs` 的时间列是 PG `TIMESTAMPTZ` → PO 必须用 `OffsetDateTime`，**用 `LocalDateTime` 会直接 500**。
* `sys_users` 等其余表是 naive `timestamp` → 用 `LocalDateTime`。**别混改**。
* 判定口径：**看表结构，不看习惯**。采集库（raw_data）的 `timestamptz` 列一律 `OffsetDateTime`
  （如 `ConceptPO.firstSeenAt` / `ConceptMemberPO.joinedAt` / `ConceptIndexPO.capturedAt`）；
  naive 列保持 `LocalDateTime`（如 `NewsPO.publishedAt` / `ConceptSnapshotPO.tradeTime`）。

### 8.6 线程池

`PoolTaskExecutorConfig` 提供 `poolTaskExecutor` Bean（core 4 / max 8 / queue 64 / `CallerRunsPolicy` / 前缀 `pool-collect-`）。Service 里**禁止** `Executors.new*`。

远程调用（collector 建任务）**不放进 `@Transactional` 方法**，避免长时间占用数据库连接 —— 见 `PoolServiceImpl.createOp` → `executor.execute(...)`。

### 8.7 Redis 扫描

禁止 `redis.keys(pattern)`（O(N) 且阻塞）。用 `SCAN` 游标 —— 见 `AuthServiceImpl.deleteByPattern`。

### 8.8 认证会话

登录态存 Redis（`StringRedisTemplate`），JWT 只作凭证载体。密码用 `BCryptPasswordEncoder`。邮件验证码走 SMTP（QQ 邮箱）。
