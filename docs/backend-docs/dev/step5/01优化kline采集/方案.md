# K 线指标改为实时计算 — 实施方案

> 状态：阶段 1（代码 + 前端 + 文档）已实施；阶段 2 已在开发库 8.148.204.54 执行删列并同步 `init.sql`，K8s 库待执行
> 范围：采集 / kline 领域 / 应用服务 / 路由 / 仓储 / 数据库表 / 前端
> 依据：`docs/backend-docs/config/DDD.md`（§3.3 领域服务、§6 反模式）、`docs/backend-docs/overview/00-项目索引.md`

## 1. 背景

### 1.1 现状

日 K 采集链路（`daily_kline` 任务 → `StockInfoService.collect()`）：

```
fetcher.fetch(days=N)                       # 只拉最近 N 天（默认 7 / 30）
  → _enrich_with_indicators(本次 N 天)       # 只用这 N 天算 18 个指标
  → KlineRepoImpl.save_batch()              # ON CONFLICT (symbol,date) DO UPDATE，含指标列
```

指标列（18 个，代码注释写的是"17"）存放在 `tech_kline_dailys` 同一行：

`ma5 ma10 ma20 ma60 / ema12 ema26 / macd_dif macd_dea macd_bar / rsi6 rsi12 rsi24 / kdj_k kdj_d kdj_j / boll_up boll_mid boll_dn`

### 1.2 缺陷

1. **增量采集把正确的历史指标覆盖成错误值**
   - 指标只用本次拉取的 N 根 K 线计算，而 `IndicatorCalculator` 全部是 `min_periods=1`：
     - 窗口第 1 天：`ma60 = close`，`rsi = 50`，`boll_up/dn = None`；
     - 前 60 天内的 MA60、前 20 天内的 BOLL、前 ~100 天内的 EMA/MACD/RSI 都是"假值"。
   - upsert 时 `DO UPDATE` 指标列，把之前全量采集时算对的值覆盖掉。
   - 服务器日志里的入参可以直接看到：首日 `ma60 == close`、`rsi6 == 50`、`boll_up IS NULL`。
2. **指标与 K 线强耦合**：改一次指标公式或参数，就得跑全表 `recalculate`。
3. **RSI 边界错误**：`avg_loss == 0`（连涨）时结果被 `fillna(50)` 改成 50，正确值应为 100。
4. **DDD 违规**：`route/api/v1/data_board.py::get_tech_kline` 直接 `KlineRepoImpl(db)`，路由层越过应用层依赖基础设施（DDD.md §6）。

### 1.3 可行性

- 全仓库没有任何 SQL 按指标列做 `WHERE` / `ORDER BY`（没有"MACD 金叉选股"之类的全市场筛选），指标只在"取某只股票 K 线"时随行返回。
- 单只股票 365 + 120 根 K 线，pandas 计算全部指标约几毫秒，远小于一次 DB 查询。
- 因此：**采集只存 OHLCV，指标在请求时实时计算**，可以根治上述缺陷。

## 2. 目标 / 非目标

**目标**

- 采集只写 K 线原始字段，不再计算、不再写指标。
- 所有返回指标的接口改为"读 N + 预热 根 K 线 → 计算 → 截取最后 N 根"，结果与采集方式、采集顺序无关。
- 历史数据不足时指标返回 `null`，不再返回假值。
- **接口响应字段名、结构保持不变**，前端只需小改（空值绘制）。
- 最终删除 `tech_kline_dailys` 上的 18 个指标列。

**非目标（本期不做）**

- 前复权 / 后复权计算（见 §9 后续可选）。
- 全市场指标选股（如需要，另建盘后批量任务写独立表，见 §9）。
- 分钟 K 指标（分钟 K 目前本身不带指标，保持不变）。

## 3. 分层设计（对照 DDD.md）

```
route (kline.py / data_board.py / stock_analysis.py)
   │  只调应用服务，不再直接 new 仓储
   ▼
application  StockInfoService
   │  get_klines_with_indicators(): 读 K 线 + 预热 → 调领域服务 → 组装 DTO
   ▼
domain
   ├── entitys/kline/entity.py     Kline：只保留 OHLCV（去掉指标字段）
   ├── entitys/kline/vo.py         新增 IndicatorValues 值对象
   └── service/indicator_calculator.py   纯算法：list[Kline] → list[IndicatorValues]
       service/signal_detector.py        形态判断：输入 K 线 + 指标
   ▲
infrastructure  KlineRepoImpl / TechKlineDailyDB：只读写 OHLCV
```

为什么放在 `domain/service`：

- DDD.md §3.3 把 `IndicatorCalculator` 列为领域服务的示例：无状态、纯计算、不依赖 IO、不属于某个实体。
- 指标是 K 线序列的**派生值**，不是 K 线本身的状态，所以不应再作为 `Kline` 聚合根的字段，而是用值对象 `IndicatorValues` 表达（DDD.md 中的 VO 示例）。
- 应用层只负责编排（取数、预热、截取），不写任何指标公式（避免 §6 "在 ApplicationService 里算 RSI"反模式）。

| 现在 | 改为 |
|---|---|

| `enrich_klines(klines, df) -> dict[date, dict]` | 删除 |

**`min_periods` / 有效期规则**（数据不足返回 `None`，不再出假值）

| 指标 | 规则 | 最少需要的 K 线数 |
|---|---|---|
| MA5/10/20/60 | `rolling(n, min_periods=n)` | n |
| BOLL(20, 2) | `rolling(20, min_periods=20)`，std 保持 `ddof=1` | 20 |
| EMA12/26 | 递推照常从第 1 根算起，前 `span-1` 根置 None | span |
| MACD(12,26,9) | 同上，DIF 前 25 根、DEA/BAR 前 33 根置 None | 34 |
| RSI6/12/24 | Wilder 平滑照常递推，前 n 根置 None；去掉 `fillna(50)`：`avg_loss==0 且 avg_gain>0 → 100`，两者都为 0（横盘）→ 50 | n+1 |
| KDJ(9,3,3) | RSV 用 `rolling(9, min_periods=9)`，前 8 根为 None，K/D 从第一个有效 RSV 开始递推 | 9 |

**为什么预热 120 根**：EMA / MACD / RSI / KDJ 是递推指标，起点不同结果会有偏差，需要足够长的预热让初值影响衰减：

- EMA26：α≈0.074，120 根后初值权重 ≈ (1-0.074)^120 ≈ 0.01%；
- RSI24：α=1/24，120 根后初值权重 ≈ 0.6%；
- MA60 / BOLL20 只需 60 根。

所以 120 根预热能让显示窗口内的所有指标与"用全量历史计算"的结果基本一致（RSI24 误差 < 1%）。`WARMUP_BARS` 放在领域服务里作为常量，应用层引用，取代 `stock_info_service.py` 里的 `INDICATOR_WINDOW = 60`。

> 可选：通达信 KDJ 初值 K=D=50，当前实现以首个 RSV 为初值。有 120 根预热后两者差异可忽略，本期不改。

### 4.2 应用层 `application/service/stock_info_service.py`

#### 4.2.1 新增核心方法

```python
async def _load_klines_with_indicators(
    self,
    symbol: str,
    start_date: date | None,
    end_date: date | None,
    limit: int,
    order_desc: bool,
) -> list[tuple[Kline, IndicatorValues]]:
    code = StockCode(symbol)
    # 1) 主查询：语义与现在的 get_klines 完全一致
    main = await self._kline_repo.find_by_symbol(
        code, start_date=start_date, end_date=end_date,
        limit=limit, order_desc=order_desc,
    )
    if not main:
        return []
    first_day = min(k.trade_date.date for k in main)
    # 2) 预热：主窗口最早一天之前的 WARMUP_BARS 根
    warm = await self._kline_repo.find_by_symbol(
        code, end_date=first_day - timedelta(days=1),
        limit=WARMUP_BARS, order_desc=True,
    )
    # 3) 合并升序 → 计算 → 只保留主窗口
    series = sorted(warm + main, key=lambda k: k.trade_date.date)
    values = await asyncio.to_thread(self._calc.calculate, series)
    offset = len(warm)
    pairs = list(zip(series[offset:], values[offset:]))
    return list(reversed(pairs)) if order_desc else pairs
```

- 两次查询都走 `uq_tech_kline_symbol_date (symbol, date)` 索引，不需要改仓储接口。
- 用"主窗口最早一天"做预热边界，`start_date` / `limit` / `order_desc` 的任意组合都正确。
- 计算放 `asyncio.to_thread`，避免 pandas 阻塞事件循环（与现状一致）。

- PostgreSQL 的 `DROP COLUMN` 只改元数据，秒级完成，但会短暂持有 `ACCESS EXCLUSIVE` 锁，建议在**非采集时段**执行。
- 磁盘空间不会立刻释放（每行约 144 字节，按 500 万行估算约 700 MB）。如需回收，可在低峰期执行 `VACUUM FULL public.tech_kline_dailys;`（会锁表重写，可选）。
- 需要在**本地开发库**和 **K8s 上的 postgres** 各执行一次（开发库 8.148.204.54 上旧 docker-compose 后端仍连着同一个库，执行前先确认它已停掉，否则旧代码写指标列会报错）。

## 6. 前端修改

接口路径和字段名都不变，前端改动只集中在"指标可能为 `null`"的处理。

### 6.1 什么时候会出现 `null`

- 有足够历史（≥ 120 + 显示根数）的股票：显示窗口内所有指标都有值。
- 新股 / 历史很短：最前面若干根的 MA60（前 59 根）、BOLL（前 19 根）、MACD DEA（前 33 根）等为 `null`。
- 以前因为 `min_periods=1` 几乎不会出现 `null`，所以前端用 `?? 0` 兜底也看不出问题；现在会把线画到 0。

### 6.2 文件清单

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 请求时多一次预热查询 + 计算 | 单次 +几 ms | 两次查询都走唯一索引；数据看板有 ETag |
| 指标数值与以前略有不同 | 用户看到图形变化 | 以前的值本身有错（被增量采集覆盖），新值更准确；在发布说明中注明 |
| 删列后无法回滚旧代码 | 回滚需重建列并重算 | 阶段 2 延后执行，阶段 1 期间可随时回滚 |
| 旧 docker-compose 后端仍连开发库 | 删列后旧代码写入报错 | 删列前先停掉 8.148.204.54 上的旧后端 |
