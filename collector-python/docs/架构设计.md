# collector-python 架构设计（全异步版）

> 原则一句话：**采集全异步，查询分开走；Collector 只管写（PG + Redis），Java 只管透传 + 查库。**
> 本文档只定架构与职责，不改代码。现状引用：`src/main.py`、`src/api/__init__.py`、`src/tasks/manager.py`、
> `src/tasks/router.py`、`src/collectors/__init__.py`、`src/collectors/base.py`、`src/core/*`、`src/models/*`。

## 0. 总览

```
前端 → Java（透传 + 查 PG collect_log） → Collector :8001 → tushare / adata / pytdx
                                            ↓ 写 PG collect_log（永久）+ Redis 进度（临时）
```

- **采集（写库）**：全部走异步任务 `POST /api/collect/tasks/{facet}/{name}` → 立即返回 `task_id` → 轮询 `GET /api/collect/tasks/{task_id}` 看进度。
- **实时查询（不写库）**：`minute_kline / concept_minute / concept_snapshot` 走 `GET /api/collect/query/{name}` 同步直查，供 Java 透传。
- **历史审计**：Java 查自己库的 `collect_log` 表（`GET /collect/logs`），不经过 Redis。

## 1. 层级划分（四层 + 一横切）

```
┌ L4 接入层 route：只接 Java，无业务 ──────────────────┐
│ tasks/router.py: POST /tasks/{f}/{n} 建任务            │
│                  GET  /tasks/{id} 查进度（读 Redis）   │
│                  GET  /tasks      最近任务（读 Redis） │
│ api/__init__.py: GET /services 目录元数据              │
│                  GET /query/{name} 实时直查            │
└────────────────────────────────────────────────────────┘
┌ L3 编排层 tasks/：展开 + 调度 + 日志 ─────────────────┐
│ manager.py: _expand / _run / create_task / get_task_state / recover_stale │
│ log_repo.py（新建）: collect_log 的 INSERT / UPDATE 终态                  │
└────────────────────────────────────────────────────────┘
┌ L2 业务层 collectors/：三类 service ───────────────────┐
│ IncrementalCollector：单步 (trade_date) → upsert       │
│ FullCollector：无参 → 全量覆盖                          │
│ RealtimeQuery：无 collect()，只有 get()                │
│ 注册表 collectors/__init__.py：BY_NAME + kind          │
└────────────────────────────────────────────────────────┘
┌ L1 数据源层 core/*_client + *Fetcher ─────────────────┐
│ core/tushare_client.py / adata_client.py / pytdx_client.py │
│ collectors/*/*Fetcher.py：fetch() → list[BO]，不碰 DB/Redis │
└────────────────────────────────────────────────────────┘
横切 core/ + models/：config / db / redis（限流+进度）/ errors / calendar / 所有 DB 模型
```

### L4 接入层（`api/__init__.py` + `tasks/router.py`，挂载于 `main.py`）

只做三件事，不写任何业务逻辑：

| 路由 | 功能 | 说明 |
|---|---|---|
| `POST /api/collect/tasks/{facet}/{name}` | 建任务 | 校验 facet/name 存在 → 调 `create_task` → 立即返回 `{task_id, total}` |
| `GET /api/collect/tasks/{task_id}` | 查进度 | 读 Redis Hash，直返 `status/total/done/success/fail/saved_total/message` |
| `GET /api/collect/tasks?limit=` | 最近任务 | 读 Redis capped list `collect:tasks`（200 条封顶） |
| `GET /api/collect/services` | 目录 | 返回全部 collector 元数据（`name/facet/kind/default_params/query_path`），前端靠 `kind` 渲染 |
| `GET /api/collect/query/{name}` | 实时直查 | 调 `service.get()`，不入库、不建任务 |

现状 `POST /api/collect/{facet}/{name}` 同步直调 `collect()` 的入口**下线**（或保留为马甲，内部转调 `create_task`，不再直调 `collect()`）。

### L3 编排层（`tasks/manager.py` + 新建 `tasks/log_repo.py`）

唯一的时间展开点 + 唯一的任务执行点：

- **`_expand(cls, params)`**：把一次任务请求展开为 N 次单步 `collect(params)` 调用参数。
  - 增量型（含 `trade_date`）：`start/end_date` 区间 → 按交易日（读 `tech_calendar`，表空回退周一~五）展开为 N 个 `{trade_date}`；单 `trade_date` → 1 次；都不传 → 今天 1 次；`trade_date` 与区间同传直接 400。
  - 区间自理型（含 `start/end_date`，如 `daily_kline`）：service 内部已处理区间，单次透传。
  - 无日期型（`stock_basic`/概念三件套）：传任何日期直接 400，避免静默忽略。
- **`_run(task_id, cls, calls, mode)`**：循环 `await cls().collect(单步)`，每步只写 Redis（`done/success/fail/saved_total/message/updated_at`），单步异常记账后继续跑剩余步；收尾写 `done/failed + finished_at` 并设 TTL 7 天。
- **`create_task / get_task_state`**：建任务（校验→展开→写日志→写 Redis→`asyncio.create_task` 后台跑→立即返回），读进度。
- **日志三态**（`log_repo.py` 封装，`manager.py` 首尾各调一次，中间高频更新只碰 Redis）：
  1. 创建：`INSERT collect_log(task_id, queued, params, range_start/end)` + Redis `hset queued`；
  2. 更新：每完成一步只 `hset` Redis，不碰 DB；
  3. 终态：`UPDATE collect_log SET status/saved_total/finished_at` 一次 + Redis 设 TTL。

### L2 业务层（`collectors/*_service.py`，协议见 `collectors/base.py`）

三类 service，同一结果类型 `CollectResult(total/success/fail/skip/saved/message)`：

| kind | 成员 | `collect(params)` 约定 | 入库 |
|---|---|---|---|
| `incremental` 增量（17 + news） | `daily_kline/adj_factor/suspend/name_change/moneyflow/moneyflow_hsgt/top_list/top_inst/block_trade/margin/hsgt_top10/limit_list_d/daily_basic/fin_income/top10_holders/top10_floatholders/dividend/holder_number/concept_index_daily/news` | 只收**单点**（单 `trade_date` 或等价单步键），区间展开由 L3 做 | 按表 UK `pg_insert(...).on_conflict_do_update` 做 upsert，禁止 `delete+insert` |
| `full` 全量（4 个） | `stock_basic/stock_concepts/concept_list/concept_members` | 无日期参数，全量快照覆盖；传日期直接由 L3 拒绝 | 全量覆盖写 |
| `realtime` 实时（3 + 1 占位） | `minute_kline/concept_minute/concept_snapshot`（+ 空壳 `sentiment`） | 无 `collect()`（或直接拒绝），只实现 `get()` 供 L4 `query` 调用 | 不入库 |

- 限流/并发在 service 内自决：`RATE_LIMIT=(source, max_count, window)` 走 `core/redis.check()`（tushare/adata 各一滑动窗口键）；`CONCURRENCY` 控制 service 内部 `asyncio.Semaphore`。
- 前端一套时间组件、两套文案：增量类显示 `start/end_date`（其中 `fin_income/holder_number` 标注“公告日期范围”，`top10_*` 标注“报告期范围”，`news` 换成“近 N 天”→`minutes`，`dividend/concept_index_daily` 标注“全拉后按范围过滤”）；全量类只显示“全量覆盖”横幅；实时类不进采集页。
- `collectors/__init__.py` 注册表：`BY_NAME` 做 `name → class` 唯一映射，`kind` 字段给 L3/L4 做分流依据。

### L1 数据源层（`core/*_client.py` + `collectors/**/*Fetcher.py`）

- `Fetcher` 唯一职责：调 SDK 拿数，转 BO（Pydantic `BaseModel`）返回 `list[BO]`，**不碰 DB、不碰 Redis**（见 `base.py: BaseFetcher.fetch()`）。
- `core/tushare_client.py` / `adata_client.py` / `pytdx_client.py`：SDK 连接与会话管理，新增数据源只加一个 client + 一批 Fetcher，上层不动。

### 横切（`core/` + `models/`）

- `core/config.py`：`DATABASE_URL / RAW_DATABASE_URL / REDIS_URL / TUSHARE_TOKEN / API_V1_PREFIX` 等。
- `core/db.py`：`db_session_factory` + `close_db`（`lifespan` 关闭时调用）。
- `core/redis.py`：三合一（client 单例 + `check_rate_limit` 滑动窗口 + `check()` 业务封装）+ 任务进度 Hash 读写。
- `core/errors.py`：`DomainError / RateLimited / SourceUnavailable / InvalidParams / NotSupported`，`main.py` 统一转 HTTP 状态码。
- `core/calendar.py`（建议从 `manager._trading_days` 抽出）：交易日查询，表空/异常回退自然日。
- `models/*.py` + 新建 `models/collect_log.py`：各业务表 DB 模型与采集日志表模型。

## 2. 全异步任务时序

```
Java POST /tasks/{f}/{n} {start_date, end_date, ...}
 │→ L4 校验 → L3 _expand → INSERT collect_log(queued) → Redis hset(queued)
 │→ asyncio.create_task(_run) → 立即返回 {task_id, total}
 │→ _run：for 每步 await service.collect(单步) → Redis hset(进度)
 │→ 收尾：Redis hset(done/failed, finished_at) + expire 7天；UPDATE collect_log 终态
前端 --GET /tasks/{id}--> L4（读 Redis）轮询进度条
任务终态后 --GET /collect/logs--> Java（查 PG collect_log）看历史审计
```

## 3. 重启恢复（已定方案：running/queued → failed）

`main.py lifespan.startup` 中调 `recover_stale_tasks()`：

```python
ids = redis.lrange("collect:tasks", 0, 200)
for tid in ids:
    st = redis.hgetall(f"collect:task:{tid}")
    if st["status"] in ("queued", "running"):
        now = utcnow()
        redis.hset(key, {"status": "failed", "finished_at": now,
                         "message": (st.message + "；服务重启中断，已终止")[:800]})
        UPDATE collect_log SET status='failed', finished_at=now, message=...
          WHERE task_id=tid AND status IN ('queued','running')
```

- 依据就是 Redis `collect:tasks` capped list，无需 SCAN。
- 效果：重启后前端看到明确 `failed（服务重启中断）` 而不是永远转圈；`collect_log` 终态一致；重跑同一区间因 upsert 幂等而安全。
- 约束：保持单 worker（`TASKS` 仍进程内 dict），恢复逻辑不依赖它。

## 4. 存储设计

**`collect_log`（PG，Java 与 collector 共库；collector 写、Java 查）**

```sql
task_id TEXT PK, facet TEXT, name TEXT, kind TEXT, mode TEXT,
params_json JSONB, range_start DATE, range_end DATE,
status TEXT,            -- queued / running / done / failed
total INT, done INT, success INT, fail INT, saved_total BIGINT,
message TEXT,
created_at TIMESTAMPTZ, started_at TIMESTAMPTZ, finished_at TIMESTAMPTZ
```

**Redis（临时，高频）**

- `collect:task:{id}` Hash：`status/total/done/success/fail/saved_total/message/created/started/updated/finished_at`，TTL 7 天。
- `collect:tasks` List：最近任务 id，`ltrim` 200 封顶。
- `collect:rl:tushare / collect:rl:adata`：滑动窗口限流键。
