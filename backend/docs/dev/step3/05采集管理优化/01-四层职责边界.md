# 01 · 四层职责边界（先读这篇）

> 目的：纠正「采集方案 = 封装 fetcher」这个理解偏差。
> 结论：**fetcher 不动；方案不直接封装 fetcher，中间还有一层采集任务。**

---

## 1. 四层结构

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 采集方案 collect_plans              ← 本次改造对象                 │

└──────────────────────────┬──────────────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────────────┐
│ ② 方案项 collect_plan_items             ← 本次新增                   │
│    存：plan_id + task_type + params + enabled + sort_order          │
│    职责：决定「触发时按什么顺序跑哪些接口、各带什么参数」               │
└──────────────────────────┬──────────────────────────────────────────┘
                           │ submit(task_type, item.params)
┌──────────────────────────▼──────────────────────────────────────────┐
│ ③ 采集任务 BaseCollectTask 子类        ← 不改                       │
```

由 `RealtimeQueryFramework` 加缓存+单飞+限流，**不建采集任务、不进方案**。

**不能加入 `collect_plan_items`**（见 `03-三表重构方案.md` §4.3 校验规则）。

## 2. 为什么 plan 不能直接关联 fetcher

你原话是「plan 关联 fetcher 的记录」。**方向对，但关联的键必须是 `task_type`，不是 Protocol 名。**

原因：`plan` 触发时调的是 `submit(task_type, params)`，而 `submit` 内部是：

```344:346:D:\codes\Attribution_Analysis\backend\src\application\service\collect_manage_service.py
    def handler(self, task_type: str) -> BaseCollectTask:
        handler = self._task_registry.get(task_type)
        if handler is None:
```

`task_registry` 是一张 `task_type → BaseCollectTask 实例` 的字典。
**`task_type`（如 `cap_top_list`）是唯一的执行入口键**，
Protocol 名（`TopListFetcher`）只是任务内部用来 `get_registry().get(...)` 拿实例用的。

所以三张表的关联关系是：

```
collect_plan_items.task_type  ──FK──▶  collect_fetchers.task_type  ──▶  采集任务注册表（代码）
                                        （同一个字符串，两边对账）
```

**`collect_fetchers` 与代码的一致性由启动期校验保证**（见 §4），
不靠 DB 外键——因为代码里的注册表不在 DB 里，DB 外键管不到。

## 4. `collect_fetchers` 与代码的一致性保证

`collect_fetchers` 是**代码的镜像**，不是配置源。代码才是唯一事实来源。

### 4.1 启动期双向校验

```
启动时：
  代码侧：registry.supported_types() → 得到 23 个 task_type
  DB 侧  ：SELECT task_type FROM collect_fetchers

  对账逻辑（_sync_fetcher_catalog）：
    ① 代码有、DB 无 → 自动 INSERT（补录）
    ② DB 有、代码无 → 记 WARNING 并标 status='orphan'（不删除，保留现场）
    ③ 两边都有     → 比对 label/description/default_params，不一致记 WARNING
```

### 4.2 为什么不做成"DB 是源"

如果 DB 是源，就得处理"DB 删了一行但代码还在"的漂移——
调度时 `handler(task_type)` 抛 `UnknownTaskType`，
用户看到的是「定时任务莫名不跑了」，排查成本极高。

**镜像 + 启动期补录**的方案：DB 缺了自动补，DB 多了标 orphan 并在 UI 上禁用，
两种漂移都有明确日志。

### 4.3 保存方案时的前置校验

用户配置方案时，`save_plan` 必须校验引用的 `task_type` 存在且 `status='ready'`：

```python
async def _validate_items(self, items: list[dict]) -> list[dict]:
    """校验方案项：task_type 必须已注册、status=ready、不是实时接口"""
    for it in items:
        task_type = it.get("task_type")
        if self._realtime_registry.get(task_type) is not None:
            raise ValueError(f"{task_type} 是实时接口，不能加入方案")
        handler = self.handler(task_type)          # 未注册 → UnknownTaskType
        if handler.status != "ready":
            raise ValueError(f"{task_type} 尚未实现，不能加入方案")
```

**这与现有 `_check_group` 的校验逻辑完全一致**（`collect_manage_service.py:472-479`），
只是从 group 迁移到 plan。

## 5. 采集任务的通用契约（不动的部分）

```238:248:D:\codes\Attribution_Analysis\backend\src\infrastructure\adapter\scheduler\collect\base.py
    async def list_units(self, params: dict) -> list[str]:
        """本次要跑的单元（股票代码 / 交易日 / ...）"""
        raise NotImplementedError(f"{type(self).__name__} 未实现 list_units")

    async def collect_one(self, unit: str, params: dict) -> UnitResult:
        """采一个单元并落库；失败抛异常"""
        raise NotImplementedError(f"{type(self).__name__} 未实现 collect_one")

    @property
    def supports_collect_one(self) -> bool:
        return type(self).collect_one is not BaseCollectTask.collect_one
```

| 方法 | 谁调 | 作用 | 本次 |
|------|------|------|------|
| `list_units(params)` | 框架 `estimate_total` / `run` | 展开成待跑单元 | 不动 |
| `collect_one(unit, params)` | 框架 `run` | 采一个单元并落库 | 不动 |
| `run(params, on_unit_done)` | `execute_task` | 主循环；遍历+并发+重试一轮 | 不动 |
| `estimate_total(params)` | `prepare` | 预估单元数 | 不动 |
| `default_params` | 参数合并 | 默认参数 | **语义变**（见 §6） |
| `concurrency` / `retry_delay` | `run` | 并发数 / 重试间隔 | 不动 |

## 6. 参数来源：从三层变两层

这是本次重构里**唯一有行为损失**的地方，需要你确认。

### 6.1 现在的三层

```253:261:D:\codes\Attribution_Analysis\backend\src\application\service\collect_manage_service.py
    async def resolve_params(self, task_type: str, params: Optional[dict] = None) -> dict:
        handler = self.handler(task_type)
        async with self._session_factory() as session:
            plan = await self._config_repo.get_plan(task_type, session)
        return {
            **handler.default_params,

            **(params or {}),

```

```
手动传入  >  方案 params  >  default_params
```

### 6.2 改后

**但方案参数没消失——它迁移到了 `collect_plan_items.params`！**

```
手动传入  >  方案项 params  >  default_params
```

代码上只是把"查 plan"换成"查 plan_item"：

```python
async def resolve_params(
    self, task_type: str, params: Optional[dict] = None,
    plan_item_params: Optional[dict] = None,   # ← 新增
) -> dict:
    handler = self.handler(task_type)
    return {
        **handler.default_params,
        **(plan_item_params or {}),
        **(params or {}),
    }
```

### 6.3 所以参数能力是增强而非削弱

| 能力 | 现在 | 改后 |
|------|------|------|
| 手动启动传参 | ✅ | ✅ |
| 方案级默认参数 | ✅（每个接口一份） | ✅（**每个方案×每个接口一份**） |
| 同一接口在两个方案用不同参数 | ❌（`task_type` unique 锁死） | ✅ |
| 手动启动时覆盖方案参数 | ✅ | ✅ |

**唯一的真实损失**：原来 23 个接口各有一条"默认方案"（自动存在，不用配），
改后方案要**手动创建**。

✅ **已决策：不迁移**（`05-待确认问题.md` Q2）。
理由：`enabled=true` 的方案有 **0 条**，说明这个功能实际还没在用；
23 条"什么都不会发生"的空方案反而会让人误以为"每个接口都必须配一个方案"。

## 7. 命名说明

`collect_plans` 叫"方案"其实比原来准确了 —— 改后它真的存"采什么 + 什么时候采"，
不再是"只有什么时候采"。

| 概念 | 表 | 中文名 |
|------|-----|--------|
| 接口元数据镜像 | `collect_fetchers` | 采集接口 |
| 触发 + 编排配置 | `collect_plans` | 采集方案 |
| 方案的组成项 | `collect_plan_items` | 方案项 |
| 代码里的执行单元 | `BaseCollectTask` 子类 | 采集任务 |

**本轮不改名**（表名 / API 路径 / 前端组件名都沿用），纯命名重构留待后续。
