# 06 统一入口与对外暴露

> 对应 README 流程 ①②（命令 + 门面）。业务 Service 迁移在 P4，HTTP / Agent 在 P6。

## 1. 三种调用方

| 调用方 | 需要什么 | 用哪个入口 |
| :-- | :-- | :-- |
| 应用层 Service（业务代码） | 取数，不入库，要类型提示 | `gateway.fetch(XxxPort, XxxParams(...))`；实时数据加 `policy=QUERY`（05） |
| 采集管理 / 采集方案 / 定时 | 取数并入库，带进度和历史 | 不变：`CollectManageService.submit / run_plan`，任务内部走 Gateway（04） |
| Agent / HTTP / 采集管理"试查" | 运行时才知道调哪个接口 | `DataQueryService.query(name, params)`（§4.1），内部 `gateway.invoke(DataCommand(...))` |

- "只取数"走 Gateway，"取数 + 入库"走采集任务（`run_one` 同步单元或 `submit` 后台任务），两者不混。
- 路由不直接调 Gateway，统一经应用层 Service（DDD.md §5 "controller 跨过 app 层"）。
- 按名调用（`invoke` + `DataCommand`）只出现在 `DataQueryService` 里；其他应用层代码一律类型化调用。

## 3. 统一目录

```
XxxPort（取什么，23 个）
  ├── 采集任务（取 + 入库，21 个，task_type 不变）          → /collect/catalog（不变）
  ├── 声明了 cache 的 Port（实时接口，2 个）                 → /collect/catalog（不变，kind=realtime）
  └── 全部 Port（直接调用）                                  → /data/catalog（新增）
```

- `/collect/catalog` 返回结构不变，前端不用改；元数据改为从 Port 读取（04 §7、05 §5）。
- `main.py` 中 `collect_fetchers` 表的对账逻辑不变，对账的是采集任务和实时接口；其余 Port 不入这张表。

## 4. HTTP 接口（P6）

### 4.1 DataQueryService（P3 先建，供"试查"使用）

按名调用的统一应用层入口。HTTP、Agent、采集管理"试查"都经过它，路由和 Agent 不直接碰 Gateway：

```python
# application/service/data_query_service.py
MAX_ITEMS = 5000

class DataQueryService:
    def __init__(self, gateway: DataGatewayPort): ...

    def catalog(self) -> list[PortInfo]:
        return self._gateway.catalog()

    async def query(self, name: str, params: dict, *, source: str | None = None) -> DataResult:
        res = await self._gateway.invoke(DataCommand(name, params, source=source, policy=CallPolicy.QUERY))
        if len(res.items) > MAX_ITEMS:
            raise InvalidParams(f"返回 {len(res.items)} 条，超过上限 {MAX_ITEMS}，请缩小范围或改用采集任务入库")
        logger.info("data.query %s source=%s n=%d %dms", name, res.source, len(res.items), res.latency_ms)
        return res
```

- 固定 `policy=QUERY`：限频不等待，避免 HTTP 请求挂 60 秒；实时类 Port 自动走缓存。
- 条数上限、调用日志在这里做，路由只做参数透传和错误映射。
- 权限沿用项目现有方式，在路由上加 `require_permission(...)` 依赖。

### 4.2 路由

```
GET  /api/v1/data/catalog
POST /api/v1/data/{name}       body: {"params": {...}, "source": "tushare" | null}
```

`GET /data/catalog` 响应：

```json
[
  {
    "name": "moneyflow",
    "label": "个股资金流向",
    "facet": "capital",
    "sub_facet": "moneyflow",
    "description": "...",
    "unit": "trade_date",
    "realtime": false,
    "params_schema": { "...": "MoneyflowParams.model_json_schema()" },
    "item_schema": { "...": "CapMoneyflowBO.model_json_schema()" },
    "adapters": [{ "tool": "tushare", "origin": "tushare", "origin_label": "Tushare", "priority": 10 }]
  }
]
```

`POST /data/{name}` 响应：

```json
{ "items": [ ... ], "source": "tushare", "cached": false, "fetched_at": "...", "latency_ms": 820, "attempts": [] }
```

错误映射：

| 异常 | HTTP |
| :-- | :-- |
| 未知 `name` | 404 |
| `InvalidParams` | 422 |
| `NotSupported` | 400 |
| `RateLimited` / `SourceUnavailable`（全部数据源失败） | 503，响应带 `attempts` |

约束：

- 路由经 `DataQueryService`（§4.1），不直接 import Gateway。
- 这些接口会消耗 tushare 积分和同花顺 IP 配额，路由必须加 `require_permission(...)`（权限码按现有 RBAC 定义）。
- 路由只做参数透传和错误映射，不写业务逻辑。

## 5. Agent 工具

Agent 侧不需要额外定义工具，直接由目录生成：

```python
def build_agent_tools(svc: DataQueryService) -> list[dict]:
    return [
        {
            "name": f"data_{p.name}",
            "description": f"{p.label}：{p.description}",
            "parameters": p.params_schema,
        }
        for p in svc.catalog()
    ]
```

调用时 `await svc.query(name, args)`。新增一个 Port，Agent 自动多一个工具。Params 用了枚举、`Field` 约束和 `extra="forbid"`（01 §4.1），生成的 JSON Schema 会带上可选值和范围，Agent 传错参数会拿到明确的 `InvalidParams` 提示。

如果 Agent 需要"采集并入库"，调用现有的 `/collect/tasks` 提交任务，不在 Gateway 里做入库。
