# 接口字段与数据库表结构对账 — 修复方案

> 目标：以 `docs/backend-docs/data/{tushare,adata,pytdx}.md` 三份接口文档的**输出字段**为唯一事实来源，逐一核对 `raw_data_db`（`raw_data-2026-10-18_150731-dump.sql`）中 24 张表的字段，给出修复 SQL。
>
> 范围：**只动表结构**，不动 fetcher、不动 SQLAlchemy ORM、不动路由。修复后所有"已建表"的字段都能 1:1 写入接口返回数据；fetcher 同步工作在后续 PR 推进。
>
> ⚠️ **不修改代码**。本文只产出 `ALTER TABLE` / `CREATE TABLE` 脚本，**实际执行**由 DDL PR 完成。

---

## 0. 背景

- **数据源**：3 份接口文档共 **28 个接口**（Tushare 21 + Adata 6 + Pytdx 1）。
- **当前 DB**：24 张 `raw_data` 表，分布在 `tech_*` / `capital_*` / `fundamental_*` 前缀下。
- **采集 service**：27 个 fetcher（部分表无 fetcher，部分 fetcher 无表）。
- **核对原则**：
  1. 接口文档的**输出字段** = 必存字段（除非明显业务无意义）
  2. 表里的**多余字段** = 业务扩展字段（先保留，不删，文档化即可）
  3. 字段名重命名（如 `vol → volume`、`pct_chg → change_pct`）= **设计选择**，不动列名，由 fetcher 转换

## 2. P0 严重问题（先修，否则写库就崩）

### 2.1 `tech_suspend.suspend_timing` 类型错

**问题**：Tushare 文档 `suspend_timing` 字段类型为 `str`（描述为"日内停牌时间段"，如 `"09:30-10:00"`），但表里定义为 `date`，写库会抛 `DataError: invalid input syntax for type date`。

**修复**：将列类型从 `date` 改为 `varchar(32)`。

```sql
ALTER TABLE public.tech_suspend
    ALTER COLUMN suspend_timing TYPE varchar(32)
        USING (suspend_timing::varchar);
```

### 2.2 `fundamental_concept_snapshot` 字段语义错位

**问题**（两处）：

1. Adata 文档 `get_market_concept_current_ths` 返回 `change`（涨跌额，元）和 `change_pct`（涨跌幅，%），但表里只有 `pct_change` 装的是"涨跌额"（语义错位），且**没有涨跌幅列**。
2. 文档返回 `trade_date`（date 字符串），表里**没有**该列，只有 `trade_time`（timestamp）。

**修复**：

```sql
-- 1. trade_date 列补上
ALTER TABLE public.fundamental_concept_snapshot
    ADD COLUMN IF NOT EXISTS trade_date date;

-- 2. 把"涨跌额"列改名为 p_change（避免与原 pct_change 混淆）
--    原 pct_change 在表里实际装的是 change（涨跌额），重命名
ALTER TABLE public.fundamental_concept_snapshot
    RENAME COLUMN pct_change TO p_change;

-- 3. 补上"涨跌幅"列
ALTER TABLE public.fundamental_concept_snapshot
    ADD COLUMN IF NOT EXISTS pct_change double precision;
```

**说明**：表里原 `pct_change` 列在注释中未给出语义，从文档反推其装的是"涨跌额"，所以重命名为 `p_change`，新列 `pct_change` 装"涨跌幅"。

## 5. P3 决策项（3 处，待产品/架构定）

### 5.1 `tech_calendar` 表的去留

**现状**：表 `tech_calendar` 已建好（exchange, cal_date, is_open, pretrade_date, UK=(cal_date, exchange)），但 **27 个 fetcher 中无对应 service**。

**两种选项**：

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. **补 fetcher**（用 `pro.trade_cal(exchange=...)`） | 完整性好；查询时不用每跑 SELECT 出交易日；停牌补 K 线时必备 | 多一个 cron job |
| B. **删表**（保留 `pro.trade_cal` 实时查询） | 表数量减少 | 每次查询都打 Tushare API（限流） |

**推荐**：**A. 补 fetcher**。原因：
- 交易日历是**低频更新**（一年约 250 天 × 3 交易所 = 750 行），写入成本极低
- 高频查询场景（K 线补齐、停牌判断、采集窗口）都依赖它
- 删表后查询会挤占 Tushare 配额

**对应 fetcher**：在 `collect/tech/` 下新建 `TradeCalTushareFetcher`，归属 `tech` 前缀。

> ⚠️ **本 PR 不实施**，仅记录决策。

### 5.2 `fundamental_concept_snapshot` 的去留

**现状**：表已建，但 P0 修复（§2.2）后还是会有"实时快照"语义——这与 `docs/backend-docs/config/五个基本面.md` 中「分k，实时概念行情变化波动大没必要持久化，实时查询+redis缓存」的指导**冲突**。

**两种选项**：

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. **保留表**，按 §2.2 修字段，**降级为"日频采样"** | AI 训练可用；1 天 1 行（不存分时） | 实时性差 |
| B. **删表**，走 Redis 实时查询 | 符合 doc 指导 | 失去时序数据，AI 无法分析 |

**推荐**：**A. 保留表，但 fetcher 调整为"日频收盘后写 1 行"**。原因：
- Adata 实时接口 `get_market_concept_current_ths` 调用频率有限
- AI 分析概念板块时需要历史快照
- 1 天 1 行，3 年 500 概念 × 1000 天 = 50 万行，可接受

> ⚠️ **本 PR 不实施**，仅记录决策。
